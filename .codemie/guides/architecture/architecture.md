# Architecture Guide

**Purpose**: Structure conventions for the A3 iOS interview-prep PoC.

The project is a learning playground for Senior iOS Developer interview topics. Each demo lives in its own SwiftUI screen, reachable from a central `HomeView`.

---

## Project Layout

```
A3_poc_ios_only/
├── project.yml                   # XcodeGen spec (single source of truth for the Xcode project)
├── A3PocIOS.xcodeproj/           # Generated by `xcodegen generate`
└── Sources/
    ├── A3PocIOSApp.swift         # @main entry → HomeView
    ├── HomeView.swift            # NavigationStack + List of topics
    ├── Info.plist
    ├── Assets.xcassets/
    └── *View.swift               # one file per interview topic / demo
```

**Project root** (`/Users/Svitlana_Korostelova/A3preparationPOC/`) is a wrapper for documentation and Claude config. The actual Xcode app is in `A3_poc_ios_only/`.

## Adding a New Interview Topic

1. Create `A3_poc_ios_only/Sources/<Topic>View.swift`.
2. Wire it into `HomeView.swift` as a new `NavigationLink` row inside the existing `Section`. See `A3_poc_ios_only/Sources/HomeView.swift:14-44`.
3. Run `xcodegen generate` from `A3_poc_ios_only/` so the new file is added to the Xcode target (sources are auto-discovered from `Sources/`).
4. Build & run in Xcode.

The PoC has no separate `Models/` or `Services/` folders — everything sits flat under `Sources/` because each demo is self-contained for study purposes. Do not introduce a folder hierarchy unless a demo genuinely needs shared types.

## View Patterns

Two conventions are used today:

### Pattern A — `@State` only (simple demos)

For demos that just append log lines and don't need cross-screen state.

Examples: `GCDView`, `LocksView`, `StructuredConcurrencyView`, `OperationQueueView`, `SemaphoreView`, `PThreadsView`.

```swift
struct GCDView: View {
    @State private var log: [String] = []
    var body: some View { /* buttons + logView */ }
}
```

See `A3_poc_ios_only/Sources/GCDView.swift:14-46`.

### Pattern B — `@StateObject` + `ObservableObject` ViewModel (MVVM-lite)

Used when subscriptions or async work need a stable lifetime independent of view re-renders.

Example: `CombineView` owns Combine subscriptions in `CombineViewModel`.

```swift
@MainActor
final class CombineViewModel: ObservableObject {
    @Published private(set) var log: [String] = []
    private var cancellables = Set<AnyCancellable>()
}

struct CombineView: View {
    @StateObject private var vm = CombineViewModel()
}
```

See `A3_poc_ios_only/Sources/CombineView.swift:20-31`, `:193-195`.

**Rule of thumb**: use Pattern A by default; switch to Pattern B when the demo needs to hold `Cancellable`s, long-lived `Task`s, or actors across re-renders.

## Common Demo Layout

Every topic screen follows the same visual layout so demos feel consistent:

1. Horizontal `ScrollView` of `demoButton(...)` triggers at the top.
2. `Divider`.
3. Scrollable `logView` showing `[String]` log auto-scrolled to the latest entry.
4. Toolbar `Clear` button.

`demoButton` and `logView` are private helpers duplicated in each view (intentionally — keeps each file self-contained for interview study). See `A3_poc_ios_only/Sources/GCDView.swift:50-82`.

If you find yourself copying a fourth time, extract into a shared file under `Sources/` only then.

## Threading Rules in Demos

- UI mutations always happen on the main thread. Background demos hop back via `DispatchQueue.main.async { ... }` or `@MainActor`.
- The `append(_:)` helper inside views like `GCDView` already wraps `log.append` in a main hop — call it from any thread. See `A3_poc_ios_only/Sources/GCDView.swift:86-92`.
