# 2.2 UIKit

## 1. View Controllers and Navigation

### 1.1 View controller lifecycle

- 
    
    The **sequence of methods** called automatically by iOS when a view controller is created, displayed, hidden, and destroyed.
    
    ```swift
    class MyViewController: UIViewController {
        // MARK: - Properties
        private let userID: String
        private var refreshTimer: Timer?
        
        // MARK: - Initialization
        init(userID: String) {
            self.userID = userID
            super.init(nibName: nil, bundle: nil)
            // ✅ SAFE - Controller properties only
            self.title = "Profile"
        }
        
        required init?(coder: NSCoder) {
            fatalError("init(coder:) has not been implemented")
        }
        
        // MARK: - View Creation
        override func loadView() {
            view = UIView()
            view.backgroundColor = .systemBackground
        }
       
        override func viewDidLoad() {
            super.viewDidLoad()
            // Called once when view loads into memory - one-time setup
            setupUI()
            setupConstraints()
        }
        
        // MARK: - Appearance Cycle
        override func viewWillAppear(_ animated: Bool) {
            super.viewWillAppear(animated)
            // Called every time before view appears - refresh data
            refreshData()
            startLocationUpdates()
        }
        
        override func viewWillLayoutSubviews() {
            super.viewWillLayoutSubviews()
            // Called before Auto Layout runs - prepare for layout changes
            clearCachedSizes()
        }
        
        override func viewDidLayoutSubviews() {
            super.viewDidLayoutSubviews()
            // Called after Auto Layout completes - update frame-dependent UI
            updateScrollViewContentSize()
        }
        
        override func viewDidAppear(_ animated: Bool) {
            super.viewDidAppear(animated)
            // Called after view appears on screen - start active operations
            startTimer()
        }
        
        // MARK: - Disappearance Cycle
        override func viewWillDisappear(_ animated: Bool) {
            super.viewWillDisappear(animated)
            // Called before view disappears - save state
            saveUserInput()
        }
        
        override func viewDidDisappear(_ animated: Bool) {
            super.viewDidDisappear(animated)
            // Called after view disappears - stop operations
            stopTimer()
        }
        
        // MARK: - Memory Cleanup
        deinit {
            // Called when object is destroyed - final cleanup
            refreshTimer?.invalidate()
        }
    ```
    
    **When to Use Each Method**
    
    - **viewDidLoad**: One-time setup (UI creation, delegates)
    - **viewWillAppear**: Refresh data, start services
    - **viewDidAppear**: Start animations, timers
    - **viewWillDisappear**: Save data, pause operations
    - **viewDidDisappear**: Stop timers, cleanup resources
    
    **Memory Management Example**
    
    - 
        
        Always balance resource allocation/deallocation to prevent memory leaks and battery drain
        
        ```swift
        class VideoPlayerViewController: UIViewController {
            private var player: AVPlayer?
            private var timer: Timer?
            
            override func viewDidAppear(_ animated: Bool) {
                super.viewDidAppear(animated)
                player?.play()
                timer = Timer.scheduledTimer(withTimeInterval: 1.0, repeats: true) { _ in
                    // Update progress
                }
            }
            
            override func viewDidDisappear(_ animated: Bool) {
                super.viewDidDisappear(animated)
                player?.pause()
                timer?.invalidate()
                timer = nil
            }
        }
        ```
        

### 1.2. Why do we need viewDidLoad if initial setup methods can be done in init() ?

- 
    
    **The Core Problem: Lazy View Loading -** The **view is not created during `init()`** — it's loaded **lazily**.
    
    ```swift
    class MyViewController: UIViewController {
        
        init() {
            super.init(nibName: nil, bundle: nil)
            
            // ❌ CRASH - view doesn't exist yet!
            view.backgroundColor = .red
            label.text = "Hello"
        }
    }
    ```
    
    ```
    init()          viewDidLoad()        viewWillAppear()    viewDidAppear()  |                   |                     |                  |
      ▼                   ▼                     ▼                  ▼
    [VC Created]    [View Hierarchy       [About to show     [Fully visible
                     is Ready]            on screen]          on screen]
    ```
    

### 1.3. AppDelegate vs SceneDelegate

- 
    
    **AppDelegate** manages the entire app lifecycle, while **SceneDelegate** manages individual window/scene lifecycles (iOS 13+).
    
    **AppDelegate (iOS 2+)**
    
    - One per app
    - Handles app-wide events
    - Manages app launch, background, termination
    - **When** to use:  ****app launch setup, push notifications, background tasks
    
    **SceneDelegate (iOS 13+)** 
    
    - Multiple scenes possible
    - Handles window/UI lifecycle
    - Supports multi-window on iPad
    - **When** to use: UI setup, window management, scene transitions
    
    ```swift
    class AppDelegate: UIResponder, UIApplicationDelegate {
        func application(_ application: UIApplication, 
                        didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
            // App-wide setup
            setupAnalytics()
            return true
        }
        
        func applicationDidEnterBackground(_ application: UIApplication) {
            // Save data, pause operations
        }
    }
    
    class SceneDelegate: UIResponder, UIWindowSceneDelegate {
        var window: UIWindow?
        
        func scene(_ scene: UIScene, willConnectTo session: UISceneSession, 
                  options connectionOptions: UIScene.ConnectionOptions) {
            // Setup UI for this scene
            guard let windowScene = scene as? UIWindowScene else { return }
            window = UIWindow(windowScene: windowScene)
            window?.rootViewController = ViewController()
            window?.makeKeyAndVisible()
        }
        
        func sceneDidEnterBackground(_ scene: UIScene) {
            // Scene-specific background handling
        }
    }
    ```
    
    - **Common Interview "Why" Questions**
        
        **Q: Why was SceneDelegate introduced?** A: To support multiple windows/scenes, especially on iPad. Separates UI lifecycle from app lifecycle.
        
        **Q: Why keep both delegates?** A: AppDelegate handles app-wide concerns (push notifications, app launch), SceneDelegate handles UI-specific concerns.
        
        **Q: Why might you not use SceneDelegate?** A: Supporting iOS 12 and below, or simple single-window apps where the complexity isn't needed.
        
        **Q: Why does SceneDelegate manage the window property?** A: Each scene can have its own window, allowing multiple UI instances of the same app.
        
    
    In **modern SwiftUI** (iOS 14+), you don't need either — use the **`@main` App struct** instead.
    
    **When You STILL Need AppDelegate**
    
    ```swift
    @main
    struct MyApp: App {
        // Attach AppDelegate to SwiftUI App
        @UIApplicationDelegateAdaptor(AppDelegate.self) var appDelegate
        
        var body: some Scene {
            WindowGroup {
                ContentView()
            }
        }
    }
    
    class AppDelegate: NSObject, UIApplicationDelegate {
        func application(_ application: UIApplication,
                         didFinishLaunchingWithOptions...) -> Bool {
            // Firebase, push notifications, third-party SDKs
            FirebaseApp.configure()
            return true
        }
    }
    ```
    
    ### **Common reasons to keep AppDelegate:**
    
    | **Reason** | **Example** |
    | --- | --- |
    | 🔥 Third-party SDKs | Firebase, Analytics |
    | 📱 Push Notifications | APNs setup |
    | 🔗 Deep Links | URL handling |
    | 📍 Background modes | Location, fetch |

### 1.5. What are the differences between modal and push navigation, and when would you use each?

- **Push** adds a view controller onto a `UINavigationController`'s stack — it's for **drilling down** into a hierarchical flow (list → detail). The user goes "deeper" and expects a **Back** button to return to where they came from.
- **Modal (`present`)** shows a view controller **on top of everything**, in its own presentation context, independent of any navigation stack. It's for **self-contained tasks** (compose, sign in, settings) that interrupt the current flow and must be explicitly **dismissed**.

| | Push | Modal (`present`) |
| --- | --- | --- |
| **API** | `navigationController?.pushViewController(_:animated:)` | `present(_:animated:completion:)` |
| **Requires** | A `UINavigationController` | Nothing — any VC can present any VC |
| **Transition** | Slide in from the right | Slide up from bottom (default), or per `modalPresentationStyle` |
| **Dismissal** | Automatic back button / swipe-back gesture / `popViewController` | Must call `dismiss(animated:)` yourself (usually via a Cancel/Done button) |
| **Relationship to stack** | Becomes part of the existing navigation stack | Presented VC gets **its own stack context**; presenting VC stays in memory underneath |
| **Typical use** | Continuing a flow, drilling into detail | Interrupting the flow: forms, alerts, onboarding, camera, share sheet |

**Push example**

```swift
let detailVC = DetailViewController()
navigationController?.pushViewController(detailVC, animated: true)

// back
navigationController?.popViewController(animated: true)
```

**Modal example**

```swift
let composeVC = ComposeViewController()
composeVC.modalPresentationStyle = .pageSheet   // .fullScreen, .formSheet, .overFullScreen…
composeVC.modalTransitionStyle = .coverVertical
present(composeVC, animated: true)

// dismiss (from the presented VC, or from the presenter)
dismiss(animated: true)
```

**Storyboard segues** — the same distinction exists as segue kinds:

| Segue | Equivalent to |
| --- | --- |
| **Show** (`push`) | `pushViewController` — requires embedding in a nav controller |
| **Show Detail** | Push on compact size classes, modal-like on regular (split view) |
| **Present Modally** | `present(_:animated:)` |
| **Present as Popover** | Anchored modal presentation, mainly iPad |

**`UIModalPresentationStyle` options** (*other* ways to configure a modal):

| Style | Behavior |
| --- | --- |
| `.fullScreen` | Covers the entire screen, presenter's view is removed from the hierarchy |
| `.pageSheet` (default, iOS 13+) | Card-like sheet, shows a peek of the presenter behind it, **swipe-to-dismiss** enabled |
| `.formSheet` | Centered, smaller card (mostly iPad) |
| `.overFullScreen` / `.overCurrentContext` | Covers the screen but keeps the presenter in the view hierarchy — needed for transparent/blurred backgrounds |
| `.popover` | Anchored bubble from a source view/bar button (iPad, or iPhone via adaptive presentation) |

**Disable pull-to-dismiss (iOS 13+):** the `.pageSheet` style lets users swipe down to dismiss, which can lose unsaved data (e.g. a half-written form). Prevent it with:

```swift
composeVC.isModalInPresentation = true // blocks interactive/pull-to-dismiss
```
You can still handle `presentationControllerDidAttemptToDismiss(_:)` to show a confirmation alert when the user tries to swipe it away.

**When to use which**

- Use **push** for hierarchical navigation the user should be able to back out of step-by-step (list → item → sub-item).
- Use **modal** for a focused, temporary task that's logically separate from the current screen and needs an explicit exit (new item creation, login, alerts, share sheets, full-screen media).
- *Other* options worth knowing: **popover** (contextual, iPad-style), **custom transitions** (`UIViewControllerAnimatedTransitioning` for bespoke animations, e.g. a card that morphs from a cell), and `UISplitViewController` (push-like on iPhone, side-by-side "master-detail" on iPad — the adaptive alternative to always pushing).

**Common Interview Questions**

**Q: Can you push without a navigation controller?** A: No — `pushViewController` silently does nothing (or crashes in older iOS versions with an assertion) if `navigationController` is `nil`. You must embed the VC in a `UINavigationController` first.

**Q: What happens to the presenting VC when you present modally?** A: It's not deallocated — it stays in memory and its view is kept in the hierarchy (unless `.fullScreen` removes it) so it can be revealed again on dismiss.

**Q: Why did Apple make `.pageSheet` the default in iOS 13?** A: To give a more lightweight, reversible feel to modals and reduce the jarring "full takeover" of the screen for simple tasks — while still allowing `.fullScreen` when the task genuinely needs it (e.g. camera, video player).

**Q: How do you pass data back from a modal?** A: Delegate protocol, a completion closure set before presenting, or Combine/`@Binding` in SwiftUI — never `unwind segue`-style circular references without care for retain cycles.

### 1.6. How do you manage child view controllers and why is containment important?

**Containment** = embedding one view controller's view inside another (`UINavigationController`, `UITabBarController`, custom containers) while keeping each VC's own lifecycle, layout, and view hierarchy self-contained and independently reusable.

**Why it matters:** without proper containment, if you just do `addSubview(childVC.view)` without the containment calls, the child never gets `viewWillAppear`/`viewDidAppear`, rotation and trait-collection changes aren't forwarded, and `UIKit` doesn't know who "owns" the child — leading to lifecycle bugs, wrong safe-area/status-bar behavior, and memory-management ambiguity.

**The 4 required steps to add a child:**

```swift
func add(_ child: UIViewController, to container: UIView) {
    addChild(child)                       // 1. establish parent-child relationship
    container.addSubview(child.view)      // 2. insert child's view into hierarchy
    child.view.frame = container.bounds   // 3. layout (or Auto Layout constraints)
    child.didMove(toParent: self)         // 4. tell child the move completed
}

func remove(_ child: UIViewController) {
    child.willMove(toParent: nil)         // 1. about to be removed
    child.view.removeFromSuperview()      // 2. remove view
    child.removeFromParent()              // 3. break parent-child relationship
}
```

- `addChild(_:)` / `removeFromParent()` manage the **VC hierarchy** (`parent`/`children`) — this is what forwards `viewWillAppear`, `viewDidAppear`, rotation, trait collection changes, and status bar/appearance queries to the child.
- `willMove(toParent:)` / `didMove(toParent:)` are lifecycle hooks the child can override to know when it's being attached/detached — **always call `didMove(toParent:)` after adding** and **`willMove(toParent: nil)` before removing**, otherwise appearance callbacks won't fire correctly.

**Why containment is important**

| Without containment (`addSubview` only) | With proper containment |
| --- | --- |
| `viewWillAppear`/`viewDidAppear` never called on child | Lifecycle events correctly forwarded |
| Rotation/trait collection changes not propagated | `willTransition(to:with:)` forwarded automatically |
| `UIKit` doesn't know the "owning" VC → ambiguous responder chain, status bar, `additionalSafeAreaInsets` | Child is a first-class part of the VC tree |
| Child VC leaks or behaves like a plain view | Clean modular, reusable, independently testable screens |

**Real-world example:** a custom paged/segmented container (like a mini `UIPageViewController`) that swaps children when a segment changes:

```swift
final class ContainerViewController: UIViewController {
    private var current: UIViewController?

    func display(_ vc: UIViewController) {
        if let current { 
            current.willMove(toParent: nil)
            current.view.removeFromSuperview()
            current.removeFromParent()
        }
        addChild(vc)
        vc.view.frame = view.bounds
        view.addSubview(vc.view)
        vc.didMove(toParent: self)
        current = vc
    }
}
```

`UINavigationController` and `UITabBarController` do exactly this under the hood — that's why pushing/switching tabs correctly fires `viewWillAppear`/`viewDidDisappear` on the right VCs.

**Common Interview Questions**

**Q: What happens if you skip `addChild`/`didMove(toParent:)` and just add the view?** A: The child's view displays, but it's an "orphan" — no lifecycle forwarding, wrong `parent`, and Auto Layout/safe-area/status-bar queries can behave unexpectedly.

**Q: Do container view controllers need extra work for rotation?** A: No — as long as containment is set up correctly, `viewWillTransition(to:with:)` and trait collection changes are automatically forwarded to all children.

**Q: When would you build a custom container instead of using `UINavigationController`/`UITabBarController`?** A: When you need custom transition animations, side-by-side/overlapping children (e.g. a drawer, paged onboarding, or split panels) that Apple's stock containers don't support.

### 1.7. TabViewController example

`UITabBarController` is a **container VC** (see 1.6) that manages an array of `viewControllers`, shows one at a time, and lets the user switch via the tab bar. Each tab is usually a `UINavigationController` wrapping the actual screen, so pushing works independently per tab.

```swift
final class MainTabBarController: UITabBarController {

    override func viewDidLoad() {
        super.viewDidLoad()

        let home = UINavigationController(rootViewController: HomeViewController())
        home.tabBarItem = UITabBarItem(title: "Home", image: UIImage(systemName: "house"), tag: 0)

        let search = UINavigationController(rootViewController: SearchViewController())
        search.tabBarItem = UITabBarItem(title: "Search", image: UIImage(systemName: "magnifyingglass"), tag: 1)

        let profile = UINavigationController(rootViewController: ProfileViewController())
        profile.tabBarItem = UITabBarItem(title: "Profile", image: UIImage(systemName: "person"), tag: 2)

        viewControllers = [home, search, profile]   // order = tab order
        selectedIndex = 0
        delegate = self   // see explanation below
    }
}
```

**What `delegate = self` means:** `UITabBarController` has a `weak var delegate: UITabBarControllerDelegate?` property — the standard **delegation pattern** used throughout UIKit. By writing `delegate = self`, `MainTabBarController` registers *itself* as the object that should be notified about tab bar events (e.g. "user is about to select this tab", "user did select this tab"). It's exactly the same pattern as `tableView.delegate = self` or `scrollView.delegate = self`.

- `self` must conform to `UITabBarControllerDelegate` (done via the `extension MainTabBarController: UITabBarControllerDelegate` below) — otherwise it's a compile error.
- The property is `weak` to avoid a retain cycle (the tab bar controller doesn't own its delegate).
- Without setting `delegate`, `UITabBarController` works fine for basic tab switching — the delegate is only needed if you want to **hook into** the switching process: veto a switch (`shouldSelect`), react after a switch (`didSelect`), or customize animated transitions between tabs (`animationControllerForTransitionFrom:to:`).

**Common tasks:**

```swift
// switch tab programmatically
tabBarController?.selectedIndex = 1

// badge on a tab
tabBarController?.viewControllers?[1].tabBarItem.badgeValue = "3"

// intercept/veto a tab switch
extension MainTabBarController: UITabBarControllerDelegate {
    func tabBarController(_ tabBarController: UITabBarController,
                           shouldSelect viewController: UIViewController) -> Bool {
        // e.g. block leaving an unsaved form, or require login for a tab
        return true
    }
}
```

Each tab's `UINavigationController` is set as the root by `UITabBarController`, which is why `viewWillAppear`/`viewDidDisappear` fire correctly on the visible tab's top VC — same containment mechanism as 1.6.

**Common Interview Questions**

**Q: Why wrap each tab's root VC in its own `UINavigationController`?** A: So each tab keeps its own independent push/pop navigation stack — switching tabs and back preserves where you were in each stack.

**Q: How do you badge a tab or add a "More" overflow?** A: `tabBarItem.badgeValue` for badges; if you have more than 5 tabs, `UITabBarController` automatically adds a "More" tab that lists the rest.

**Q: How would you build this in SwiftUI instead?** A: `TabView { ... .tabItem { ... } }` — conceptually the same container pattern, just declarative.

### 2.2. CA Layer vs UIView

**Core idea:** Every `UIView` is backed by a `CALayer` (`view.layer`). UIView (UIKit) owns **event handling, layout, responder chain, gesture recognizers**; CALayer (Core Animation) owns **rendering, compositing and animation**. UIView is a thin wrapper that forwards drawing/visual work to its backing layer — separation of concerns between "interaction" and "presentation".

| | `UIView` | `CALayer` |
|---|---|---|
| Framework | UIKit | Core Animation |
| Responsibility | touch handling, hit-testing, Auto Layout, responder chain | rendering, compositing (GPU), implicit/explicit animation |
| Can exist standalone | No — nothing to touch without a layer | Yes — sublayers (`CAShapeLayer`, `CAGradientLayer`) can be added directly with no `UIView` |
| Animating a change | `UIView.animate { }` wraps CA under the hood | animate directly via `CABasicAnimation`/`CATransaction`, or get implicit animation for free |
| Cost | heavier (hit-testing, accessibility, layout) | lightweight, cheaper to add many of |
| Typical properties | `frame`, `backgroundColor`, `alpha`, `isHidden` | `bounds`, `position`, `cornerRadius`, `borderWidth`, `shadowXxx`, `transform` (`CATransform3D`), `mask` |

```swift
// UIView always has a backing layer
let view = UIView()
view.layer.cornerRadius = 8
view.layer.borderWidth = 1
view.layer.shadowOpacity = 0.3

// Customizing the backing layer class of a UIView subclass
final class ShapeView: UIView {
    override class var layerClass: AnyClass { CAShapeLayer.self }
    var shapeLayer: CAShapeLayer { layer as! CAShapeLayer }
}

// A CALayer with NO corresponding UIView — cheap, no touch handling
let gradient = CAGradientLayer()
gradient.frame = view.bounds
gradient.colors = [UIColor.red.cgColor, UIColor.blue.cgColor]
view.layer.addSublayer(gradient)
```

**Implicit animation:** changing an animatable `CALayer` property (e.g. `opacity`, `position`, `backgroundColor`) animates automatically via the layer's default *action*, even outside `UIView.animate`. UIKit disables this for view-backed layers unless you're inside an animation block (it wraps changes in `CATransaction` with actions disabled), so `view.layer.opacity = 0` on a plain `UIView`'s layer typically animates implicitly too — to suppress it, wrap in `CATransaction`:

```swift
CATransaction.begin()
CATransaction.setDisableActions(true)
view.layer.cornerRadius = 20   // applied instantly, no implicit animation
CATransaction.commit()
```

**Common Interview Questions**

**Q: Why does UIView need a separate CALayer instead of drawing itself?** A: Separation of concerns — UIKit handles interaction/layout on the main thread, while Core Animation handles rendering/compositing, which can be optimized and driven independently (render server, GPU) without blocking touch handling.

**Q: Can a CALayer exist without a UIView?** A: Yes — you can add `CALayer`/`CAShapeLayer`/`CAGradientLayer` sublayers directly to `view.layer` for effects, masks, or many cheap decorative elements. They don't get touches automatically; you'd hit-test manually if needed.

**Q: Where do properties like `cornerRadius`, `shadow*`, `borderWidth`, `transform` live?** A: On the layer, not the view — you access them via `view.layer.cornerRadius`, etc., because they're rendering concerns, not layout/interaction concerns.

**Q: What decides whether a property change animates implicitly?** A: Whether it happens inside a `CATransaction`/`UIView.animate` block and whether the layer has a delegate providing actions; `UIView`-backed layers get actions disabled outside of explicit animation blocks so plain property assignment doesn't animate.

### 2.3. What is transformation matrix?

**Core idea:** A transformation matrix encodes geometric operations (translate, scale, rotate, skew, perspective) as a single matrix that's applied to a view/layer's coordinate space when rendering. It changes **where/how content is drawn on screen** without touching `frame`/`bounds`/Auto Layout — the layout system still thinks the view is at its original frame; only the *presentation* is transformed.

| | `CGAffineTransform` | `CATransform3D` |
|---|---|---|
| Lives on | `UIView.transform` | `CALayer.transform` |
| Dimensions | 2D (3×3 matrix, last column implicit `0 0 1`) | 3D (4×4 matrix) — supports `z` translation, rotation around x/y, perspective |
| Common ops | translate, scale, rotate, skew | all of the above + 3D rotation, perspective (`m34`) |
| Applied around | `view.center` / layer's `anchorPoint` | layer's `anchorPoint` |
| Interop | `CATransform3DMakeAffineTransform` / `CATransform3DGetAffineTransform` convert between them | |

```swift
// CGAffineTransform — 2D, on UIView
view.transform = .identity
view.transform = CGAffineTransform(translationX: 50, y: 0)
view.transform = view.transform.scaledBy(x: 1.2, y: 1.2)          // combine
view.transform = view.transform.rotated(by: .pi / 4)

UIView.animate(withDuration: 0.3) {
    view.transform = CGAffineTransform(scaleX: 0.9, y: 0.9)
}

// CATransform3D — 3D, on CALayer, e.g. flip/perspective card animation
var transform = CATransform3DIdentity
transform.m34 = -1 / 500                 // perspective (further = smaller)
transform = CATransform3DRotate(transform, .pi / 4, 0, 1, 0)  // rotate around Y axis
view.layer.transform = transform
```

**Matrix form (affine, 2D):**

```
| a  b  0 |      x' = a*x + c*y + tx
| c  d  0 |  →   y' = b*x + d*y + ty
| tx ty 1 |
```
`a,d` = scale, `b,c` = rotation/skew, `tx,ty` = translation — this is exactly why compound transforms (scale + rotate + translate) can be combined by matrix multiplication instead of applying steps separately.

**Common Interview Questions**

**Q: Does changing `transform` update `frame`/constraints?** A: No — `frame` becomes derived/undefined when a non-identity transform is applied (Apple docs warn against reading `frame` on a transformed view); Auto Layout still lays out based on `bounds`/`center` as if untransformed, then the transform is applied on top at render time.

**Q: Why use `transform` instead of animating `frame`?** A: `transform` is GPU-accelerated (pure matrix math on the render layer) and doesn't retrigger layout; animating `frame`/constraints can be more expensive and can fight Auto Layout.

**Q: How do you reset a transform?** A: Set it back to `.identity` (`CGAffineTransform.identity` / `CATransform3DIdentity`) — never try to "undo" by hand-inverting unless you specifically need the inverse matrix (`CGAffineTransform.inverted()`).

**Q: 2D vs 3D — when do you need `CATransform3D`?** A: When you need depth (`z` translation/rotation) or perspective, e.g. flip transitions, card-flip animations, parallax — plain `CGAffineTransform` can't represent perspective or out-of-plane rotation.

### 2.4. How to create custom container view controller if you do not want to use navigation vc?

**Core idea:** Use UIKit's view controller **containment API** — `addChild`, `didMove(toParent:)`, `willMove(toParent:)`, `removeFromParent()` — to embed one or more child VCs' views inside a parent VC. This is the same mechanism `UINavigationController`/`UITabBarController` use internally, but you control the layout/transition yourself (e.g. custom tab switcher, onboarding pager, side menu, a mini "navigation stack").

**Full example — a custom push/pop container (mini nav controller):**

```swift
final class ContainerViewController: UIViewController {
    private var stack: [UIViewController] = []

    private func addChildView(_ child: UIViewController) {
        addChild(child)
        child.view.frame = view.bounds
        child.view.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(child.view)
        NSLayoutConstraint.activate([
            child.view.leadingAnchor.constraint(equalTo: view.leadingAnchor),
            child.view.trailingAnchor.constraint(equalTo: view.trailingAnchor),
            child.view.topAnchor.constraint(equalTo: view.topAnchor),
            child.view.bottomAnchor.constraint(equalTo: view.bottomAnchor),
        ])
        child.didMove(toParent: self)
    }

    private func removeChildView(_ child: UIViewController) {
        child.willMove(toParent: nil)
        child.view.removeFromSuperview()
        child.removeFromParent()
    }

    func push(_ child: UIViewController, animated: Bool = true) {
        let previous = stack.last
        stack.append(child)
        addChildView(child)

        guard animated, let previous else { return }
        child.view.frame = view.bounds.offsetBy(dx: view.bounds.width, dy: 0)
        UIView.animate(withDuration: 0.3) {
            child.view.frame = self.view.bounds
            previous.view.frame = previous.view.frame.offsetBy(dx: -self.view.bounds.width, dy: 0)
        } completion: { _ in
            previous.view.frame = self.view.bounds // reset for reuse if popped back to
        }
    }

    func pop(animated: Bool = true) {
        guard stack.count > 1 else { return }
        let top = stack.removeLast()
        let previous = stack.last!

        // insert `previous` back below `top` before animating out
        view.insertSubview(previous.view, belowSubview: top.view)
        previous.view.frame = view.bounds

        let finish = {
            self.removeChildView(top)
        }
        guard animated else { return finish() }

        UIView.animate(withDuration: 0.3) {
            top.view.frame = self.view.bounds.offsetBy(dx: self.view.bounds.width, dy: 0)
        } completion: { _ in finish() }
    }
}
```

**Q: Why call both `addChild`/`removeFromParent` and `didMove`/`willMove`?** A: `addChild`/`removeFromParent` register the containment relationship (so appearance/rotation/trait events propagate); `willMove(toParent:)`/`didMove(toParent:)` are lifecycle hooks the child can override — call `willMove(toParent: nil)` *before* removing the view, and `didMove(toParent: self)` *after* adding it.

**Q: How do you animate the swap?** A: Use `transition(from:to:duration:options:animations:completion:)`, or manually animate frames as above — both must stay bracketed by the same containment calls.

**Q: Why keep `previous.view` under `top.view` during pop?** A: So the outgoing view slides off while the one underneath is already visible, matching `UINavigationController`'s pop transition instead of flashing a blank container.

### 2.5. Rules for table/collection views; unexpected behaviors

**Core rules you must follow:**

1. **Register before you dequeue.** `register(_:forCellReuseIdentifier:)` / `register(_:forCellWithReuseIdentifier:)` (class or nib) must run before `dequeueReusableCell`, otherwise it crashes (`dequeueReusableCell(withIdentifier:for:)` always crashes without registration; the non-`for:` variant just returns `nil`).
2. **Fully configure every reused cell — every time.** Cells come from a reuse pool, so any property you don't overwrite carries over from whatever row previously used that cell (stale image, checkmark, label text, background color).
3. **Reset transient/async state in `prepareForReuse()`.** Cancel in-flight image loads, reset `accessoryType`, `isSelected`, custom subviews' visibility — anything that isn't driven unconditionally by `cellForRowAt`.
4. **Data source counts must match reality before/after every update.** `numberOfRowsInSection` must reflect the model *before* `reloadData()`, and the delta you pass to `performBatchUpdates` must exactly match the change you made to the backing array — mismatches throw `NSInternalInconsistencyException: Invalid number of rows in section`.
5. **All UI mutations happen on the main thread.** Mutating the model and calling `reloadData`/`insertRows` off the main thread causes crashes or the classic purple runtime warning.
6. **`performBatchUpdates` index-path semantics:** deletes/moves reference the *pre-update* index paths, inserts/moves-to reference the *post-update* index paths — mutate the backing array first, then describe deltas that match it exactly, in one batch call (don't interleave manual `reloadData` with pending batch animations).

**Cell reuse — reset & async race example:**

```swift
final class ImageCell: UITableViewCell {
    private var currentToken: UUID?

    override func prepareForReuse() {
        super.prepareForReuse()
        currentToken = nil          // invalidate any in-flight request
        imageView?.image = nil      // don't show the previous row's image while loading
        accessoryType = .none
    }

    func configure(url: URL) {
        let token = UUID()
        currentToken = token
        ImageLoader.shared.load(url) { [weak self] image in
            guard let self, self.currentToken == token else { return } // cell was reused meanwhile
            self.imageView?.image = image
        }
    }
}
```

**Batch update crash vs. fix:**

```swift
// ❌ Crashes: array mutated, but batch update not called with matching delta
items.remove(at: 2)
tableView.reloadData() // works, but loses row animation — fine if that's acceptable

// ❌ Crashes: says "delete row 2" but array wasn't changed yet
tableView.performBatchUpdates {
    tableView.deleteRows(at: [IndexPath(row: 2, section: 0)], with: .automatic)
} // -> NSInternalInconsistencyException, counts don't match

// ✅ Correct: mutate first, then describe the exact same delta
tableView.performBatchUpdates {
    items.remove(at: 2)
    tableView.deleteRows(at: [IndexPath(row: 2, section: 0)], with: .automatic)
}
```

**Other unexpected behaviors to watch for:**

- **Stale index paths in closures/async callbacks.** By the time an async task completes, the cell at that `indexPath` may now show different data (scrolled/reused). Re-check via `tableView.indexPath(for: cell)` or a per-request token (see example above) rather than trusting a captured `indexPath`.
- **`reloadData()` resets scroll position feel** — it doesn't literally scroll to top, but it discards animations and can shift `contentOffset` when row heights change; prefer targeted `reloadRows(at:)`/`performBatchUpdates`/diffable snapshots for smoother updates.
- **Self-sizing cells need both `estimatedRowHeight` and `rowHeight = UITableView.automaticDimension`**, plus complete, unambiguous constraints pinned to the content view's edges — otherwise you get 0-height or incorrect first-pass layout (visible as a flash/jump).
- **Off-screen cells don't exist.** `cellForRow(at:)` returns `nil` for non-visible rows — never use a cell to store or read your source of truth; keep state in the data model.
- **`willDisplay`/`didEndDisplaying` aren't perfectly paired during fast scrolls or reloads** — don't assume exactly one `didEndDisplaying` per `willDisplay`; guard cleanup code with identity checks (same token/reuse-race pattern as above).
- **Prefetching (`UITableViewDataSourcePrefetching` / `UICollectionViewDataSourcePrefetching`) fires *before* `willDisplay`**, on rows that aren't visible yet — cancel prefetch work in `cancelPrefetchingForRowsAt` if the user scrolls away.
- **Section header/footer reuse has the same pitfalls as cells** — they come from their own reuse pool (`register(_:forHeaderFooterViewReuseIdentifier:)`) and need the same reset discipline.

**Comparison — ways to update table/collection views:**

| Approach | Behavior | Risk |
| --- | --- | --- |
| `reloadData()` | Full rebuild, no animation | Safe but loses animations, can feel jarring, no diffing needed |
| `performBatchUpdates` + `insert/delete/moveRows` | Animated, precise | Manual index-path math — mismatched counts crash |
| `UITableViewDiffableDataSource` / `UICollectionViewDiffableDataSource` + snapshots | Animated diff computed for you from old vs. new snapshot | Safest for concurrent/complex updates (see [2.7](#27-what-is-uidiffabledatasource--why-for-diffable-classes)); requires hashable, unique identifiers |

**Common Interview Questions**

**Q: Why does my app crash with "Invalid number of rows in section" after updating an array and calling `reloadData`?** A: It usually isn't `reloadData()` itself (that always works because it doesn't diff) — the crash comes from a `performBatchUpdates`/`insertRows`/`deleteRows` call whose index-path delta doesn't match the actual change you made to the backing array (wrong count, wrong section, or the array wasn't mutated at all before the animated call).

**Q: Why did the wrong image show up on a cell after fast scrolling?** A: Classic reuse race — an async image load kicked off for a cell showing row N completed after that cell was recycled for row M. Fix by cancelling/invalidating with a per-request token in `prepareForReuse()`, or checking the cell is still associated with the expected index path/URL before applying the result.

**Q: Why is `performBatchUpdates` safer than manual `reloadData` for complex updates, and why might you still prefer diffable data sources?** A: `performBatchUpdates` batches multiple insert/delete/move calls into one animation pass and validates consistency at the end — but you must compute the index-path deltas yourself, which is error-prone for concurrent/rapid updates. Diffable data sources compute the diff between two full snapshots automatically, eliminating manual index-path math and the most common crash class, at the cost of needing stable, hashable item identifiers.

**Q: Why shouldn't you keep application state in table/collection view cells?** A: Cells are ephemeral and reused — a cell for an off-screen row can be `nil` (`cellForRow(at:)` returns `nil`) or already repurposed for different data. State must live in the model/view model; cells should be a pure, stateless projection of that model for whatever index path they're currently configured with.

**Q: What causes self-sizing cells to render at the wrong height briefly, and how do you fix it?** A: Missing/ambiguous constraints to the content view's edges, or omitting `estimatedRowHeight`/`UITableView.automaticDimension`, forces UIKit to guess a height on the first pass before Auto Layout resolves the real one. Fix: pin all edges unambiguously, set both `rowHeight = .automaticDimension` and a reasonable `estimatedRowHeight`, and avoid intrinsic-content-size-less views without explicit constraints.

**Q: Is it safe to update the data source array on a background thread and then call `reloadData` on main?** A: Only if the entire mutation of the array *and* the reload/batch-update call happen on the main thread relative to each other — you can compute the new data off-thread, but the swap of the array reference and any table/collection view API call must be dispatched to main, otherwise you risk data races (reading the array mid-mutation) and UIKit API-on-background-thread crashes/warnings.

### 2.6. Why do we reuse cells in table view or collection view?

- Only a handful of rows are ever visible — reuse keeps memory/CPU proportional to **visible** cells, not total data set size, instead of alloc + Auto Layout pass per row.
- UIKit pools off-screen cells per `reuseIdentifier`; `dequeueReusableCell(withIdentifier:for:)` recycles one instead of creating new.

```swift
tableView.register(ImageCell.self, forCellReuseIdentifier: "ImageCell")
let cell = tableView.dequeueReusableCell(withIdentifier: "ImageCell", for: indexPath) as! ImageCell
cell.configure(with: items[indexPath.row]) // must fully reconfigure - old state may remain
```

- Trade-off: must fully reconfigure/reset (`prepareForReuse()`) every reused cell, or stale data leaks across rows — see [2.5](#25-rules-for-tablecollection-views-unexpected-behaviors).

**Common Interview Questions**

**Q: What happens if a reuse identifier isn't registered?** A: `dequeueReusableCell(withIdentifier:for:)` crashes; the non-`for:` variant returns `nil` instead.

**Q: Why does reuse cause the "wrong image on wrong row" bug?** A: An async load for row N finishes after that cell was recycled for row M; fix with a per-request token invalidated in `prepareForReuse()`.

**Q: Does SwiftUI's `List`/`LazyVStack` need manual reuse?** A: No explicit `reuseIdentifier`, but it's the same idea — lazy/virtualized rendering of only near-visible rows.

### 3.1. What is Auto Layout

- 
    
    Auto Layout is a **constraint-based layout system** in UIKit that automatically calculates the size and position of views based on rules (constraints) you define. Instead of setting fixed frames, you describe **relationships between views**.
    
    ```swift
    let button = UIButton()
    button.translatesAutoresizingMaskIntoConstraints = false
    view.addSubview(button)
    
    NSLayoutConstraint.activate([
        button.centerXAnchor.constraint(equalTo: view.centerXAnchor),
        button.centerYAnchor.constraint(equalTo: view.centerYAnchor),
        button.widthAnchor.constraint(equalToConstant: 100),
        button.heightAnchor.constraint(equalToConstant: 50)
    ])
    
    // Modern Approach with Layout Anchors
    
    // Make button fill width with padding
    button.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 20).isActive = true
    button.trailingAnchor.constraint(equalTo: view.trailingAnchor, constant: -20).isActive = true
    ```
    
    - **Common Interview "Why" Questions:**
        
        **Q: Why set `translatesAutoresizingMaskIntoConstraints = false`?** A: By default, UIKit creates automatic constraints from the view's frame. Setting this to **`false`** lets you use your own constraints.
        
        **Q: Why use Safe Area?** A: Safe Area respects notches, home indicators, and navigation bars, ensuring content isn't hidden.
        
        **Q: Why prefer Layout Anchors over NSLayoutConstraint?** A: Layout Anchors are more readable, type-safe, and less verbose than the old NSLayoutConstraint syntax.
        
        **Q: Why use Stack Views?** A: They automatically manage spacing and distribution of subviews, reducing constraint complexity by 80%.

### 3.2. Difference between frame and bounds in UIView

- 
    - **frame**: The rectangle that defines the view’s position and size in its **superview’s coordinate system**. Useful for layout, **positioning views in their parent**.
    - **bounds**: The rectangle that defines the view’s position and size in its **own coordinate system**. Useful for drawing, handling touch events, or when you want to work within the view’s own space (e.g., custom drawing).
    
    ```swift
    let view = UIView(frame: CGRect(x: 50, y: 100, width: 200, height: 150))
    print(view.frame)  // (50.0, 100.0, 200.0, 150.0)
    print(view.bounds) // (0.0, 0.0, 200.0, 150.0)
    ```
    
    **rotation** or transformation - **frame** changes (relative to superview), but **bounds** usually stay the same (relative to itself).

### // TODO: Sveta What’s wrong with extension for UIImageView that downloads an image and sets it

- 
    1. **no Caching:** every time you set an image, it downloads again, wasting bandwidth and slowing down your app.
    2. **no Cancellation:** if the cell/image view is reused (e.g., in a table view), the old download might finish after reuse, setting the wrong image.

        ```swift
        // BAD EXAMPLE
        
        extension UIImageView {
            func setImage(from url: URL) {
                URLSession.shared.dataTask(with: url) { data, _, _ in
                    if let data = data {
                        DispatchQueue.main.async {
                            self.image = UIImage(data: data)
                        }
                    }
                }.resume()
            }
        }
        ```
        
    - **✅ GOOD** example
        
        ```swift
        let imageCache = NSCache<NSURL, UIImage>()
        
        extension UIImageView {
            func setImage(from url: URL, placeholder: UIImage? = nil) {
                self.image = placeholder
                
                if let cached = imageCache.object(forKey: url as NSURL) {
                    self.image = cached
                    return
                }
                
                URLSession.shared.dataTask(with: url) { data, _, error in
                    guard let data = data, let img = UIImage(data: data), error == nil else { return }
                    imageCache.setObject(img, forKey: url as NSURL)
                    DispatchQueue.main.async {
                        self.image = img
                    }
                }.resume()
            }
        }
        ```
        
        **How does this work?**
        
        - Shows a placeholder while loading.
        - Uses cache to avoid re-downloading images.
        - Sets the image on the main thread.

### What is BezierPath?

- 
    
    UIBezierPath is a UIKit class that lets you **create and draw custom shapes**, lines, and curves programmatically.
    
    **Path vs Drawing**: BezierPath creates the "instructions" for what to draw, but doesn't actually draw anything until you stroke or fill it.
    
    ```swift
    class TriangleView: UIView {
        override func draw(_ rect: CGRect) {
            let path = UIBezierPath()
            
            // Start at top center
            path.move(to: CGPoint(x: rect.midX, y: 20))
            // Draw to bottom left
            path.addLine(to: CGPoint(x: 20, y: rect.height - 20))
            // Draw to bottom right
            path.addLine(to: CGPoint(x: rect.width - 20, y: rect.height - 20))
            // Close the path (back to start)
            path.close()
            
            UIColor.blue.setFill()
            path.fill()
        }
    }
    ```
    
    - **Key Methods**
        - **`move(to:)`** - Move without drawing
        - **`addCurve(to:controlPoint1:controlPoint2:)`** - Draw curves
        - **`addArc()`** - Draw circular arcs
        - **`close()`** - Connect back to start point
        - **`addLine(to:)`** - Draw straight line

### How to round only two angles in view?

- 
    
    using **`CACornerMask`** with the view's layer
    
    ```swift
    // Round only top corners
    view.layer.cornerRadius = 16
    view.layer.maskedCorners = [.layerMinXMinYCorner, .layerMaxXMinYCorner]
    
    // Round only bottom corners  
    view.layer.cornerRadius = 16
    view.layer.maskedCorners = [.layerMinXMaxYCorner, .layerMaxXMaxYCorner]
    
    // Round only left corners
    view.layer.cornerRadius = 16
    view.layer.maskedCorners = [.layerMinXMinYCorner, .layerMinXMaxYCorner]
    ```
    
    - **`cornerRadius`** sets the radius size
    - **`maskedCorners`** specifies which corners to apply the radius to
    - The layer automatically handles the clipping
    
    **Common Use Cases**
    
    - **Bottom sheets**: Round top corners only
    - **Table section headers**: Round top corners of first cell
    - **Card stacks**: Round different corners for layered effect
    
    **Q: Why set `clipsToBounds = true` sometimes?** A: When you have subviews extending beyond the rounded bounds. Though **`maskedCorners`** usually handles this automatically.
    
- 
    
    Use **`UIPinchGestureRecognizer`** to detect pinch gestures and apply scale transformation to your view.
    
    ```swift
    class ZoomableImageView: UIView {
        private let imageView = UIImageView()
        private var initialScale: CGFloat = 1.0
        
        override func awakeFromNib() {
            super.awakeFromNib()
            setupImageView()
            setupPinchGesture()
        }
        
        private func setupImageView() {
            imageView.contentMode = .scaleAspectFit
            imageView.image = UIImage(named: "photo")
            addSubview(imageView)
            imageView.frame = bounds
        }
        
        private func setupPinchGesture() {
            let pinchGesture = UIPinchGestureRecognizer(target: self, action: #selector(handlePinch(_:)))
            addGestureRecognizer(pinchGesture)
        }
        
        @objc private func handlePinch(_ gesture: UIPinchGestureRecognizer) {
            switch gesture.state {
            case .began:
                initialScale = imageView.transform.a // Current scale
            case .changed:
                let scale = initialScale * gesture.scale
                let clampedScale = min(max(scale, 0.5), 3.0) // Limit zoom: 0.5x to 3x
                imageView.transform = CGAffineTransform(scaleX: clampedScale, y: clampedScale)
            default:
                break
            }
        }
    }
    ```
    
    **How It Works**
    
    1. **Gesture Detection**: **`UIPinchGestureRecognizer`** tracks finger distance changes
    2. **Scale Calculation**: **`gesture.scale`** provides zoom factor relative to gesture start
    3. **Transform Application**: **`CGAffineTransform`** scales the view around its center
    4. **State Management**: Store initial scale to maintain smooth continuous zooming
    
    - **Practical Use Case**
        
        **Photo Gallery App**: Users can zoom into photos to see details, zoom out for overview. Essential for examining image quality, reading text in photos, or focusing on specific areas.
        
    - **Common Interview "Why" Questions**
        
        **Q: Why store `initialScale`?** A: Without it, each gesture would reset to 1x scale. We need cumulative scaling across multiple pinch gestures.
        
        **Q: Why clamp the scale values?** A: Prevents unusable zoom levels - too small makes content invisible, too large causes performance issues and poor UX.
        
        **Q: Why use `transform.a` for current scale?** A: **`transform.a`** represents the x-axis scaling factor in the transformation matrix, giving us the current zoom level.
        
        **Q: Why not use `UIScrollView` instead?** A: **`UIScrollView`** is better for complex zoom with panning, but custom implementation gives more control over zoom behavior and visual feedback.
