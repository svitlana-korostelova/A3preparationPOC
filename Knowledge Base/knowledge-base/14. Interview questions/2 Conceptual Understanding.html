Swift & SwiftUI — Q & A

5. Difference between Protocol and Protocol with Associated Types. Why does an enum with associated types need Equatable for custom types?

Regular protocol: usable directly as type (var x: any Drawable). Compiler treats it as existential — concrete type erased at runtime.

Protocol with Associated Types (PAT): introduces a type placeholder. Cannot be used as a plain existential before Swift 5.7. Must use generics (func process<C: Container>(_ c: C)) or, from Swift 5.7, any Container — but that loses the associated type info.

protocol Container {
    associatedtype Item
    func add(_ item: Item)
    func first() -> Item?
}

// Before Swift 5.7 — must use generic constraint
func fill<C: Container>(_ c: inout C, with item: C.Item) { c.add(item) }

// Swift 5.7+ existential — loses Item type
var box: any Container   // Item is opaque

Enum with associated types + Equatable: Swift synthesises Equatable automatically only if every associated value also conforms to Equatable. Custom types without conformance break synthesis → must implement == manually or make associated types Equatable.

enum Outcome {
    case success(MyModel)   // MyModel must be Equatable for auto-synthesis
    case failure(Error)     // Error is not Equatable → must implement == manually
}

6. What are Generics and why are they useful?

Generics let you write type-safe reusable code with a type placeholder resolved at compile time — no boxing/unboxing, no casting, no Any.

func swap<T>(_ a: inout T, _ b: inout T) { let tmp = a; a = b; b = tmp }
func max<T: Comparable>(_ a: T, _ b: T) -> T { a > b ? a : b }

struct Stack<Element> {
    private var items: [Element] = []
    mutating func push(_ item: Element) { items.append(item) }
    mutating func pop() -> Element? { items.popLast() }
}

Why useful:

  • Type safety enforced at compile time — no runtime crashes from wrong casts
  • Performance: compiler can specialise/inline; value types avoid heap allocation
  • DRY: one implementation works for all conforming types (Array, Optional, Result are generic)
  • Constraints (where T: Codable & Identifiable) allow targeted capability requirements

7. Difference between escaping and non-escaping closures. Which to prefer and what is the risk of @escaping?

Non-escaping (default): closure must be called before the function returns. Compiler guarantees it cannot outlive the call. self. inside can be omitted.

@escaping: closure is stored (as property, in a dispatch queue, in an async callback) and called after the function returns.

// Non-escaping — safe, no retain risk
func runNow(_ work: () -> Void) { work() }

// Escaping — closure stored, outlives the call
func runLater(_ work: @escaping () -> Void) {
    DispatchQueue.main.asyncAfter(deadline: .now() + 1) { work() }
}

class Loader {
    var onComplete: (() -> Void)?

    func fetch(_ done: @escaping () -> Void) {
        onComplete = done          // stored → escaping
    }

    func start() {
        fetch { [weak self] in     // weak self breaks retain cycle
            self?.render()
        }
    }
}

Risk: if closure captures self strongly and self also holds the closure → retain cycle, memory leak. Always use [weak self] in escaping closures that reference the enclosing object.

Prefer non-escaping — safer, allows compiler optimisations, no capture semantics to reason about. Use @escaping only when the closure genuinely must outlive the call site.

8. Core difference between a function returning some View and a function marked @ViewBuilder.

some View (opaque return type): compiler-level contract — "I return exactly one concrete type, but I won't name it." Branching between different concrete types is a compile error.

@ViewBuilder: result builder DSL. Lets a function body contain multiple view expressions, if/else, switch. Compiler synthesises _ConditionalContent<A,B> / TupleView etc. Can still return some View as the outer signature — the builder constructs what some View erases.

// some View alone — ONE concrete type, no branching
var body: some View { Text("Hi") }           // ✅
// var body: some View { isOn ? Text("") : Button("") {} }  // ❌ compile error

// @ViewBuilder — multiple types OK via conditional synthesis
@ViewBuilder
var content: some View {
    if isLoggedIn {
        Dashboard()             // one branch
    } else {
        LoginView()             // another branch — different type, fine here
    }
    Footer()                    // additional view — TupleView
}

// ViewBuilder on parameter (how SwiftUI uses it)
struct Card<Content: View>: View {
    @ViewBuilder var content: () -> Content
    var body: some View { content() }
}

Rule of thumb: some View = single opaque type contract. @ViewBuilder = multi-expression/conditional view construction. Both often appear together: @ViewBuilder builds it, some View is the return type.

9. In SwiftUI, what to use for user data operations — init or .task? Can heavy operations in init affect UX?

init: runs synchronously when SwiftUI creates the view struct. Cannot await. Heavy work here blocks the main thread — users see a frozen/blank screen during the delay.

.task: async context, fires after view appears, automatically cancelled when view disappears. Correct place for network calls, DB queries, any async/heavy work.

// ❌ Heavy work in init — blocks main thread
struct CatalogView: View {
    let items: [Item]
    init() {
        items = Database.shared.fetchAll()  // synchronous, main thread frozen
    }
    var body: some View { List(items) { Text($0.name) } }
}

// ✅ .task — async, off main thread, cancels on disappear
struct CatalogView: View {
    @State private var items: [Item] = []
    var body: some View {
        List(items) { Text($0.name) }
            .task {
                items = await api.fetchItems()
            }
    }
}

Rule: init for lightweight, synchronous property setup only. All async/heavy operations belong in .task.

10. Are .onAppear and .task triggered on the same events? What is the difference? For image loading in scrollable list cells, which to use and why?

Both fire when the view appears on screen. Differences:

.onAppear.task
ContextSynchronous closureAsync (await supported)
CancellationNone — task lives until completionAuto-cancelled when view disappears
Re-triggerEach appearEach appear (fresh task)
Dependency paramNoYes: .task(id:) re-runs on value change

For image loading in list cells — use .task. When the user scrolls quickly, cells disappear before their images load. .task cancels the in-flight load automatically, freeing the network slot and preventing a ghost image from landing on a recycled cell.

// ❌ .onAppear — no cancellation; wasted requests for scrolled-past cells
.onAppear {
    Task { image = await imageLoader.load(url) }  // not cancelled on disappear
}

// ✅ .task — cancels when cell leaves screen
.task {
    image = await imageLoader.load(url)  // cancelled automatically on disappear
}

Without .task, rapidly scrolled lists spawn uncontrolled concurrent loads — memory pressure, bandwidth waste, and images appearing in wrong cells after reuse.

11. What is the core difference between SwiftUI and UIKit for you?

UIKit — imperative: you tell the system how to update. Subclass UIViewController, own the lifecycle, mutate views directly (label.text = "…"). Reference types (classes). Full control, full responsibility.

SwiftUI — declarative: you describe what the UI looks like for a given state. Framework diffs and renders. Value types (structs). State change → body re-evaluated → SwiftUI applies minimal diff.

UIKitSwiftUI
ParadigmImperativeDeclarative
TypesClasses (reference)Structs (value)
LayoutAutoLayout / framesModifiers / layout containers
AnimationManual (UIView.animate)Automatic with state change
PreviewsStoryboards / run appLive #Preview
DebuggingView Hierarchy Debugger, breakpointsLimited — no stepping through body
CustomisationDeep (layer/GPU access)Limited for complex custom rendering

Mental model shift: UIKit = "go here and change that"; SwiftUI = "this is what the screen looks like when state is X".

12. What were the difficulties in transitioning from UIKit to SwiftUI?

  • Mental model inversion: stopped thinking in mutations, started thinking in state. Hardest part — instinct to "update the label" must become "update the model".
  • Debugging: no stepping through body with breakpoints; _printChanges() and Instruments help but experience gap vs UIKit is real.
  • State ownership: choosing between @State, @StateObject, @ObservedObject, @EnvironmentObject — wrong choice causes either re-render storms or stale data.
  • Lifecycle mismatch: .onAppear fires differently from viewDidAppear — especially inside NavigationStack (fires on push AND pop in some scenarios).
  • API immaturity: NavigationView deprecated in iOS 16, replaced by NavigationStack; many patterns changed across OS versions, requiring conditional availability guards.
  • Custom transitions: UIKit UIViewControllerAnimatedTransitioning has no SwiftUI equivalent for complex custom transitions — still need UIViewRepresentable wrapping.
  • Testing: UIKit has XCUITest + snapshot testing; SwiftUI testing tooling (ViewInspector etc.) is third-party and less stable.

14. What is the Responder Chain and how does it work? How does UIKit differ from SwiftUI in handling events? Can one tap propagate through a stack of views?

Responder Chain (UIKit): a linked chain of UIResponder subclasses. Unhandled events travel up: UIView → UIViewController → UIWindow → UIApplication → AppDelegate. First responder gets first opportunity; each can handle or pass up via next.

Hit testing: hitTest(_:with:) traverses the view hierarchy depth-first to find the deepest view where pointInside(_:with:) returns true. That view becomes first responder for the touch. Override hitTest returning nil to make a view invisible to touches (pass-through).

// UIKit: pass-through overlay — ignore self, but let subviews receive touches
override func hitTest(_ point: CGPoint, with event: UIEvent?) -> UIView? {
    let hit = super.hitTest(point, with: event)
    return hit == self ? nil : hit
}

// UIKit: handle same tap at multiple levels — call super or forward manually
override func touchesBegan(_ touches: Set<UITouch>, with event: UIEvent?) {
    super.touchesBegan(touches, with: event)  // pass up the chain
    doLocalWork()
}

SwiftUI: no explicit responder chain. Gestures are attached via modifiers (.onTapGesture, .gesture()). A gesture attached to a parent view is masked by child gestures unless composed with .simultaneously(with:) or .sequenced(before:). .allowsHitTesting(false) makes a view transparent to touches.

Can one tap propagate through a stack of SwiftUI views? Not automatically — the deepest matching gesture wins. There is no built-in SwiftUI equivalent of UIKit's responder chain pass-through for tap events. You must explicitly compose gestures to share a tap across layers.

15. How to implement token refresh in the network layer. What happens to in-flight requests on 401? What if refresh token is also expired?

Architecture: short-lived access token + long-lived refresh token. Network interceptor catches 401, refreshes silently, retries.

Flow:

  1. Request returns 401 → interceptor catches before caller sees it
  2. Pause / queue all concurrent requests
  3. Fire one POST /auth/refresh with stored refresh token
  4. Success → store new access token → replay queued requests with new token
  5. Failure (refresh expired/revoked) → clear all credentials → force user back to login

Race condition: multiple simultaneous 401s → only one refresh call should fire. Use an actor or flag + continuation queue:

actor TokenRefresher {
    private var isRefreshing = false
    private var waiters: [CheckedContinuation<String, Error>] = []

    func refreshIfNeeded() async throws -> String {
        if isRefreshing {
            return try await withCheckedThrowingContinuation {
                waiters.append($0)
            }
        }
        isRefreshing = true
        defer { isRefreshing = false }

        let newToken = try await AuthAPI.refresh(using: Keychain.refreshToken)
        Keychain.accessToken = newToken
        waiters.forEach { $0.resume(returning: newToken) }
        waiters.removeAll()
        return newToken
    }
}

Dead in-flight requests on 401: automatically retried with the fresh access token — never ask the user to retry manually.

Access token expired: refresh silently and transparently.

Refresh token expired: no technical workaround — by design. Must redirect user to login screen to re-enter credentials. Refresh token is the last secret; once gone, only the user can prove identity again.

16. What technique prevents a Man-in-the-Middle (MITM) attack in an iOS app?

Primary defence — Certificate Pinning: embed the server's certificate or public key hash in the app bundle. During TLS handshake, compare server's presented certificate against the pinned value. Reject any mismatch.

// URLSession-based pinning
extension NetworkClient: URLSessionDelegate {
    func urlSession(
        _ session: URLSession,
        didReceive challenge: URLAuthenticationChallenge,
        completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void
    ) {
        guard challenge.protectionSpace.authenticationMethod == NSURLAuthenticationMethodServerTrust,
              let serverTrust = challenge.protectionSpace.serverTrust,
              let certificate = SecTrustGetCertificateAtIndex(serverTrust, 0) else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }
        let serverData = SecCertificateCopyData(certificate) as Data
        if pinnedCertificates.contains(serverData) {
            completionHandler(.useCredential, URLCredential(trust: serverTrust))
        } else {
            completionHandler(.cancelAuthenticationChallenge, nil)
        }
    }
}

Key pinning vs cert pinning: pin to the public key, not the leaf certificate — survives cert renewal without an app update, as long as the key pair stays the same. Always ship at least two pinned keys (primary + backup) for rotation safety.

Additional layers:

  • ATS (NSAppTransportSecurity) enforces HTTPS by default — never disable without justification
  • HSTS (server-side) — instructs clients to always use HTTPS; enforced by browser/system
  • Certificate Transparency — server provides signed proof cert is in public log; Safari/iOS validates automatically
  • Never allow self-signed certificates in production

Pinning risk: if server rotates the cert/key without a shipped app update → all users blocked. Mitigate with key pinning + backup key + coordinated rollout (publish new app before rotating key).
