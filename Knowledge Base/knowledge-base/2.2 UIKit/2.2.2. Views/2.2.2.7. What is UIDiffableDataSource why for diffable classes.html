2.2.2.7. What is UIDiffableDataSource ? why for diffable classes?

  • UITableViewDiffableDataSource / UICollectionViewDiffableDataSource (iOS 13+) manage a table/collection view's content from a declarative snapshot of sections and items, instead of manual index-path bookkeeping. You build an NSDiffableDataSourceSnapshot<SectionID, ItemID> and call apply(_:); the data source diffs it against the previous snapshot and animates the delta itself.
  • SectionID/ItemID must be Hashable — the diff keys on identity (hash/==), not array position or content. You still supply a cell-provider closure, but never implement numberOfRowsInSection/cellForRowAt yourself.
  • Replaces implementing UITableViewDataSource/UICollectionViewDataSource plus manual performBatchUpdates(_:) insert/delete/move index-path math.

Why diffable exists

  • Crash safety: performBatchUpdates crashes if the counts you report don't exactly match the inserts/deletes you declared. Diffable derives counts straight from the applied snapshot, so they can never disagree.
  • No manual diffing: inserts, deletes, moves, and reorders are detected and animated automatically — no hand-written index-path arithmetic.
  • Background-safe: apply(_:animatingDifferences:) can be called off the main thread; calls are queued and applied serially.

Reload vs. reconfigure

  • reloadItems(_:) destroys and re-creates the cell via the cell provider — use when identity is unchanged but the cell must be fully rebuilt (rare).
  • reconfigureItemsWithIdentifiers(_:) (iOS 15+) updates the existing cell in place — the cheap, correct choice for "same identity, changed content" (e.g. a like-count bump).
  • Neither called? A snapshot that only changes an item's data while ItemID stays == is a visual no-op — the diff reacts to identity, not content.

enum Section { case main }

struct Item: Hashable {
    let id: UUID
    let title: String
}

final class ListViewController: UIViewController {
    private var tableView: UITableView!
    private lazy var dataSource = makeDataSource()

    private func makeDataSource() -> UITableViewDiffableDataSource<Section, Item> {
        UITableViewDiffableDataSource(tableView: tableView) { tableView, indexPath, item in
            let cell = tableView.dequeueReusableCell(withIdentifier: "Cell", for: indexPath)
            cell.textLabel?.text = item.title
            return cell
        }
    }

    func apply(items: [Item], animating: Bool = true) {
        var snapshot = NSDiffableDataSourceSnapshot<Section, Item>()
        snapshot.appendSections([.main])
        snapshot.appendItems(items, toSection: .main)
        dataSource.apply(snapshot, animatingDifferences: animating) // diffs & animates automatically
    }
}

Gotchas

  • Item identity must be unique across the whole snapshot, even across sections — duplicate Hashable values trigger a runtime crash/assertion.
  • The diff compares identity, not content — mutating a struct's non-identity fields without reconfigureItemsWithIdentifiers/reloadItems silently leaves stale cell content on screen. 
    struct Item: Hashable {
    let id: UUID       // identity
    var title: String  // content — not part of hash/equality

    static func == (l: Item, r: Item) -> Bool { l.id == r.id }
    func hash(into hasher: inout Hasher) { hasher.combine(id) }
}

var item = items[0]
item.title = "Updated"   // same id -> diff sees no change
snapshot.reconfigureItems([item.id])       // forces the cell to redraw with the new title
dataSource.apply(snapshot)
  • Pass animatingDifferences: false for the very first snapshot (e.g. initial load into an empty table) to avoid an unwanted animation.

Common Interview Questions

Q: Why does Apple recommend diffable data sources over manual performBatchUpdates? A: They eliminate the classic crash where declared inserts/deletes don't match the reported counts — the diff (and therefore the counts) is always derived directly from the applied snapshot, so the two can never disagree.

Q: What must SectionID and ItemID conform to, and why? A: Hashable — the diffing algorithm identifies items by identity/equality, not array index, so it can tell inserts/deletes/moves apart from in-place updates.

Q: If I change a property on an item but keep the same identity, will the cell update? A: Not automatically — the diff sees no identity change and produces no update. Call reconfigureItemsWithIdentifiers(_:) (cheap, in-place) or reloadItems(_:) (destroys/recreates the cell) on the snapshot before applying it.

Q: Is it safe to build and apply a snapshot from a background thread? A: Yes — apply(_:animatingDifferences:) is documented as safe to call off the main thread; successive calls are serialized internally, though the actual UI update still happens on the main thread.

func applyInBackground(items: [Item]) {
    DispatchQueue.global().async {
        var snapshot = NSDiffableDataSourceSnapshot<Section, Item>()
        snapshot.appendSections([.main])
        snapshot.appendItems(items, toSection: .main)

        // Called off-main; UIKit updates the UI and calls completion on main.
        dataSource.apply(snapshot, animatingDifferences: true) {
            // Safe to update UIKit here.
        }
    }
}
