2.2.2.1. UIView lifecycle

  • UIView has no single official "lifecycle", unlike UIViewController. Instead, three separate systems drive its behavior: hierarchy attachment (superview/window), the layout pass, and the display/draw pass. This page covers when each one fires and how the run loop batches them together.

1. Creation

  • init(frame:) — used when you create the view in code. frame/bounds are set, but the view has no superview yet. Don't size subviews here — do that in layoutSubviews() instead.
  • init?(coder:) — used when the view comes from a nib/storyboard. You must implement it, or the app crashes when Interface Builder tries to load the view.
  • awakeFromNib() — called once, after every object in the nib is loaded and all outlets are connected. This is the safe place for one-time setup, because outlets are never nil here (unlike inside init?(coder:)).

2. Hierarchy flow

Adding a view to an already-visible hierarchy (e.g. addSubview(_:)) calls these methods in order:

  1. willMove(toSuperview:) — about to get a new superview.
  2. willMove(toWindow:) — about to get a window.
  3. The superview and window are actually set.
  4. didMoveToWindow().
  5. didMoveToSuperview().

Removing a view (removeFromSuperview()) fires the same five callbacks, in the same order — but each one now gets nil instead of a superview/window.

  • window != nil is the closest thing UIView has to "on screen" — but it's not exact. A view can have a window while scrolled off-screen, hidden, or fully transparent (alpha == 0).

3. Layout pass

  • setNeedsLayout() marks the view as needing layout and returns right away. The run loop batches every pending request into one layoutSubviews() call before the next frame.
  • layoutIfNeeded() forces that pass to run right now, synchronously — needed before reading a view's final frame (e.g. for a custom transition), but avoid calling it often (e.g. inside scrollViewDidScroll) since it's expensive.
  • layoutSubviews() runs on every ancestor layout pass, not just once — never do heavy or one-off work here (allocations, network calls); only position/size subviews.
  • With Auto Layout, constraints are resolved right before layoutSubviews() runs; frame is only guaranteed correct after that pass — never in init or right after addSubview(_:).

Practical example: setNeedsLayout() vs layoutIfNeeded()

Use setNeedsLayout() when a property change should reposition subviews on the next layout pass. It's cheap because UIKit batches it with any other pending layout work — good for something like a custom badge view whose content just changed:

final class BadgeView: UIView {
    var count: Int = 0 {
        didSet {
            // content changed - ask UIKit to re-layout on the next pass
            setNeedsLayout()
        }
    }

    override func layoutSubviews() {
        super.layoutSubviews()
        // runs once, batched with any other pending layout work
        countLabel.frame = frame(for: count)
    }
}

Use layoutIfNeeded() when the new layout must apply right now, synchronously — the classic case is animating an Auto Layout constraint change. Update the constraint, then call layoutIfNeeded() inside the animation block so the animator can interpolate from the view's current frame to its new one:

func setExpanded(_ expanded: Bool) {
    heightConstraint.constant = expanded ? 200 : 44

    // force the new constraint to take effect immediately,
    // so the animation block can interpolate from a known frame
    UIView.animate(withDuration: 0.3) {
        self.layoutIfNeeded()
    }
}

Without the layoutIfNeeded() call, the animator would only see the constraint's new value — not an actual frame change — and the height would jump instantly instead of animating.

4. Display / draw pass

  • setNeedsDisplay() marks the view's layer as needing a redraw. Core Animation calls draw(_:) later, before the next frame commits — batched the same way as layout.
  • Overriding draw(_:) at all forces the layer to allocate its own backing store, which turns off the fast, GPU-composited path — only override it for genuine custom Core Graphics drawing; use layers/images otherwise.
  • draw(_:) always runs on the main thread and must be fast — it blocks the next frame's commit.

5. Teardown

  • removeFromSuperview() triggers willMove(toSuperview: nil)/willMove(toWindow: nil), then the matching didMoveTo… calls with nil. deinit runs once the last strong reference to the view is gone.
  • A retain cycle happens when something the view strongly holds (or that strongly holds the view) keeps a reference back to it — neither side's reference count ever drops to zero, so deinit never runs, even after removeFromSuperview(). The view still stops updating (it has no window, so layout/draw callbacks stop firing), but it — and its whole subview tree — stays in memory. This is the most common cause of "invisible" leaks in iOS apps.

It typically happens with:

  • A repeating Timer whose closure captures self strongly. The run loop keeps the timer alive, and the timer's closure keeps the view alive — a cycle that survives removeFromSuperview() unless you call invalidate().
  • A CADisplayLink, which — like Timer — retains its target until you explicitly call invalidate().
  • A closure-based callback (a network completion handler, a NotificationCenter block observer, a child view's action closure) that captures self strongly and is stored on an object the view can also reach — e.g. a property the view itself holds.
  • A delegate property declared without weak, so a child view retains its parent while the parent also retains the child.
final class PulsingView: UIView {
    private var timer: Timer?

    override func didMoveToWindow() {
        super.didMoveToWindow()
        guard window != nil else {
            timer?.invalidate() // break the cycle once the view leaves the hierarchy
            timer = nil
            return
        }
        // [weak self] avoids the timer keeping this view alive forever
        timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
            self?.pulse()
        }
    }
}

final class AvatarView: UIView {
    private let imageView = UIImageView()

    override init(frame: CGRect) {
        super.init(frame: frame)
        addSubview(imageView) // one-time hierarchy setup only
    }

    required init?(coder: NSCoder) {
        super.init(coder: coder)
        addSubview(imageView)
    }

    override func awakeFromNib() {
        super.awakeFromNib()
        // outlets from the nib are safe to use here
    }

    override func willMove(toWindow newWindow: UIWindow?) {
        super.willMove(toWindow: newWindow)
        // start/stop expensive work based on visibility
        newWindow == nil ? pauseAnimating() : resumeAnimating()
    }

    override func layoutSubviews() {
        super.layoutSubviews()
        // called repeatedly - keep this cheap and idempotent
        imageView.frame = bounds
    }

    override func draw(_ rect: CGRect) {
        // only override for real Core Graphics drawing
        super.draw(rect)
    }

    deinit {
        // final cleanup - invalidate timers/observers here
    }
}

Gotchas

  • frame read in init/right after addSubview(_:) is unreliable with Auto Layout — wait for layoutSubviews() or call layoutIfNeeded() first.
  • Calling layoutIfNeeded() inside a scroll/drag callback (e.g. scrollViewDidScroll) can hurt frame rate — it forces a full, synchronous layout pass on every call.
  • Overriding draw(_:) "just in case" quietly turns off layer compositing optimizations for that view — a common, hard-to-spot perf regression.
  • isHidden = true and alpha = 0 do not trigger willMove(toWindow:)/didMoveToWindow() — the view is still attached, just not drawn.

Common Interview Questions

Q: Why doesn't UIView have a viewDidAppear-style callback? A: "Visibility" is a presentation concept owned by UIViewController/UIWindow. A view only knows whether it's attached to a superview/window — that's not the same as being "actually on screen" (it could still be off-screen, hidden, or covered).

Q: What's the difference between setNeedsLayout() and layoutIfNeeded()? A: setNeedsLayout() schedules a layout pass for the next run-loop tick, batching multiple requests into one. layoutIfNeeded() forces that pass to run right now, synchronously, walking up to the nearest ancestor that needs layout.

Q: Is overriding layoutSubviews() good or bad practice? A: Neither by default — it's the standard, UIKit-sanctioned way to manually position subviews when Auto Layout alone isn't enough (custom controls, non-rectangular layouts, performance-critical cases). It turns bad when you forget to call super.layoutSubviews(), do heavy or non-idempotent work there (allocations, network calls), or trigger another layout pass from inside it:

override func layoutSubviews() {
    super.layoutSubviews()
    // BAD: marks the view dirty again, so UIKit schedules
    // another layoutSubviews() call right after this one - risk of a loop
    setNeedsLayout()
}

Keep layoutSubviews() cheap and idempotent — same inputs should always produce the same frame, with no side effects and no calls that request another layout pass.

Q: On which thread does UIView.animate run, and when do we need it? A: The call itself — and the block you pass to it — must run on the main thread, since it reads and writes UIKit/layer properties, which aren't thread-safe. What happens next isn't a Swift loop, though: UIKit captures the start and end values, then hands the actual per-frame interpolation to Core Animation, which drives it off the main thread (via the render server) using CABasicAnimations under the hood. That's why long animations don't block your UI — the main thread is free again as soon as the block finishes running.

We need it whenever a property change should appear smooth instead of an instant jump: showing/hiding a view (alpha), moving or resizing it (frame/transform), or applying an Auto Layout change (update the constraint, then call layoutIfNeeded() inside the block, as in the example above):

UIView.animate(withDuration: 0.3) {
    // runs on the main thread; Core Animation interpolates the rest
    view.alpha = 0
    view.transform = CGAffineTransform(scaleX: 0.8, y: 0.8)
}

Q: Which fires first when adding a view to a visible hierarchy — willMove(toSuperview:) or willMove(toWindow:)? A: willMove(toSuperview:) fires first, then willMove(toWindow:). Once both are actually set, the "did" callbacks fire in reverse order — window first, then superview.

Q: Why must both init(frame:) and required init?(coder:) be implemented in a UIView subclass? A: They're the two designated initializers UIKit can call, depending on whether the view is created in code or from a nib/storyboard. Skipping init?(coder:) still compiles, but the app crashes at runtime as soon as Interface Builder tries to load the view.

Q: If a view is removed from its superview but a timer closure still captures it, does deinit run? A: No — the closure's strong capture keeps the view alive indefinitely. This is a classic invisible leak: the view shows no visible symptoms once it's off-screen, just growing memory use.
