2.2.2.5. Rules for table/collection views; unexpected behaviors

UITableView/UICollectionView reuse cells for performance, which is also where most bugs come from. This page covers the rules that keep reuse safe, a complete setup with the data source and delegate, and the specific crashes/glitches that show up when those rules are broken.

Core rules you must follow:

  1. Register before you dequeue. register(_:forCellReuseIdentifier:) / register(_:forCellWithReuseIdentifier:) (class or nib) must run before dequeueReusableCell. Without it, dequeueReusableCell(withIdentifier:for:) crashes; the non-for: variant just returns nil.
  2. Fully configure every reused cell, every time. Cells come from a reuse pool, so any property you don't overwrite carries over from whatever row previously used that cell (stale image, checkmark, label text, background color).
  3. Reset transient/async state in prepareForReuse(). Cancel in-flight image loads, reset accessoryType, isSelected, custom subviews' visibility — anything not driven unconditionally by cellForRowAt.
  4. Data source counts must match reality before and after every update. numberOfRowsInSection must reflect the model before reloadData(), and the delta passed to performBatchUpdates must exactly match the change made to the backing array — mismatches throw NSInternalInconsistencyException: Invalid number of rows in section.
  5. All UI mutations happen on the main thread. Mutating the model and calling reloadData/insertRows off the main thread causes crashes or the classic purple runtime warning.
  6. performBatchUpdates index-path semantics: deletes/moves reference the pre-update index paths, inserts/moves-to reference the post-update index paths. Mutate the backing array first, then describe a matching delta in one batch call — don't interleave manual reloadData with pending batch animations.

Full example — UITableView setup with data source & delegate:

A minimal, complete setup: register a cell, implement UITableViewDataSource to supply rows, and UITableViewDelegate to react to selection. Comments call out where each core rule above applies.

final class FruitsViewController: UIViewController {

    private let tableView = UITableView(frame: .zero, style: .plain)
    private var fruits = ["Apple", "Banana", "Cherry", "Date", "Fig"]
    private let cellID = "FruitCell"

    override func viewDidLoad() {
        super.viewDidLoad()
        tableView.frame = view.bounds
        tableView.dataSource = self   // wire up the data source
        tableView.delegate = self     // wire up the delegate
        tableView.rowHeight = .automaticDimension
        tableView.estimatedRowHeight = 44
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: cellID) // rule 1: register before dequeue
        view.addSubview(tableView)
    }
}

// MARK: - UITableViewDataSource — what to show
extension FruitsViewController: UITableViewDataSource {

    func tableView(_ tableView: UITableView, numberOfRowsInSection section: Int) -> Int {
        fruits.count // rule 4: must match the array before reloadData/insertRows runs
    }

    func tableView(_ tableView: UITableView, cellForRowAt indexPath: IndexPath) -> UITableViewCell {
        let cell = tableView.dequeueReusableCell(withIdentifier: cellID, for: indexPath)
        var content = cell.defaultContentConfiguration()
        content.text = fruits[indexPath.row]          // rule 2: fully configure — no stale leftovers
        cell.contentConfiguration = content
        cell.accessoryType = .disclosureIndicator
        return cell
    }

    func tableView(_ tableView: UITableView, commit editingStyle: UITableViewCell.EditingStyle, forRowAt indexPath: IndexPath) {
        guard editingStyle == .delete else { return }
        tableView.performBatchUpdates {
            fruits.remove(at: indexPath.row)                        // rule 6: mutate the model first...
            tableView.deleteRows(at: [indexPath], with: .automatic) // ...then describe the same delta
        }
    }
}

// MARK: - UITableViewDelegate — how it behaves
extension FruitsViewController: UITableViewDelegate {

    func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
        tableView.deselectRow(at: indexPath, animated: true)
        let name = fruits[indexPath.row]
        print("Selected: " + name)
    }

    func tableView(_ tableView: UITableView, heightForRowAt indexPath: IndexPath) -> CGFloat {
        UITableView.automaticDimension // paired with estimatedRowHeight above to avoid layout flicker
    }
}

What this wires up, end to end: register runs once in viewDidLoad so dequeueReusableCell never crashes; numberOfRowsInSection/cellForRowAt supply data and fully overwrite every reused cell; commit editingStyle: shows the mutate-then-animate pattern for safe deletes; and the delegate methods handle selection and self-sizing height without touching the model.

Cell reuse — reset & async race example: a cell can be recycled for a new row while its old async image request is still in flight; if that request completes after reuse, it can paint the wrong image onto the now-repurposed cell. The currentToken check guards against this by only applying the result if the cell is still showing the row that requested it.

final class ImageCell: UITableViewCell {
    private var currentToken: UUID?

    override func prepareForReuse() {
        super.prepareForReuse()
        currentToken = nil          // invalidate any in-flight request
        imageView?.image = nil      // don't show the previous row's image while loading
        accessoryType = .none
    }

    func configure(url: URL) {
        let token = UUID()
        currentToken = token
        ImageLoader.shared.load(url) { [weak self] image in
            guard let self, self.currentToken == token else { return } // cell was reused meanwhile
            self.imageView?.image = image
        }
    }
}

Batch update crash vs. fix:

// ❌ Crashes: array mutated, but batch update not called with matching delta
items.remove(at: 2)
tableView.reloadData() // works, but loses row animation — fine if that's acceptable

// ❌ Crashes: says "delete row 2" but array wasn't changed yet
tableView.performBatchUpdates {
    tableView.deleteRows(at: [IndexPath(row: 2, section: 0)], with: .automatic)
} // -> NSInternalInconsistencyException, counts don't match

// ✅ Correct: mutate first, then describe the exact same delta
tableView.performBatchUpdates {
    items.remove(at: 2)
    tableView.deleteRows(at: [IndexPath(row: 2, section: 0)], with: .automatic)
}

Comparison — ways to update table/collection views:

Approach Behavior Risk
reloadData() Full rebuild, no animation Safe but loses animations, can feel jarring, no diffing needed
performBatchUpdates + insert/delete/moveRows Animated, precise Manual index-path math — mismatched counts crash
UITableViewDiffableDataSource / UICollectionViewDiffableDataSource + snapshots Animated diff computed for you from old vs. new snapshot Safest for concurrent/complex updates (see 2.2.2.7. 2.7); requires hashable, unique identifiers

Common Interview Questions

Q: Why does my app crash with "Invalid number of rows in section" after updating an array and calling reloadData? A: It usually isn't reloadData() itself (that always works because it doesn't diff) — the crash comes from a performBatchUpdates/insertRows/deleteRows call whose index-path delta doesn't match the actual change you made to the backing array (wrong count, wrong section, or the array wasn't mutated at all before the animated call).

Q: What causes self-sizing cells to render at the wrong height briefly, and how do you fix it? A: Missing/ambiguous constraints to the content view's edges, or omitting estimatedRowHeight/UITableView.automaticDimension, forces UIKit to guess a height on the first pass before Auto Layout resolves the real one. Fix: pin all edges unambiguously, set both rowHeight = .automaticDimension and a reasonable estimatedRowHeight, and avoid intrinsic-content-size-less views without explicit constraints.

Q: reloadData() vs. performBatchUpdates — when to use which? A: reloadData() rebuilds every visible cell with no animation — use it for whole-screen replacements (first load, filter/sort changing most rows). performBatchUpdates animates only the rows that actually changed — use it for incremental changes (one row inserted/deleted/moved), but the delta you describe must exactly match the mutation already made to the backing array, or it crashes. Prefer a diffable data source over hand-rolled performBatchUpdates when the update logic gets complex.

Q: How do you implement pagination correctly in a UITableView, and which methods update the UI? A: Detect "near the end of data" in willDisplay cell:forRowAt: (or UITableViewDataSourcePrefetching) to trigger the next page fetch before the user hits the bottom. Fetch off the main thread, then on the main thread append the new items to the model first and describe only that delta with insertRows(at:with:) inside performBatchUpdates — never call reloadData() for an appended page, since it rebuilds all cells, kills the insert animation, and can jump scroll position. Guard with isLoadingPage/hasMorePages flags to avoid duplicate concurrent fetches.

func tableView(_ tableView: UITableView, willDisplay cell: UITableViewCell, forRowAt indexPath: IndexPath) {
    let thresholdIndex = items.count - 5
    if indexPath.row >= thresholdIndex {
        loadNextPageIfNeeded()
    }
}

private func loadNextPageIfNeeded() {
    guard !isLoadingPage, hasMorePages else { return }
    isLoadingPage = true

    Task {
        let newItems = try await api.fetchItems(offset: items.count, limit: pageSize)
        await MainActor.run { self.applyPage(newItems) }
    }
}

// Mutate model first, then describe the matching delta — never reloadData() here.
private func applyPage(_ newItems: [Item]) {
    let startIndex = items.count
    items.append(contentsOf: newItems)
    let indexPaths = (startIndex..<items.count).map { IndexPath(row: $0, section: 0) }

    tableView.performBatchUpdates {
        tableView.insertRows(at: indexPaths, with: .automatic)
    }
    isLoadingPage = false
}

Q: If the user scrolls too quickly, what should happen to pending loads (images, prefetch, pagination requests)? A: Cancel work tied to cells/rows that are no longer relevant instead of letting it complete into the wrong place. Cancel per-cell async loads in prepareForReuse() (recycled) and didEndDisplaying cell:forRowAt: (scrolled off-screen); cancel queued prefetch work in cancelPrefetchingForRowsAt; and guard pagination with an isLoadingPage flag so rapid willDisplay calls don't fire duplicate page requests. The most common cancellation mechanism is keeping a handle to the in-flight work — a URLSessionTask/Task reference or a request token — and calling .cancel() on it (or comparing the token) when the cell is reused or removed.
