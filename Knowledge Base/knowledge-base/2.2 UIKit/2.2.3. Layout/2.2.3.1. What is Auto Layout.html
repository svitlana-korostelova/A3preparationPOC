2.2.3.1. What is Auto Layout

Auto Layout is a constraint-based layout system in UIKit that automatically calculates the size and position of views based on rules (constraints) you define, instead of fixed frames. You describe relationships between views — e.g. "center this button in its superview" or "pin this label 20pt from the leading edge" — and a constraint solver (built on the Cassowary algorithm) resolves those relationships into concrete frames, recalculating automatically whenever screen size, orientation, or content changes.

Basic Example

let button = UIButton()
button.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(button)

NSLayoutConstraint.activate([
    button.centerXAnchor.constraint(equalTo: view.centerXAnchor),
    button.centerYAnchor.constraint(equalTo: view.centerYAnchor),
    button.widthAnchor.constraint(equalToConstant: 100),
    button.heightAnchor.constraint(equalToConstant: 50)
])

// Modern approach with layout anchors:
// make the button fill the width, with padding on both sides
button.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 20).isActive = true
button.trailingAnchor.constraint(equalTo: view.trailingAnchor, constant: -20).isActive = true

Common Interview "Why" Questions

  • Q: Why set translatesAutoresizingMaskIntoConstraints = false?
    A: By default, UIKit auto-generates constraints from a view's frame/autoresizing mask. Setting this to false disables that auto-generated set so your own explicit constraints aren't fighting the automatic ones (which would otherwise cause an "unsatisfiable constraints" conflict at runtime).

  • Q: Why use Safe Area instead of the superview's edges?
    A: Safe Area anchors (safeAreaLayoutGuide) respect notches, the Dynamic Island, status bar, navigation/tab bars, and the home indicator, so content isn't clipped or hidden behind system UI.

  • Q: Why prefer Layout Anchors over raw NSLayoutConstraint?
    A: Anchors (leadingAnchor, widthAnchor, etc.) are type-safe — the compiler stops you from constraining, say, an X-axis anchor to a Y-axis anchor — and read closer to natural language than the older NSLayoutConstraint(item:attribute:relatedBy:toItem:attribute:multiplier:constant:) initializer or Visual Format Language.

  • Q: Why use Stack Views (UIStackView)?
    A: A stack view manages the spacing, alignment, and distribution of its arranged subviews for you, generating the constraints internally. It removes most of the boilerplate constraint code for common row/column layouts.

  • Q: What happens if constraints are ambiguous or conflicting?
    A: Ambiguous means the system doesn't have enough constraints to determine a unique frame (e.g. missing width/height); Auto Layout picks an arbitrary valid value and logs a warning. Conflicting means two or more required (priority 1000) constraints can't be satisfied simultaneously; the engine breaks the constraint it considers least important, logs an "Unable to simultaneously satisfy constraints" error, and you should fix it before shipping.

  • Q: What are constraint priorities for?
    A: Every constraint has a priority (1–1000). Required constraints use 1000; anything lower is optional and can be broken if it can't be satisfied. This lets you express "preferences" (e.g. a label's contentHuggingPriority/contentCompressionResistancePriority) so the engine knows which view should grow or shrink first when space is tight.

Auto Layout vs. SwiftUI Layout

A frequent interview trap: SwiftUI does not run on top of Auto Layout. It has an entirely different, purpose-built layout engine, even though both ultimately position UIView/CALayer instances on screen.

AspectAuto Layout (UIKit)SwiftUI
ParadigmImperative — you build a list of constraintsDeclarative — you describe the view tree; the framework derives layout
AlgorithmConstraint solver (Cassowary) resolving a system of linear equationsTwo-pass size negotiation: a parent proposes a size to each child, the child returns the size it wants, then the parent places it
Core APINSLayoutConstraint, layout anchors, Visual Format Language, UIStackViewVStack/HStack/ZStack, modifiers like .padding, .frame, .fixedSize
Ambiguity/conflictsPossible — under/over-constrained layouts log runtime warningsNot possible — every view always resolves to exactly one size deterministically
PrioritiesExplicit numeric priorities (1–1000) plus hugging/compression resistanceImplicit, driven by layout priority modifiers (.layoutPriority(_:)) and each view's intrinsic "flexibility"
DebuggingConsole constraint-conflict logs, Xcode's Auto Layout debugger/previewXcode previews, ._printChanges(), layout inspector overlays
InteropCan be embedded in SwiftUI via UIViewRepresentableCan be embedded in UIKit via UIHostingController (which internally still lays out its root view using SwiftUI's engine, then reports one final size back to Auto Layout as a single opaque box)

Q: If I put a SwiftUI view inside a UIKit screen, whose layout system wins?
A: Both are involved, but they don't mix constraints. UIHostingController's view participates in Auto Layout like any other UIView (you can pin its edges with constraints). Internally, everything inside that hosting view is laid out purely by SwiftUI's proposal/response system — Auto Layout only ever sees the hosting view's outer frame.
