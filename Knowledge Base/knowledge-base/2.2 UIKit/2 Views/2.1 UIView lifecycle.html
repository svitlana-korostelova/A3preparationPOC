2.1. UIView lifecycle

  • Unlike UIViewController, UIView has no single official "lifecycle" — behavior comes from three independent, overlapping systems: hierarchy attachment (superview/window), the layout pass, and the display/draw pass. Knowing when each fires — and how the run loop coalesces them — is the core of this topic.

1. Creation

  • init(frame:) — programmatic creation. frame/bounds are set, but the view isn't in a hierarchy yet; layout-dependent setup (subview sizing) doesn't belong here.
  • init?(coder:) — created from a nib/storyboard; must be implemented or the view crashes when Interface Builder instantiates it.
  • awakeFromNib() — called once, after all objects in the nib are unarchived and outlets connected; the right place for one-time nib-based setup (outlets are guaranteed non-nil here, unlike inside init?(coder:)).

2. Hierarchy attachment

  • willMove(toSuperview:) → superview added/removed → didMoveToSuperview().
  • willMove(toWindow:) → the view's window changes (attach, detach, or the superview is reparented into a different hierarchy) → didMoveToWindow().
  • Order when adding to an already-visible hierarchy: willMove(toSuperview:) → willMove(toWindow:) → superview/window actually set → didMoveToWindow() → didMoveToSuperview(). Removal fires the same callbacks with nil, in the same relative order.
  • window != nil is the closest thing UIView has to "on screen" — but it's an approximation (a view can have a window while scrolled off-screen, hidden, or alpha == 0).

3. Layout pass

  • setNeedsLayout() marks the view dirty and returns immediately; the run loop coalesces every pending request into a single layoutSubviews() call before the next frame commits.
  • layoutIfNeeded() forces that pass to happen synchronously right now — needed before reading a view's final frame (e.g. driving a custom transition) but expensive if called repeatedly (e.g. inside scrollViewDidScroll).
  • layoutSubviews() runs on every ancestor layout pass, not just once — never do heavy or non-idempotent work there (allocations, network calls); only position/size subviews.
  • With Auto Layout, constraints are resolved right before layoutSubviews() runs; frame is only guaranteed correct after that pass — never in init or immediately after addSubview(_:).

4. Display / draw pass

  • setNeedsDisplay() marks the backing layer's contents dirty; Core Animation calls draw(_:) asynchronously before the next commit — same coalescing idea as layout.
  • Overriding draw(_:) at all forces the layer to allocate its own backing store and opts the view out of the fast, implicitly GPU-composited path — only override it for genuine custom Core Graphics drawing; prefer layers/images otherwise.
  • draw(_:) always runs on the main thread and must be fast — it blocks the next frame's commit.

5. Teardown

  • removeFromSuperview() triggers willMove(toSuperview: nil)/willMove(toWindow: nil), then the corresponding didMoveTo… calls with nil, then deinit once the last strong reference is released.
  • A retain cycle (a closure, timer, or delegate capturing self strongly) keeps the view — and its whole subview subtree — alive after removal; deinit never fires, layout/draw callbacks silently stop, but memory leaks.
final class AvatarView: UIView {
    private let imageView = UIImageView()

    override init(frame: CGRect) {
        super.init(frame: frame)
        addSubview(imageView) // one-time hierarchy setup only
    }

    required init?(coder: NSCoder) {
        super.init(coder: coder)
        addSubview(imageView)
    }

    override func awakeFromNib() {
        super.awakeFromNib()
        // outlets from the nib are safe to use here
    }

    override func willMove(toWindow newWindow: UIWindow?) {
        super.willMove(toWindow: newWindow)
        // start/stop expensive work based on visibility
        newWindow == nil ? pauseAnimating() : resumeAnimating()
    }

    override func layoutSubviews() {
        super.layoutSubviews()
        // called repeatedly - keep this cheap and idempotent
        imageView.frame = bounds
    }

    override func draw(_ rect: CGRect) {
        // only override for real Core Graphics drawing
        super.draw(rect)
    }

    deinit {
        // final cleanup - invalidate timers/observers here
    }
}

Gotchas

  • frame read in init/right after addSubview(_:) is unreliable with Auto Layout — wait for layoutSubviews() or call layoutIfNeeded() first.
  • Calling layoutIfNeeded() inside a scroll/drag callback (e.g. scrollViewDidScroll) can tank frame rate — it forces a synchronous full layout pass every call.
  • Overriding draw(_:) "just in case" silently disables layer compositing optimizations for that view — a common, hard-to-spot perf regression.
  • isHidden = true and alpha = 0 do not trigger willMove(toWindow:)/didMoveToWindow() — the view is still attached, just not rendered.

Common Interview Questions

Q: Why doesn't UIView have a viewDidAppear-style callback? A: "Visibility" is a presentation concept owned by UIViewController/UIWindow; a view only knows about superview/window attachment, which isn't equivalent to "actually on screen" (it could be off-screen, hidden, or covered).

Q: What's the difference between setNeedsLayout() and layoutIfNeeded()? A: setNeedsLayout() schedules an async, coalesced pass on the next run-loop tick; layoutIfNeeded() forces that pass to run synchronously right now, walking up to the nearest dirty ancestor.

Q: Which fires first when adding a view to a visible hierarchy — willMove(toSuperview:) or willMove(toWindow:)? A: willMove(toSuperview:), then willMove(toWindow:); the "did" callbacks fire in reverse (window, then superview) once both are actually set.

Q: Why must both init(frame:) and required init?(coder:) be implemented in a UIView subclass? A: They're the two designated initializers UIKit can call depending on how the view is instantiated (code vs. nib/storyboard); omitting init?(coder:) compiles but crashes at runtime the moment Interface Builder tries to unarchive the view.

Q: If a view is removed from its superview but a timer closure still captures it, does deinit run? A: No — the closure's strong capture keeps the view alive indefinitely; this is a classic invisible leak since the view produces no visible symptoms once off-screen, only growing memory.
