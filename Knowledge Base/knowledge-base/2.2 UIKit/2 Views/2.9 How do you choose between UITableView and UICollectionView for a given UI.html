2.9. How do you choose between UITableView and UICollectionView for a given UI?

  • Default to UITableView for single-column, vertically scrolling lists of rows (settings screens, chat threads, simple feeds) — it's simpler to set up and comes with row-oriented behaviors (swipe actions, section index titles, plain/grouped/inset styles) for free.
  • Reach for UICollectionView whenever the layout isn't a single vertical column of full-width rows: grids, multi-column layouts, horizontal carousels, mixed/adaptive cell sizes, or anything that needs custom geometry (Pinterest/waterfall grids, cards, pager-style paging).
  • In modern codebases the two have converged a lot: both support UITableViewDiffableDataSource/UICollectionViewDiffableDataSource, self-sizing cells, prefetching, and cell registration APIs — UICollectionViewCompositionalLayout can even reproduce a plain list (.list(using:) configuration, iOS 14+), so today it's really a layout decision, not a data-source-capability decision.

Practical decision checklist

  • Is every cell full-width and stacked in one column? → UITableView (or a compositional list layout if you might need grid sections later).
  • Do you need a grid, multiple columns, or horizontal scrolling? → UICollectionView.
  • Do cells vary a lot in size/shape (photos, cards, masonry)? → UICollectionView with compositional or custom layout.
  • Do you need swipe-to-delete, index titles, or reorder controls with minimal code? → UITableView gives these for free; on UICollectionView you'd wire up UISwipeActionsConfiguration/drag-and-drop yourself.
  • Will the screen need mixed sections (a list section plus a grid section)? → UICollectionView with per-section layout (UICollectionViewCompositionalLayout(sectionProvider:)), since a table view can't mix column counts.
  • SwiftUI context? The same reasoning maps to List (table-like) vs LazyVGrid/LazyHGrid (collection-like).

Gotchas

  • Don't force a grid into UITableView by stacking horizontal stack views inside rows — it works for a couple of items but breaks down for dynamic counts, accessibility, and independent scrolling; that's exactly the case UICollectionView was built for.
  • Migrating an existing table view to a collection view "list" layout (UICollectionLayoutListConfiguration) is often less churn than it sounds — it keeps swipe actions, leading/trailing accessories, and separators while opening the door to per-section grid layouts later.
  • Both should use diffable data sources for anything with dynamic content — manual reloadData()/performBatchUpdates index math is a common source of crashes ("attempt to delete row X, but only Y rows exist") in both view types.

Common Interview Questions

Q: Is there anything a UITableView can do that a UICollectionView cannot? A: Not really since iOS 14 — UICollectionLayoutListConfiguration/.list(using:) gives collection views swipe actions, accessories, separators, and index titles, so a collection view can fully subsume a table view's behavior while also supporting non-list sections.

Q: You have a settings screen — which would you pick and why? A: UITableView (or a collection view list layout) — it's a single column of full-width rows, and the built-in grouped style, swipe actions, and simplicity outweigh the flexibility a collection view offers, which isn't needed here.

Q: How would you build a screen with a horizontal "featured" carousel followed by a vertical grid of items? A: One UICollectionView with UICollectionViewCompositionalLayout(sectionProvider:) — the carousel section uses horizontal scrolling behavior (.groupPaging or orthogonal scrolling) and the grid section uses a fractional-width group; a table view can't express per-section scroll direction or column counts.

Q: What's the performance difference between the two for large data sets? A: Negligible on their own — both reuse cells and support prefetching (UITableViewDataSourcePrefetching/UICollectionViewDataSourcePrefetching) and diffable data sources with the same batching semantics. Perceived performance differences usually come from cell complexity (Auto Layout cost, image decoding) rather than the container type.
