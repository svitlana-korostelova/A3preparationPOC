2.7. What is UIDiffableDataSource ? why for diffable classes?

  • UITableViewDiffableDataSource / UICollectionViewDiffableDataSource are generic data source objects (introduced iOS 13) that manage a table/collection view's content as a declarative state (a snapshot) instead of imperative index-path bookkeeping. You describe "what the data should look like now"; the data source diffs it against the previous state and animates the delta itself.
  • They replace implementing UITableViewDataSource/UICollectionViewDataSource and manually calling insertRows(at:)/deleteRows(at:)/performBatchUpdates(_:) with matching index-path math.

1. Core pieces

  • NSDiffableDataSourceSnapshot<SectionID, ItemID> — a value type listing sections and items in order. You build a new snapshot and apply(_:) it; nothing renders until you do.
  • Both SectionID and ItemID must conform to Hashable — identity (via hash/==), not array position, is what the diff algorithm keys on.
  • The data source itself conforms to UITableViewDataSource/UICollectionViewDataSource under the hood, so you still supply a cell-provider closure, but never implement numberOfRowsInSection/cellForRowAt yourself.

2. Why diffable exists (vs. manual batch updates)

  • Crash safety: performBatchUpdates crashes at runtime if the counts you report from the data source don't exactly match the inserts/deletes you declared — a very common, hard-to-debug bug. Diffable computes the delta itself, so counts and updates can never disagree.
  • No manual diffing: you never hand-write index-path arithmetic for inserts/moves/deletes; the data source runs a diffing algorithm (based on identity, similar in spirit to a Myers diff) and produces the correct animation automatically.
  • Correct animations for free: moves, reloads, and reorders are detected and animated distinctly, which is tedious and error-prone to hand-roll.
  • Thread model: apply(_:animatingDifferences:) can be called from a background queue safely (each call is enqueued and applied serially) — useful when snapshots are computed off the main thread from a network/DB update.

3. Reloading items vs. reconfiguring items

  • reloadItems(_:) on a snapshot forces the cell to be fully destroyed and re-created via the cell provider — needed when the item's identity is unchanged but you must force a rebuild (rare).
  • reconfigureItemsWithIdentifiers(_:) (iOS 15+) updates the existing cell in place without a destroy/recreate cycle — the right choice for "same identity, changed content" (e.g. a like-count bump), and much cheaper.
  • If neither is called, a snapshot that only changes an item's associated data (while the ItemID stays ==) is a no-op visually — the diff only reacts to identity, not content, unless told otherwise.
enum Section { case main }

struct Item: Hashable {
    let id: UUID
    let title: String
}

final class ListViewController: UIViewController {
    private var tableView: UITableView!
    private lazy var dataSource = makeDataSource()

    private func makeDataSource() -> UITableViewDiffableDataSource<Section, Item> {
        UITableViewDiffableDataSource(tableView: tableView) { tableView, indexPath, item in
            let cell = tableView.dequeueReusableCell(withIdentifier: "Cell", for: indexPath)
            cell.textLabel?.text = item.title
            return cell
        }
    }

    func apply(items: [Item], animating: Bool = true) {
        var snapshot = NSDiffableDataSourceSnapshot<Section, Item>()
        snapshot.appendSections([.main])
        snapshot.appendItems(items, toSection: .main)
        dataSource.apply(snapshot, animatingDifferences: animating) // diffs & animates automatically
    }
}

Gotchas

  • Item identity must be stable and unique across the whole snapshot (even across sections) — duplicate Hashable values in the same snapshot trigger a runtime crash/assertion.
  • Diffable compares by identity, not content — mutating a struct's non-identity fields without a new snapshot (or without reconfigureItemsWithIdentifiers/reloadItems) silently produces stale cell content.
  • animatingDifferences: true on the very first snapshot applied to an empty table still performs a (harmless but sometimes visible) animation; pass false for the initial load if that's undesired.
  • For self-sizing/complex layouts, rapid consecutive apply(_:) calls are coalesced/queued — don't assume each call renders before the next is applied.

Common Interview Questions

Q: Why does Apple recommend diffable data sources over manual performBatchUpdates? A: They eliminate the classic crash where declared inserts/deletes don't match the data source's reported counts, since the diff (and therefore the counts) is always derived directly from the snapshot you applied — there's no way for the two to disagree.

Q: What must SectionID and ItemID conform to, and why? A: Hashable (and Equatable) — the diffing algorithm identifies items by identity/equality, not by array index, so it can tell inserts/deletes/moves apart from in-place updates.

Q: If I change a property on an item but keep the same identity, will the cell update? A: Not automatically — the diff sees no identity change and produces no update. You must call reconfigureItemsWithIdentifiers(_:) (cheap, in-place) or reloadItems(_:) (destroys/recreates the cell) on the snapshot before applying it.

Q: Is it safe to build and apply a snapshot from a background thread? A: Yes — apply(_:animatingDifferences:) is documented as safe to call off the main thread; successive calls are serialized internally, though the actual UI update still happens on the main thread.

Q: What happens if a snapshot contains two items with the same Hashable value? A: It's a programmer error — applying such a snapshot triggers a runtime crash/assertion, since the data source can no longer uniquely map items to cells.
