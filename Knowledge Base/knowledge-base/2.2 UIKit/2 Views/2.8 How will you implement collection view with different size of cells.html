2.8. How will you implement collection view with different size of cells ?

  • Three practical approaches, in order of preference today: UICollectionViewCompositionalLayout (iOS 13+, declarative, supports mixed sizes/orientations/nested groups), UICollectionViewFlowLayout with self-sizing or a delegate callback (works everywhere, imperative), and a custom UICollectionViewLayout subclass (full control — Pinterest/waterfall-style grids, custom geometry).

1. Compositional layout (preferred, modern)

  • Build layout from NSCollectionLayoutSize → NSCollectionLayoutItem → NSCollectionLayoutGroup → NSCollectionLayoutSection. Sizes are expressed as .fractionalWidth/.fractionalHeight/.absolute/.estimated, so different cells in the same section can have different dimensions without any delegate math.
  • .estimated(_:) lets Auto Layout compute the final size per cell (self-sizing), which is the standard way to mix cells whose content (e.g. text length, image aspect ratio) drives height.
  • Can combine with UICollectionViewDiffableDataSource and per-section layouts (UICollectionViewCompositionalLayout(sectionProvider:)) for very different card sizes across sections in one view.
func makeLayout() -> UICollectionViewCompositionalLayout {
    let smallItem = NSCollectionLayoutItem(
        layoutSize: NSCollectionLayoutSize(widthDimension: .fractionalWidth(1.0),
                                              heightDimension: .fractionalHeight(1.0)))
    smallItem.contentInsets = NSDirectionalEdgeInsets(top: 4, leading: 4, bottom: 4, trailing: 4)

    // two stacked small items next to one large item
    let pairGroup = NSCollectionLayoutGroup.vertical(
        layoutSize: NSCollectionLayoutSize(widthDimension: .fractionalWidth(0.3),
                                              heightDimension: .fractionalHeight(1.0)),
        subitems: [smallItem, smallItem])

    let bigItem = NSCollectionLayoutItem(
        layoutSize: NSCollectionLayoutSize(widthDimension: .fractionalWidth(0.7),
                                              heightDimension: .fractionalHeight(1.0)))

    let rowGroup = NSCollectionLayoutGroup.horizontal(
        layoutSize: NSCollectionLayoutSize(widthDimension: .fractionalWidth(1.0),
                                              heightDimension: .absolute(200)),
        subitems: [bigItem, pairGroup])

    let section = NSCollectionLayoutSection(group: rowGroup)
    return UICollectionViewCompositionalLayout(section: section)
}

2. Flow layout (legacy but still valid)

  • Delegate-driven: implement collectionView(_:layout:sizeForItemAt:) in UICollectionViewDelegateFlowLayout and return a per-item CGSize computed from your model (e.g. text length, aspect ratio table).
  • Self-sizing alternative: set flowLayout.estimatedItemSize = .automatic (or a rough estimate) and let Auto Layout constraints inside the cell determine the final size — avoids a switch/lookup in the delegate but requires the cell's content view to be fully constrained top-to-bottom.
func collectionView(_ collectionView: UICollectionView, layout: UICollectionViewLayout,
                    sizeForItemAt indexPath: IndexPath) -> CGSize {
    let item = items[indexPath.item]
    let width = item.isFeatured ? collectionView.bounds.width : collectionView.bounds.width / 2
    return CGSize(width: width, height: item.isFeatured ? 240 : 140)
}

3. Custom UICollectionViewLayout (waterfall/Pinterest grids)

  • Override prepare() to compute and cache an [UICollectionViewLayoutAttributes] per index path (tracking a running height per column), override collectionViewContentSize, and layoutAttributesForElements(in:)/layoutAttributesForItem(at:) to return the cached frames.
  • Needed when item placement isn't expressible as rows/columns of fixed proportions — e.g. masonry layouts where the next item's column is chosen by "shortest column so far".

Gotchas

  • Self-sizing (estimated size) requires the cell's contentView to have a complete, unambiguous constraint chain from top to bottom — a missing constraint makes the estimate become the final size (cells look clipped or too tall).
  • Flow layout's sizeForItemAt is called frequently during scrolling/rotation; keep the size computation cheap (no layout passes or string measurement on every call — cache computed sizes on the model).
  • Compositional layout's .estimated sizing invalidates and re-measures after the cell is displayed, which can cause a visible "jump" on first appearance for content that differs a lot from the estimate — pick a realistic estimate to minimize it.
  • Custom layouts must invalidate correctly on bounds change (shouldInvalidateLayout(forBoundsChange:)) or rotation/size-class changes will leave stale frames.

Common Interview Questions

Q: How do you support cells of different sizes in the same section with compositional layout? A: Model the section as nested NSCollectionLayoutItem/NSCollectionLayoutGroup objects, giving each item its own fractional/absolute/estimated width and height — different items in the same group can have different dimensions without a delegate callback.

Q: What's the difference between .estimated and .absolute sizing? A: .absolute is a fixed point value; .estimated gives the layout engine a starting guess and then lets Auto Layout (via the cell's constraints) resolve the real size after the cell is created — needed for content-driven (self-sizing) cells.

Q: Why would you write a custom UICollectionViewLayout instead of using compositional layout? A: When placement can't be expressed as rows/columns with fixed proportions — e.g. a Pinterest-style waterfall where each item goes into whichever column currently has the least height — compositional layout's group model can't express that, so you compute attributes manually in prepare().

Q: What breaks if a self-sizing cell's constraints are incomplete? A: Auto Layout can't resolve an intrinsic content size, so the layout falls back to the estimated size as final — cells render clipped, overlapping, or with wrong spacing, and it can look fine at first glance until content varies.
