2.10. What are the advantages of using Auto Layout programmatically versus Interface Builder?

  • Code review / VCS: Storyboards/XIBs are large XML blobs — diffs are unreadable and merge conflicts are common and painful to resolve by hand. Swift constraint code diffs and merges like any other source file.
  • Reusability & DI: Programmatic views are easier to parameterize (generics, dependency injection, configuration structs) and reuse across screens without duplicating a XIB per variant.
  • Dynamic layout logic: When constraints depend on runtime state (feature flags, data-driven number of rows, conditional sections), branching in code is far cleaner than IB's static canvas + endless `IBOutlet` wiring.
  • Compiler/tooling safety: Typos in code are caught by the compiler; broken `IBOutlet`/`IBAction` connections in IB only fail at runtime (or silently disconnect).
  • No load overhead: No NIB/Storyboard deserialization cost; views are built directly.
  • IB's counterpoint (still valid): faster visual prototyping, live constraint preview, easier designer/dev collaboration, built-in localization (Base Internationalization). Many teams use a hybrid — IB for quick prototyping/simple screens, code for reusable components and complex/conditional UI.

Common Interview Questions

Q: Why do teams still keep a Storyboard for the app entry point or launch screen? A: Historical Xcode project templates wire `Main.storyboard` as the initial scene; launch screen can now be a plain `Info.plist`-driven storyboard, but many legacy projects still ship one XIB for it. It's convention, not a technical requirement of Auto Layout itself.

Q: What's the biggest practical downside of 100% programmatic UI? A: No live visual canvas — you must build & run (or use SwiftUI Previews / `@available` Xcode Previews for UIKit) to see the result, slowing down pure visual iteration.

Q: How do you review a Storyboard change in a PR? A: You mostly can't review the XML diff meaningfully; rely on screenshots, manual QA, or Xcode's storyboard diff view rather than line-by-line code review.
