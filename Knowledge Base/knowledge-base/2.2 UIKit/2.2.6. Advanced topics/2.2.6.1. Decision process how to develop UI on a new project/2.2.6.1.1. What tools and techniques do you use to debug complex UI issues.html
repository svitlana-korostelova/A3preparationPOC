2.2.6.1.1. What tools and techniques do you use to debug complex UI issues?

Work in this order: reproduce → isolate → inspect → fix → verify. Pick the tool by symptom.

SymptomTool
View is missing, wrong size, or clippedXcode View Debugger (Debug View Hierarchy)
"Unable to simultaneously satisfy constraints"Console log + symbolic breakpoint + constraint identifiers
Scrolling or animation lagsInstruments: Animation Hitches, Time Profiler; Simulator colour debug options
Tap goes to the wrong viewView Debugger + logging in hitTest(_:with:); print the responder chain
Screen never deallocatesMemory Graph Debugger, deinit log
UI update from background threadMain Thread Checker (on by default), purple runtime warnings
Breaks with big fonts, dark mode, other languagesXcode environment overrides, pseudo-languages, Accessibility Inspector

1. View Debugger

  • Shows the view hierarchy as 3D layers. Check frame, alpha, isHidden, clipsToBounds, and constraints in the inspector.
  • Turn on Show Clipped Content to see views cut off by a parent.
  • Turn on Show Constraints to see which constraints belong to a view.
  • Issue navigator lists ambiguous or missing layout.

2. Auto Layout problems

  • Set identifier on constraints. The console log then shows names, not addresses.
  • Add a symbolic breakpoint on UIViewAlertForUnsatisfiableConstraints to stop at the moment of conflict.
  • Ambiguous layout (not enough constraints) gives no log. Use view.hasAmbiguousLayout and view.constraintsAffectingLayout(for:).

3. LLDB: inspect and change the UI live

(lldb) expr -l objc -O -- [[[UIApplication sharedApplication] keyWindow] recursiveDescription]
(lldb) expr -l objc -O -- [[[UIApplication sharedApplication] keyWindow] _autolayoutTrace]
(lldb) po view.next                       // walk the responder chain
(lldb) e view.backgroundColor = .red      // change a value without a rebuild
(lldb) e CATransaction.flush()            // force the screen to redraw

recursiveDescription and _autolayoutTrace are private. Use them only while debugging, never in shipped code.

4. Quick visual helper

#if DEBUG
extension UIView {
    func debugBorders(_ color: UIColor = .systemRed) {
        layer.borderColor = color.cgColor
        layer.borderWidth = 1
        subviews.forEach { $0.debugBorders(color) }
    }
}
#endif

5. Performance

  • Simulator → Debug menu: Color Blended Layers (red = transparent views, GPU blends them), Color Off-screen Rendered (yellow), Color Misaligned Images.
  • Common off-screen causes: cornerRadius + masksToBounds, shadow without shadowPath, layer.mask, shouldRasterize misuse.
  • Instruments Animation Hitches shows which frames missed the deadline (16.6 ms at 60 Hz, 8.3 ms at 120 Hz). Time Profiler shows what the main thread did in that time.
  • Always profile on a real device, in Release build.

6. Environment checks

  • Xcode debug bar → Environment Overrides: Dynamic Type size, dark mode, Increase Contrast, and more, without leaving the app.
  • Scheme options: Double-Length Pseudo-language and Right-to-Left Pseudo-language test long text and RTL layout.
  • Test on the smallest and the largest device, in both orientations, with Split View on iPad.

Follow-up questions

  • A view is in the hierarchy but not visible. What do you check? isHidden and alpha; zero-size frame (missing constraints, or translatesAutoresizingMaskIntoConstraints still true); parent with clipsToBounds and the view is outside its bounds; another view covering it; wrong superview.
  • How do you find which constraint to break in a conflict? The system breaks one constraint to recover, and it is not always the wrong one. Read the whole list, compare priorities (.required is 1000), then lower the one that should be flexible, for example to .defaultHigh.
  • Why does the app hang only in Release? Release is optimized and Debug is slower, so timing differs. Always profile a Release build on a real device.
  • How do you find a leaking view controller? Add deinit { print("deinit \(Self.self)") }, pop the screen, and check the log. If it is missing, open the Memory Graph and follow the strong reference (often a closure or a delegate not marked weak).
