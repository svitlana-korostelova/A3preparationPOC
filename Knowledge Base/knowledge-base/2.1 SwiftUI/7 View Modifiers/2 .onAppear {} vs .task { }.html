2. .onAppear vs .task

.onAppear — Executes synchronous code when the view enters the screen.
.task — Launches a structured async task tied to the view's lifetime; automatically cancelled when the view disappears.

Comparison

Feature .onAppear .task
Async / await support ❌ Synchronous only ✅ Built-in async context
Automatic cancellation ❌ None — manual cleanup required ✅ Cancelled on view disappear
Available from iOS 13+ iOS 15+
Task management Must create Task { } manually Built-in structured task
Re-trigger on value change ❌ No ✅ Yes — via .task(id:)
Priority control N/A ✅ .task(priority: .background)
Task outlives view? Yes, if Task { } is not cancelled manually No — always cleaned up automatically
Typical use case Analytics logging, sync UI setup Network fetches, async data loading

Code Examples

// ✅ .onAppear — synchronous work only
.onAppear {
    logAnalytics()
}

// ⚠️  .onAppear + manual Task — works, but YOU must cancel it on disappear
.onAppear {
    loadTask = Task {
        await fetchUserData()
    }
}
.onDisappear {
    loadTask?.cancel()   // required — or the task outlives the view
}

// ✅ .task — async work, automatically cancelled when view disappears
.task {
    await fetchUserData()
}

// ✅ .task with lower priority (does not block UI)
.task(priority: .background) {
    await prefetchImages()
}

.task(id:) — Re-trigger on Value Change

Pass any Equatable value as id. Whenever the value changes, SwiftUI cancels the running task and starts a new one — replacing the old .onChange + Task { } pattern.

struct UserProfileView: View {
    let userID: String

    var body: some View {
        ProfileContent()
            // Re-fetches automatically every time userID changes
            .task(id: userID) {
                await loadProfile(for: userID)
            }
    }
}
💡 Pro tip: .task(id:) is the idiomatic replacement for .onChange(of:) { Task { await … } } whenever async work must re-run in response to a changing dependency.

When to Use Each

  • Use .onAppear for lightweight synchronous side-effects: analytics pings, UI state resets, starting a timer.
  • Use .task for any async work: network calls, database queries, async image loading.
  • Use .task(id:) when async work must re-run in response to a changing dependency.
  • Avoid spawning a raw Task { } inside .onAppear unless you explicitly manage its lifecycle — it will not be cancelled when the view disappears.

Interview Questions

Q: Why doesn't .onAppear support async directly?

It predates Swift's async/await model (Swift 5.5 / iOS 15). Its closure is synchronous by design. .task was added in SwiftUI 3 as the structured-concurrency-native alternative.

Q: Why is automatic cancellation important?

Without cancellation, a task may complete after the view has disappeared and attempt to update state — causing crashes or "publishing changes from background thread" warnings. It also wastes CPU and network resources on work whose result will never be displayed.

Q: What happens to a .task when the view re-appears?

SwiftUI starts a brand-new task. The previous task was cancelled on disappear, so re-appearing always triggers a fresh execution — no manual restart logic needed.

Q: Can you attach multiple .task modifiers to the same view?

Yes. Each .task runs as an independent structured task, and all of them are cancelled together when the view disappears.

Q: What is the default task priority of .task { }?

.userInitiated — appropriate for data the user is actively waiting for. Override with .task(priority: .background) for prefetching or non-urgent work.

Q: Can .onAppear and .task be used together on the same view?

Yes. A common pattern is .onAppear for synchronous setup (e.g., logging, resetting scroll position) and .task for async data loading — both in the same modifier chain.
