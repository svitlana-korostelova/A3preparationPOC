13.20. Singleton

notes:

Q11. fetch() calls LocalCache.shared.save. Can a test pass a mock cache? What is the smallest change?

Say this: Not as written. In Swift a test cannot replace LocalCache.shared. The smallest change is a protocol, an extension so LocalCache itself is not edited, and an init parameter that defaults to .shared.

protocol CacheSaving {
    func save(_ account: Account) async
}
extension LocalCache: CacheSaving {}

final class AccountsViewModel {
    private let cache: any CacheSaving
    init(cache: any CacheSaving = LocalCache.shared) {
        self.cache = cache
    }
    func fetch() async {
        let account = /* ... */
        await cache.save(account)
    }
}

Call sites that already use AccountsViewModel() keep compiling. The test passes CacheSpy(). LocalCache's source does not change, because the conformance lives in the extension.

If you stall: "Can the test replace .shared?" No. Then: "Can LocalCache conform to a new protocol without changing its code?" Yes, in an extension.

Q12. Which SOLID principles does a singleton usually break?

Say this: The clear one is DIP. SRP is the second. The practical smell is a hidden dependency. LSP and OCP are arguable, and I say why instead of listing all five.

  • DIP. Callers depend on the concrete global LocalCache.shared. They cannot be given another implementation. That is the dependency-inversion break, and it is why Q11 cannot be tested.
  • SRP. The type does its job and it owns its own lifetime ("create me once, on first access"). Over time every new cache rule gets added to the same type, because there is only one place to put it.
  • Hidden dependency. fetch()'s signature does not show that it writes to disk. A reader has to open the body. That is not a SOLID letter, and it is the reason the other two hurt.
  • LSP, only if they ask. Callers name LocalCache, so a subtype cannot stand in for it. The principle is about subtypes of a named type. The global access point is what blocks substitution.
  • OCP, only if they ask. You can add methods. You cannot change which object callers use without editing the callers. That is closed in the wrong direction.

A singleton is still a fair choice for a process-wide resource with no interesting substitute, such as a logger you never mock. The problem is using it for a cache, a session, or an API client that tests and previews must replace.
