Q2. Why do we need actors? Can you still get a race condition?

Say this: Actors remove data races on their own state. They do not remove logic races. The usual hole is reentrancy at await.

An actor runs one piece of its isolated code at a time, so two tasks cannot write the same stored property at the same moment. That is the data-race guarantee.

At every await the actor lets the next waiter in. State you checked before the await may be different when you resume. The memory is still safe. The decision you made from the old state may be wrong. That is a race condition, and actors do not stop it.

actor AccountStore {
    private var balance = 100

    func withdraw(_ amount: Int) async throws {
        guard balance >= amount else { throw BankError.insufficient }
        await audit.log(amount)   // suspension: another withdraw can enter
        balance -= amount         // may overdraw
    }
}

Fix: do the check and the mutation together, before any await. If the later call can fail and you must roll back, re-read the state after the await and decide again. Do not trust a value you captured before the suspension.

func withdraw(_ amount: Int) async throws {
    guard balance >= amount else { throw BankError.insufficient }
    balance -= amount            // still inside the actor, no await yet
    await audit.log(amount)
}

Two extras if they keep going:

  • A data race can still exist around an actor: nonisolated(unsafe), a class reference that escapes the actor, or a global var touched from both inside and outside.
  • Two actors that await each other can deadlock. Actors do not detect that.

If you stall: "What happens to actor state across an await?" Then: "Have you heard of actor reentrancy?"

Q3. Where does this Task run, when does refresh() return, and what happens to the UI?

@MainActor
final class AccountsViewModel {
    func refresh() {
        Task {
            let data = heavySynchronousWork()
            apply(data)
        }
    }
}

a) Where does the body run? Task { } inherits the actor, the priority, and task-local values from the place it is created. refresh() is on the main actor, so the task body is main-actor isolated too. It is not a background task.

b) When does refresh() return? Immediately. Task { } only schedules the work and returns a handle. This code drops the handle. The caller of refresh() does not wait for heavySynchronousWork().

c) What happens to the UI? It freezes. heavySynchronousWork() has no await, so it runs straight through on the main thread. Task does not move synchronous work off the caller. Only an await suspends.

Fix, in the order I would offer:

  1. A nonisolated async function, awaited from the main-actor task. The heavy call leaves the main actor. apply runs after the await, back on the main actor.
  2. A separate actor, if the work also has state to protect.
  3. Task.detached only if you also mean to drop priority and task-locals. See Q4.
@MainActor
final class AccountsViewModel {
    func refresh() {
        Task {
            let data = await Self.heavyWork()
            apply(data)   // resumed on the main actor
        }
    }

    nonisolated static func heavyWork() async -> Data {
        heavySynchronousWork()
    }
}

Senior extra: in Swift 6.2 the upcoming mode NonisolatedNonsendingByDefault keeps a nonisolated async function on the caller's actor. In that mode the function above would still freeze the UI. Mark it @concurrent so it actually runs on the cooperative pool. A dedicated actor does not have this trap.

Also: if refresh() can be async and the caller is SwiftUI .task, delete the inner Task. An unstructured task is only needed to start async work from synchronous code, and it is not cancelled with the view. The same freeze is trap 5 in 4.6.2.

If you stall: "What does a Task inherit from where it's created?" Then: "Is the body isolated to any actor?"

Q4. When would you use Task.detached, and what do you lose?

Say this: Almost never as a first choice. Task.detached starts unstructured work that inherits nothing: not the actor, not the priority, not task-local values.

Use it when the work must not run on the caller's actor and you also do not want the caller's priority or task-locals (a trace id, a transaction id). For "just get this off the main actor", prefer the nonisolated / @concurrent function or a separate actor from Q3. Those keep priority and task-locals.

What you lose:

  • Actor isolation. You cannot touch main-actor state inside the detached body. Hop back to apply UI state.
  • Priority. A tap-priority caller can spawn a default-priority detached task, so the work may sit behind other jobs.
  • Task-local values.

Cancellation is the same trap as Task { }: neither is cancelled when the caller is cancelled, and dropping the handle does not cancel it. Keep the handle and call cancel(). The stored-handle sample is already in 4.6.2, Q4. Inheritance of actor, priority, and task-locals is the table in 4.6.1.

Q10. How do you test async code? What changes with Swift Testing?

Say this: In XCTest I wait on an expectation, or I make the test method async and await the work. Swift Testing drops the expectation type: the test is async, checks are #expect / #require, and repeated events use confirmation.

XCTest

  • Completion handler. Create an XCTestExpectation, fulfill() in the callback, then wait(for:timeout:). On a new SDK, await fulfillment(of:timeout:) from an async test.
  • async/await. Mark the test async throws and await the call. No expectation for a single result.
  • Publisher. Same expectation in sink, or await publisher.values.first inside an async test. Remember to keep the cancellable alive until fulfill.
func testRefresh() async throws {
    let vm = AccountsViewModel(service: FakeAccounts())
    await vm.refresh()
    XCTAssertEqual(vm.state, .loaded)
}

func testSaveCallback() {
    let exp = expectation(description: "saved")
    cache.save { exp.fulfill() }
    wait(for: [exp], timeout: 1)
}

Swift Testing

This is what new tests on the banking project use.

  • @Test instead of a method that starts with test.
  • #expect records a failure and continues. #require stops the test when the value must exist (it unwraps).
  • The test function can be async throws. No XCTestExpectation.
  • confirmation for "this event happened N times".
  • @Test(arguments:) runs the same body once per value.
import Testing

@Test func refreshLoads() async throws {
    let vm = AccountsViewModel(service: FakeAccounts())
    await vm.refresh()
    #expect(vm.state == .loaded)
}

@Test func emitsTwoUpdates() async {
    await confirmation(expectedCount: 2) { confirm in
        for await _ in store.updates.prefix(2) { confirm() }
    }
}

@Test(arguments: [200, 404, 500])
func mapsStatus(_ code: Int) {
    #expect(AccountError.map(code) != nil)
}

If you stall: "In XCTest, what do you wait on?" An expectation.
