4.6.2. Cancellation, unstructured tasks & senior-level traps

This is where senior interviews usually go deeper: cancellation details, bridging old APIs, and "what is wrong with this code?" questions.

Q1. How does cancellation work in Swift concurrency?

Short answer: Cancellation is cooperative. Calling cancel() only sets a flag. The task keeps running until its code checks the flag and stops.

Ways to check:

  • Task.isCancelled — returns a Bool; you decide what to do (e.g. return partial results).
  • try Task.checkCancellation() — throws CancellationError if cancelled.
  • Many system APIs check for you: Task.sleep and URLSession's async methods throw when the task is cancelled.
func process(_ items: [Item]) async throws -> [Result] {
    var output: [Result] = []
    for item in items {
        try Task.checkCancellation()   // stop between items
        output.append(heavyWork(item))  // sync CPU work never checks by itself
    }
    return output
}

Cancellation goes down the tree (parent → children), never up. Cancelling one child does not cancel its parent or siblings.

Q2. How do you cancel a legacy callback API when the task is cancelled?

Short answer: Use withTaskCancellationHandler. The onCancel closure runs immediately when the task is cancelled — even while the operation is suspended — so you can call the old API's cancel method.

func fetch(_ request: URLRequest) async throws -> Data {
    let box = TaskBox()   // Sendable, lock-protected holder of URLSessionDataTask?
    return try await withTaskCancellationHandler {
        try await withCheckedThrowingContinuation { continuation in
            let task = URLSession.shared.dataTask(with: request) { data, _, error in
                if let error { continuation.resume(throwing: error) }
                else { continuation.resume(returning: data ?? Data()) }
            }
            box.set(task)
            task.resume()
        }
    } onCancel: {
        box.cancel()   // may run on any thread, so TaskBox must be thread-safe
    }
}

Two things to mention: onCancel can run on any thread, at the same time as the operation; and if the task is already cancelled, onCancel runs right away, before the operation starts. So TaskBox should remember "cancel was requested" and cancel the data task as soon as it is set.

Q3. How do you wrap a completion-handler API with async? What are the rules?

Short answer: Use withCheckedContinuation / withCheckedThrowingContinuation. You must call resume exactly once on every path.

func currentLocation() async throws -> CLLocation {
    try await withCheckedThrowingContinuation { continuation in
        locationService.requestOnce { result in
            continuation.resume(with: result)   // exactly once
        }
    }
}
MistakeWhat happens
Resume twiceChecked continuation: crash with a clear message. Unsafe continuation: undefined behaviour.
Never resumeThe task hangs forever. Checked continuation logs "leaked its continuation" in the console.
Delegate API that fires many timesContinuation is the wrong tool — use AsyncStream instead.

Use withUnsafeContinuation only after measuring a real performance problem.

Q4. Task { } vs Task.detached { } — when is unstructured code OK?

Short answer: You need an unstructured task to start async work from synchronous code, such as a button action or viewDidLoad. Prefer Task { }. Task.detached is rarely the right choice.

  • Task { } keeps the current actor, priority and task-locals. In a @MainActor view model it runs on the main actor.
  • Task.detached { } keeps none of them. Use it only when you must not run on the current actor and can't make the work nonisolated instead.
  • Neither is cancelled automatically. Dropping the handle does not cancel the task. Store it and call cancel() yourself.
@MainActor
final class ProfileViewModel {
    var profile: Profile?
    private var loadTask: Task<Void, Never>?

    func onAppear() {
        loadTask?.cancel()
        loadTask = Task { [weak self] in
            let profile = try? await api.profile()
            self?.profile = profile
        }
    }

    func onDisappear() { loadTask?.cancel() }
}

Note: Task { } holds a strong reference to everything it captures (including self) until it finishes. A long or endless loop inside it keeps the view model alive.

Q5. How does SwiftUI's .task modifier relate to structured concurrency?

Short answer: .task ties a task to the view's lifetime. SwiftUI starts it when the view appears and cancels it when the view disappears. .task(id:) also cancels and restarts the task whenever id changes.

struct SearchView: View {
    @State private var query = ""
    @State private var results: [Item] = []

    var body: some View {
        List(results) { Text($0.title) }
            .searchable(text: $query)
            .task(id: query) {                       // old search is cancelled on each keystroke
                try? await Task.sleep(for: .milliseconds(300))  // debounce
                guard !Task.isCancelled else { return }
                results = (try? await api.search(query)) ?? []
            }
    }
}

This is the go-to answer for "implement search-as-you-type with debounce" in SwiftUI — no Combine needed.

Q6. How do you add a timeout to an async call?

Short answer: Race the work against Task.sleep in a throwing task group. Take whichever finishes first, then cancel the other.

struct TimeoutError: Error {}

func withTimeout<T: Sendable>(
    _ duration: Duration,
    operation: @escaping @Sendable () async throws -> T
) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask { try await operation() }
        group.addTask {
            try await Task.sleep(for: duration)
            throw TimeoutError()
        }
        defer { group.cancelAll() }          // stop the loser
        return try await group.next()!     // first result or first error wins
    }
}

Follow-up they may ask: the timeout only works if operation reacts to cancellation. The group still waits for the losing child before it returns.

Q7. "What is wrong with this code?" — common traps

Trap 1: Task { } inside a loop

func refreshAll() async {
    for id in ids {
        Task { await refresh(id) }   // ❌ unstructured: not awaited, not cancelled with parent
    }
    // returns immediately — refreshes are still running
}

Fix: use a task group so the function waits and cancellation flows down.

Trap 2: Blocking inside async code

func load() async -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result = Data()
    legacyFetch { result = $0; semaphore.signal() }
    semaphore.wait()      // ❌ blocks a thread of the small cooperative pool
    return result
}

The pool has about one thread per CPU core. Blocking them (semaphores, Thread.sleep, DispatchGroup.wait) can stall all async work or deadlock the app. Fix: use a continuation (Q3).

Trap 3: Unused async let is silently cancelled

func onLogin() async {
    async let _ = analytics.track("login")   // ❌ cancelled + awaited at scope exit
    await showHome()
}

The function also waits for it before returning. Fix: await it, or — if it should really outlive the function — make it an explicit Task { }.

Trap 4: Showing CancellationError to the user

do {
    items = try await api.load()
} catch is CancellationError {
    return                       // ✅ the user left — not a real error
} catch let error as URLError where error.code == .cancelled {
    return                       // ✅ URLSession reports cancel this way
} catch {
    showAlert(error)
}

Trap 5: Heavy work in Task { } on the main actor

@MainActor func exportTapped() {
    Task {
        let pdf = renderPDF(pages)   // ❌ sync CPU work — runs on main, UI freezes
        share(pdf)
    }
}

Task { } is not "background". Fix: move the work into a nonisolated async function (or another actor), then await it.

Trap 6: Mutating shared state from group children

var total = 0
await withTaskGroup(of: Void.self) { group in
    for file in files {
        group.addTask { total += await size(of: file) }   // ❌ data race — Swift 6 compile error
    }
}

Fix: make children return their value (of: Int.self) and sum them in the parent with for await.

Q8. Is a task tied to a thread? What happens at await?

Short answer: No. At every await the task may be suspended, and it may resume on a different thread. That's why you should not use thread-based tools (thread-locals, NSLock held across an await, Thread.current checks) in async code.

  • Holding a lock across await can deadlock: another task on the same thread may try to take the same lock.
  • After await, any state you read before may have changed — this is the root of actor re-entrancy bugs. Re-check your assumptions after each await.
  • Use actors or task-local values instead.
