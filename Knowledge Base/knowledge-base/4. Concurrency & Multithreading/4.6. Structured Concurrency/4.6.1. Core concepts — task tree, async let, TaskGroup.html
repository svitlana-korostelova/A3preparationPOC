4.6.1. Core concepts — task tree, async let, TaskGroup

The most common "explain it" questions. Each answer starts with a short version you can say out loud, then gives detail and code.

Q1. What is structured concurrency?

Short answer: Child tasks live inside the scope that created them. The scope cannot finish until every child has finished. So tasks form a tree, like nested function calls.

This gives three guarantees "for free":

  • No leaked work — when a function returns, none of its child tasks are still running.
  • Cancellation flows down — cancel the parent and every child is marked as cancelled.
  • Errors flow up — a child's error is rethrown in the parent, where you can handle it.

Swift has exactly two structured tools: async let and task groups (withTaskGroup, withThrowingTaskGroup, withDiscardingTaskGroup). Task { } and Task.detached { } are unstructured.

// Task tree
// loadScreen()               ← parent
//  ├─ async let profile      ← child
//  └─ withTaskGroup          ← child scope
//      ├─ thumbnail(id: 1)   ← grandchild
//      └─ thumbnail(id: 2)   ← grandchild

Q2. Why was it introduced? What was wrong with GCD and completion handlers?

Short answer: With GCD, nothing links a piece of work to the code that started it. You must track, cancel and wait for work by hand, and it's easy to forget.

Problem with GCD / callbacksHow structured concurrency fixes it
Forgot to call the completion handler, or called it twiceA function returns a value or throws — exactly once, checked by the compiler
Cancellation must be wired by hand (flags, DispatchWorkItem)Cancellation propagates through the task tree automatically
DispatchGroup enter/leave mismatch → hang or crashasync let / task group always wait for children
Errors passed as Result through nested closuresNormal try / catch
Thread explosion: blocked threads make GCD create more threadsCooperative pool with about one thread per CPU core; await frees the thread instead of blocking it

Q3. How does async let work?

Short answer: async let starts a child task right away and runs it in parallel with the rest of the function. You get the value later with await.

func loadScreen(userID: String) async throws -> Screen {
    async let user  = api.user(id: userID)      // starts now
    async let feed  = api.feed(for: userID)    // starts now, in parallel
    async let badge = api.unreadCount()        // starts now, in parallel

    // total time ≈ the slowest call, not the sum
    return try await Screen(user: user, feed: feed, badge: badge)
}

Compare with sequential code — each await waits for the previous one:

let user  = try await api.user(id: userID)    // 1 s
let feed  = try await api.feed(for: userID)  // + 1 s
let badge = try await api.unreadCount()      // + 1 s  → 3 s total

Key facts interviewers check:

  • If you leave the scope without awaiting an async let, Swift cancels it and waits for it anyway. It never outlives the function.
  • You can't pass an async let value around or store it — you can only await it in the same scope.
  • If one awaited async let throws, the function exits, and the other not-yet-awaited ones are cancelled and awaited.

Q4. How do task groups work?

Short answer: A task group runs a dynamic number of child tasks of the same result type. You add tasks with addTask and read results as they finish.

func loadThumbnails(ids: [Int]) async throws -> [Int: UIImage] {
    try await withThrowingTaskGroup(of: (Int, UIImage).self) { group in
        for id in ids {
            group.addTask {
                (id, try await api.thumbnail(id: id))
            }
        }

        var result: [Int: UIImage] = [:]
        for try await (id, image) in group {   // completion order, not add order
            result[id] = image
        }
        return result
    }
}
  • Results arrive in completion order. To keep the input order, return the index with the value (as above) and sort or map afterwards.
  • Collect results in the parent (the for await loop). Don't mutate a shared var from inside addTask — child closures are @Sendable, and Swift 6 rejects this as a data race.
  • When the closure ends, the group waits for any children you didn't read.

Q6. How do you limit how many tasks a group runs at once?

Short answer: Task groups have no built-in limit. Start the first N tasks, then add one new task each time one finishes.

func downloadAll(_ urls: [URL], maxConcurrent: Int = 4) async throws -> [Data] {
    try await withThrowingTaskGroup(of: Data.self) { group in
        var iterator = urls.makeIterator()
        var results: [Data] = []

        // 1. Fill the first N slots
        for _ in 0..<maxConcurrent {
            guard let url = iterator.next() else break
            group.addTask { try await download(url) }
        }

        // 2. Each time one finishes, start the next
        while let data = try await group.next() {
            results.append(data)
            if let url = iterator.next() {
                group.addTask { try await download(url) }
            }
        }
        return results
    }
}

Why it matters: 1 000 parallel image downloads can exhaust memory and overload the server, even though Swift's thread pool itself stays small.

Q7. What happens when one child task in a throwing group fails?

Short answer: The error is not raised immediately. It is stored until you read that child's result (next() or for try await). When the error is thrown out of the group closure, the group cancels all other children and waits for them before rethrowing.

try await withThrowingTaskGroup(of: Void.self) { group in
    group.addTask { try await upload(a) }
    group.addTask { throw UploadError.offline }   // fails fast
    group.addTask { try await upload(c) }

    try await group.waitForAll()   // rethrows .offline → siblings get cancelled
}
  • If you want "collect every result, even failures", return Result<T, Error> from each child and use a non-throwing group.
  • withThrowingDiscardingTaskGroup (iOS 17) is different: the first child error cancels the group right away, with no need to read results.

Q8. What is withDiscardingTaskGroup and when do you need it?

Short answer: A group for children that return Void. It frees each child as soon as it finishes instead of keeping its result. Use it for long-running "fire many jobs" loops, so memory doesn't grow forever. Available from iOS 17 / Swift 5.9.

await withDiscardingTaskGroup { group in
    for await message in socket.messages {   // endless stream
        group.addTask { await handle(message) }
    }
}

With a normal withTaskGroup, every finished child stays in memory until you call next(), which this loop never does.

Q9. What do child tasks inherit from the parent?

Inherited?Child task (async let, group)Task { }Task.detached { }
Cancellation from parent✅ Yes❌ No❌ No

Child tasks in a group are @Sendable closures and are not isolated to the caller's actor. If they call an actor's method, they hop to that actor with await.

Q10. What are task-local values?

Short answer: A value bound to the current task and all of its children, like a thread-local, but for tasks. Good for request IDs, tracing and logging context — things you don't want to pass through every function.

enum Trace {
    @TaskLocal static var requestID: String = "none"
}

await Trace.$requestID.withValue("req-42") {
    async let a = fetchA()   // inside: Trace.requestID == "req-42"
    async let b = fetchB()   // inside: Trace.requestID == "req-42"
    _ = await (a, b)
}
// outside: Trace.requestID == "none" again

The value is read-only inside the scope. It is not passed to Task.detached.

Q11. How does priority work? What is priority escalation?

Short answer: Children inherit the parent's priority. If a high-priority task awaits a lower-priority task, Swift raises the awaited task's priority so the important work isn't stuck behind it. This prevents priority inversion.

let prefetch = Task(priority: .background) { await loadCache() }

// later, on the main actor (userInitiated):
let cache = await prefetch.value   // prefetch is escalated to userInitiated

Actors also escalate: if high-priority work is waiting for an actor, the job that is currently running on it gets a higher priority.

Quick rule

  • Fixed set of parallel calls → async let.
  • Unknown number of calls → task group; add a limit for big inputs.
  • Many Void jobs, long-running → discarding task group.
  • Reach for Task { } only when you must start async work from sync code (see 4.6.2).
