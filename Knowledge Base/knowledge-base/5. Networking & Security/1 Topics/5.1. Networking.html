5.1. Networking

notes:

Q8. fetch() calls the backend, maps the response, and updates state. What types do you create, and who owns URLSession?

Say this: The view model asks a repository. The repository asks a network service. The service is the only type that sees URLSession. The bytes are a DTO. The repository maps that DTO into a domain model before the view model stores it.

View model  →  repository (protocol)  →  network service  →  URLSession
                 maps DTO to domain         Codable DTO
  • View model. Calls await repository.accounts(), writes state (.loading / .loaded / .failed). It does not build a URLRequest and it does not know URLSession exists.
  • Repository or use case. A protocol. It owns the mapping from the API shape to the app model, and any cache rule. The view model depends on the protocol.
  • Network service. Builds the request, calls the session, checks the status code, decodes the DTO. One service, many endpoints.
  • DTO vs domain. The Codable struct matches the JSON (account_id, optional fields, wire dates). The domain model is what the screen uses. They are different types so a backend rename does not leak into SwiftUI.

Who owns URLSession. The composition root creates one session (or passes .shared) and injects it into the network service. The service holds it. The repository and the view model do not. A session is expensive to create per call: it owns the connection pool and the cookie storage. One session per app, or one per backend, is enough.

protocol AccountsRepository {
    func accounts() async throws -> [Account]
}

struct AccountDTO: Decodable {
    let accountId: String
    let balanceCents: Int
}

final class AccountsAPI: AccountsRepository {
    private let client: HTTPClient
    func accounts() async throws -> [Account] {
        let dto: [AccountDTO] = try await client.get("/accounts")
        return dto.map { Account(id: $0.accountId, balanceCents: $0.balanceCents) }
    }
}

If you stall: "Would the view model know about URLSession?" No.

Q9. The network service calls URLSession.shared directly. How do you test it?

Say this: .shared is a real network. I do not call it from a unit test. Two changes I would offer, and I can name a third.

  1. Inject the session. init(session: URLSession = .shared). Production call sites stay the same. The test builds a session whose configuration uses a stub URLProtocol. .shared ignores a protocol you register later, so the default parameter is what makes the stub possible.
  2. A small protocol around the one method you call. HTTPClient with data(for:). URLSession conforms in an extension. The test passes a fake that returns Data and an HTTPURLResponse. This is the smallest fake when you do not care about redirects, cookies, or timeouts.
  3. URLProtocol. Use this when you want the real URLSession stack (status codes, decoding errors) without the network. Register the protocol on the configuration of the injected session, not on .shared.
protocol HTTPClient {
    func data(for request: URLRequest) async throws -> (Data, URLResponse)
}
extension URLSession: HTTPClient {
    func data(for request: URLRequest) async throws -> (Data, URLResponse) {
        try await data(for: request, delegate: nil)
    }
}

final class NetworkService {
    private let client: HTTPClient
    init(client: HTTPClient = URLSession.shared) { self.client = client }
}

I would not subclass URLSession. Its important methods are not designed as override points. I also would not hit a live host from the unit-test process.

If you stall: "Can the service receive the session from outside?" Yes. Default the parameter to .shared so existing callers do not change.
