10.26. MVVM: Model View- View Model

notes:

Q6. Who owns the coordinator and the navigation controller? How does the view model talk to the coordinator?

Say this: The parent owns the child coordinator. The child coordinator owns the navigation controller. The view controller owns the view model. The view model never imports UIKit. It reports a route. The coordinator turns that route into a push.

What keeps the coordinator alive: the parent holds it strongly. A flow coordinator that nobody retains will deallocate and later pushes vanish. The other pattern is to let the root view controller retain the coordinator. I name that if they ask, and I still prefer an explicit parent, because the lifetime is visible in the composition root.

Three ways to connect the view model and the coordinator:

  1. Weak delegate. The view model holds weak var router: AccountRouting?. The coordinator conforms. No cycle, as long as the protocol is AnyObject and the property is weak.
  2. Closures the coordinator assigns. viewModel.onShowDetails = { [weak self] id in self?.showDetails(id) }. Easy to read. The cycle appears when the closure captures the coordinator strongly and the coordinator owns the view model.
  3. A route stream. The view model exposes AsyncStream<Route> or a PassthroughSubject. It holds no coordinator at all. The coordinator subscribes. This is the answer to "notify without holding a reference".

I would pick the route stream for a new feature, or a weak delegate if the file already uses delegates. Closures are fine for one or two events. I would not let the view model push a UIViewController.

enum AccountRoute { case details(Account.ID) }

@MainActor
final class AccountsViewModel {
    private let routes: AsyncStream<AccountRoute>.Continuation
    let routeStream: AsyncStream<AccountRoute>

    init() {
        var continuation: AsyncStream<AccountRoute>.Continuation!
        routeStream = AsyncStream { continuation = $0 }
        routes = continuation
    }

    func accountTapped(_ id: Account.ID) {
        routes.yield(.details(id))
    }
}

If you stall: "What keeps the coordinator alive?" Then: "How could the view model notify without holding a reference?"

Q7. How do you unit test that tapping "Account details" opens the account details screen?

Say this: I do not launch the app. I inject a router into the coordinator, trigger the view-model event, and assert the spy recorded the details screen.

The seam is the navigation controller, or a small router protocol in front of it. The spy stores what was pushed. The test calls the same method the button calls (accountTapped), then reads the spy. A UI test is the wrong tool for this.

protocol AccountRouting: AnyObject {
    func pushDetails(_ id: Account.ID)
}

final class RouterSpy: AccountRouting {
    private(set) var details: [Account.ID] = []
    func pushDetails(_ id: Account.ID) { details.append(id) }
}

@Test @MainActor
func tapOpensDetails() {
    let spy = RouterSpy()
    let vm = AccountsViewModel()
    let coordinator = AccountsCoordinator(viewModel: vm, router: spy)

    coordinator.start()
    vm.accountTapped("acc-1")

    #expect(spy.details == ["acc-1"])
}

If the view model emits a route stream (Q6), the coordinator's start() subscribes and forwards to the spy. The test still does not build a UINavigationController. Injecting the real navigation controller and asserting viewControllers.last is AccountDetailsViewController also works, and it is heavier.

If you stall: "What would you inject into the coordinator?"
