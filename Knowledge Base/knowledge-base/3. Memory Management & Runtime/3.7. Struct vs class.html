3.7. Struct vs class

Short answer

Start with a struct. Use a class only when you need shared mutable identity, a deinit, inheritance or Obj-C/UIKit subclassing. A struct is a value type: every copy is independent. A class is a reference type: all variables point to the same object, and ARC tracks it.

Apple's standard library follows this rule: Array, String, Dictionary, Set, Data, URL and Date are all structs.

Use a value type when…

  • Equality is by content. Two coordinates with the same numbers are the same value.
  • Copies must be independent. No surprise changes through another variable (no aliasing).
  • You pass data across threads. Copies cannot race. Conform to Sendable.
  • Data flows through pure functions, e.g. reducers ((State, Action) -> State), parsing, mapping.
  • Performance matters. No heap, no ARC, and arrays of structs are contiguous in memory.
  • It is a SwiftUI View. Views are structs by design; SwiftUI diffs cheap value snapshots.
  • Typical examples: models, API responses (Codable), geometry, configuration, app state.
struct HTTPRequest {
    var url: URL
    var headers: [String: String]
}

func sign(_ req: HTTPRequest) -> HTTPRequest {
    var signed = req                 // independent copy
    signed.headers["Authorization"] = token()
    return signed                      // the original is unchanged
}

Use a reference type when…

  • Shared mutable state must be seen by many owners: a cache, a session, a store.
  • You need deinit to close a file, socket, database or C handle. A resource must have one owner and must not be copied.
  • Identity matters. Two sessions with equal data are still different sessions.
  • You need inheritance (e.g. a coordinator base class).
  • The framework requires it: UIView, UIViewController, NSObject subclasses, ObservableObject (@StateObject / @ObservedObject).
  • Callbacks must reach one instance: delegates and observers (AnyObject protocols).
  • The object is large and must never be copied, e.g. a big document model.
final class ImageCache {                  // shared by many screens
    private var storage: [URL: UIImage] = [:]
    func image(for url: URL) -> UIImage? { storage[url] }
    func store(_ image: UIImage, for url: URL) { storage[url] = image }
}

final class DatabaseConnection {            // exclusive resource
    private let handle: OpaquePointer
    init(path: String) { handle = openDB(path) }
    deinit { closeDB(handle) }
}

A class used from several threads needs protection. Prefer an actor, which is a reference type with built-in isolation.

Common mistakes

1. Class "to be safe"

A class with no shared state, no inheritance and no deinit only adds ARC and aliasing risk. Make it a struct.

2. Struct for shared state

struct BadCounter { var count = 0 }
var a = BadCounter()
var b = a
a.count += 1
print(b.count)   // 0: b is a separate copy

3. Reference inside a struct

A struct with a class property is not fully a value type. Copying the struct copies the pointer, so both copies share the object.

final class Buffer { var data: [UInt8] = [] }
struct Packet { var buffer = Buffer() }

var p1 = Packet()
var p2 = p1
p2.buffer.data.append(0xFF)
// p1.buffer.data is also [0xFF]

Fix: make Buffer a struct too, or use copy-on-write (3.8). If every stored property is a value type or a COW type like Array / String, the struct is a true value type.

4. Huge inline structs

Large fixed-size structs are copied in full on assignment. Large data in Array, String or Data is fine because they are copy-on-write.

SwiftUI note

Views are structs. State holders are classes: ObservableObject and @Observable view models. The framework keeps their identity across redraws. See SwiftUI.
