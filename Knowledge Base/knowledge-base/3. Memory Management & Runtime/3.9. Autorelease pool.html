3.9. Autorelease pool

Short answer

autorelease means "release this object later, not now". The object is added to the current autorelease pool. When the pool drains, it sends release to every object inside. In Swift you only meet it through Obj-C APIs (Foundation, UIKit, Core Graphics…). Wrap heavy loops in autoreleasepool { } so temporary objects are freed each iteration, not at the end of the run-loop turn.

Why it exists

An Obj-C method that returns an object it created has a problem: it no longer owns the object, but if it releases it now, the caller gets a dead pointer. autorelease solves this. The object lives until the pool drains, which gives the caller time to use it or retain it.

// Obj-C, manual reference counting (historical)
- (NSString *)greet {
    NSString *s = [[[NSString alloc] initWithFormat:@"Hello"] autorelease];
    return s;   // still alive after return; released when the pool drains
}
TermMeaning
autoreleaseRegisters an object in the current pool for a later release
PoolA per-thread stack of pools holding autoreleased objects
DrainSend release to everything in the pool, then pop the pool
@autoreleasepool { } / autoreleasepool { }Modern syntax: push a pool, run the block, drain (also when leaving by throw). NSAutoreleasePool is the old manual class, and cannot be used in Swift or with ARC

Where the pool comes from

  • Main thread: the run loop pushes a pool at the start of each iteration and drains it at the end (see 3.10). Objects live for at most one loop turn (about one frame).
  • GCD queues and OperationQueue: they create pools around work items, but Apple does not say when they drain. Do not depend on it for big batches.
  • Threads you create with pthread: no pool at all unless you create one.
  • Unit tests and command-line tools: no UIKit run-loop pool.

When you need an explicit pool

1. A loop that creates many Obj-C temporaries

// All images pile up until the run-loop turn ends (big memory peak)
for url in imageURLs {
    let image = UIImage(contentsOfFile: url.path)
    saveThumbnail(image)
}

// Each iteration frees its own images (peak = one iteration)
for url in imageURLs {
    autoreleasepool {
        let image = UIImage(contentsOfFile: url.path)
        saveThumbnail(image)
    }
}

2. Background work that uses Obj-C APIs heavily

DispatchQueue.global().async {
    autoreleasepool {
        let data = NSData(contentsOfFile: path)   // autoreleased
        parse(data)
    }   // drained here, at a known point
}

3. Tests, scripts and tools

Wrap Obj-C-heavy code in a pool. There is no run loop to drain it. The same applies to hot loops inside async functions. Do not rely on a pool per Task.

When you do not need one

  • Pure Swift types. Swift objects use direct retain/release. Nothing is autoreleased, so a pool around them does nothing.
  • Normal UI code on the main thread. The run loop pool is enough.
  • The compiler can remove an autorelease completely when caller and callee cooperate (the "return value optimization"), so you must not rely on an object being autoreleased.

A pool is cheap to push and pop (a stack operation), so do not avoid it for speed reasons. Put it only around code that really creates Obj-C temporaries.

Threads and pools

Pools are per thread and nest like a stack. You cannot drain another thread's pool. If you pass an autoreleased object to another thread, retain it first (ARC does this when you keep a strong reference).

Quick reference

ScenarioExplicit pool?
UI code on the main threadNo, the run loop handles it
Loop with thousands of Obj-C temporaries (images, NSData)Yes, inside each iteration
Heavy Obj-C work on a background queueYes, around the block's work
Pure Swift value types and classesNo
Tests, command-line toolsYes, around Obj-C-heavy code
