3.2. Object lifetime and deinit

Short answer

A class instance lives while its strong count is greater than 0. When the count drops to 0, Swift calls deinit once, on the thread that released the last reference, and then frees the memory.

Lifetime phases

PhaseWhat happens
AllocationHeap memory is allocated; strong count = 1
UseCount goes up and down as references are copied and released
TriggerCount reaches 0
deinitRuns your cleanup code, then the superclass deinit, and the object's stored properties are released
FreeMemory is returned. Weak references now read as nil

deinit rules

  • Runs exactly once. You cannot call it yourself.
  • Runs on whatever thread released the last reference. Touch UI only after hopping to the main thread.
  • Subclass deinit runs first, then the superclass deinit automatically.
  • Releasing stored properties can trigger more deinit calls (a chain).
  • Only classes and actors have deinit. Structs do not.
class Animal { deinit { print("Animal deinit") } }
class Dog: Animal { deinit { print("Dog deinit") } }

var d: Dog? = Dog()
d = nil   // "Dog deinit", then "Animal deinit"

What to clean up in deinit

class ScreenViewController: UIViewController {
    private var timer: Timer?

    deinit {
        NotificationCenter.default.removeObserver(self)  // old-style observers
        timer?.invalidate()                              // stop timers
    }
}

Use it for file handles, observers, timers and C resources. Do not start new work or store self anywhere in deinit.

If deinit never prints, the object is leaking. This is the quickest leak check. See 3.4.

Closures can keep an object alive

A closure that captures self strongly holds a strong reference. The object cannot die until the closure is released.

class Fetcher {
    func load() {
        URLSession.shared.dataTask(with: url) { [weak self] data, _, _ in
            // Without [weak self] the request keeps Fetcher alive until it finishes,
            // even if the screen is already gone.
            self?.process(data)
        }.resume()
    }
}

withExtendedLifetime

The optimizer may release an object right after its last use, not at the end of the scope. This matters when you pass an unretained pointer to a C API. withExtendedLifetime keeps the object alive for the whole block.

func callC(with obj: MyClass) {
    withExtendedLifetime(obj) {
        cFunction(Unmanaged.passUnretained(obj).toOpaque())
    }   // obj is guaranteed alive until here
}

Weak references after deinit

After the object dies, every weak reference to it reads as nil. This is why weak variables must be Optional. How it works: 3.3 and 3.6.
