3.12. Memory safety

Short answer

In safe Swift code, the language prevents the usual C memory bugs: reading uninitialized memory, using freed memory, and writing outside a buffer. It also enforces exclusive access: you cannot read and write the same variable at the same moment. Unsafe pointer APIs switch these guarantees off, and then you are responsible.

Four guarantees

GuaranteeHow Swift enforces it
No uninitialized memoryCompiler error if a variable is read before it is set
No dangling referencesARC keeps an object alive while a strong reference exists. weak becomes nil, unowned traps instead of reading garbage
No buffer overflowBounds checks on arrays and collections trap on a bad index
Exclusive accessOverlapping read/write access to a variable is an error (compile time, or runtime when it cannot be proven)
var count: Int
print(count)          // ❌ compile error: used before being initialized

let arr = [1, 2, 3]
let x = arr[5]         // runtime trap: index out of range

Exclusive access

A write access is exclusive for its whole duration. A read can overlap with other reads, but not with a write. The rule covers inout arguments, mutating methods and properties.

var score = 0
func increment(_ n: inout Int) { n += 1 }
increment(&score)             // OK: one write access during the call

Swift.swap(&score, &score)   // ❌ error: overlapping accesses to 'score'

A common runtime case is a function that takes a variable inout while its own code also touches that variable (for example a closure that reads the same global or class property). Swift cannot always prove this at compile time, so it checks at runtime. A violation crashes with "Simultaneous accesses to …". This check is on in debug and release builds by default.

  • Structs: overlapping access to different stored properties of a local struct is allowed when the compiler can prove it is safe. It is not allowed for global variables or class properties.
  • Exclusivity is about one thread. Access from several threads is a data race. Use an actor, queue or lock (see the Concurrency section).

Unsafe pointers

For C interop and rare performance work, Swift offers pointer types with no safety checks.

TypeMeaning
UnsafePointer<T> / UnsafeMutablePointer<T>Typed pointer, read-only / read-write, no bounds checks
UnsafeRawPointer / UnsafeMutableRawPointerUntyped pointer to raw bytes
UnsafeBufferPointer<T>Typed pointer + count. Still no bounds trap in release builds
Unmanaged<T>Object reference outside ARC. You do retain/release yourself

Use the withUnsafe… functions. The pointer is valid only inside the closure.

var buffer = [UInt8](repeating: 0, count: 256)
buffer.withUnsafeMutableBytes { ptr in
    fillBuffer(ptr.baseAddress!, Int32(ptr.count))   // C function; valid here only
}

var leaked: UnsafePointer<Int>?
var n = 42
withUnsafePointer(to: &n) { leaked = $0 }   // ❌ pointer escapes: undefined behaviour

Undefined behaviour

Break the rules in unsafe code and the result is undefined: crashes, silent corruption, or code that works in debug and fails with optimizations. Typical causes:

  • Using a pointer after the memory it points to is gone.
  • Reading or writing past the end of a buffer.
  • Reading memory as the wrong type (type punning without UnsafeRawPointer rules).
  • Unbalanced Unmanaged retain/release (leak or over-release).

Best practices

  • Keep unsafe code small and hidden behind a safe function or type.
  • Write down your assumptions about lifetime, size and alignment in a comment.
  • Prefer withUnsafe… closures and UnsafeBufferPointer over loose pointers.
  • Test with Address Sanitizer (see 3.11).
