3.19. Use a value type when…

Value types — struct, enum, tuple — store data inline and copy on assignment. Here are the concrete signals that a value type is the right choice.

1. Equality is defined by content, not identity

If two instances with the same data should be considered equal, you want value semantics. There is no meaningful "same object" — only "same value".

struct Coordinate: Equatable {
    var latitude:  Double
    var longitude: Double
}

let a = Coordinate(latitude: 51.5, longitude: -0.1)
let b = Coordinate(latitude: 51.5, longitude: -0.1)
a == b   // true — same data, not same instance

2. Copies should be independent

When you pass a value to a function or assign it to another variable, mutations to the copy must not affect the original. This eliminates a whole class of aliasing bugs.

struct HTTPRequest {
    var url:     URL
    var method:  String
    var headers: [String: String]
}

func signRequest(_ req: HTTPRequest) -> HTTPRequest {
    var signed = req                     // independent copy
    signed.headers["Authorization"] = token()
    return signed
}
// original `req` is unchanged — no defensive copying needed

3. You want thread safety without locks

A value type copied across thread boundaries cannot be mutated by another thread — each thread owns its own copy. No data races, no NSLock, no @Sendable dance for the value itself.

struct FeatureFlags: Sendable {
    var isNewUIEnabled:    Bool
    var maxRetryCount:     Int
    var experimentVariant: String
}

// Safe to copy into a Task — each Task gets its own independent copy
let flags: FeatureFlags = loadFlags()
Task {
    process(flags)   // no lock needed
}

4. You want to avoid aliasing bugs

With reference types, two variables can point at the same object. A function that seems to "only read" can modify the caller's data if both share the same instance. Structs eliminate this entirely.

// Class: aliasing risk
class Config { var timeout: Int = 30 }
let shared = Config()
let alias  = shared
alias.timeout = 0    // also changes shared.timeout!

// Struct: no aliasing
struct ConfigV { var timeout: Int = 30 }
let original = ConfigV()
var copy = original
copy.timeout = 0     // original.timeout is still 30

5. Functional / immutable data flow

Pipelines that transform data — parsing, mapping, filtering, rendering — fit naturally with value types. Each stage receives an independent copy and returns a new one. No need to worry about intermediate state escaping.

struct AppState {
    var user:   User
    var items:  [Item]
    var filter: Filter
}

// Reducer: pure function, returns a new state
func reduce(_ state: AppState, action: Action) -> AppState {
    var next = state
    switch action {
    case .setFilter(let f): next.filter = f
    default: break
    }
    return next
}

6. Performance: no ARC, no heap (usually)

A struct with only stored value-type properties lives entirely on the stack. No reference counting overhead on copy, no heap allocation, no lock contention. For hot-path code (tight loops, rendering), this matters.

struct Vector3 {
    var x, y, z: Float   // 12 bytes total, fully inline
}

// Thousands of these in an array: contiguous memory, no pointer chasing
var particles: [Vector3] = Array(repeating: .zero, count: 10_000)

7. SwiftUI views must be structs

SwiftUI requires View conforming types to be structs. The framework diffs value snapshots to decide what to re-render. A class-based View would break diffing because two references to the same instance look identical even after mutation.

struct ProfileCard: View {
    let name:   String
    let avatar: Image

    var body: some View {
        HStack { avatar; Text(name) }
    }
}
// struct → SwiftUI can cheaply snapshot and diff the view

Anti-pattern: struct with class properties that share state

A struct that holds a reference type does not give you full value semantics. Copying the struct copies the pointer, not the underlying object. Both copies mutate the same heap data.

class Buffer { var data: [UInt8] = [] }

struct Packet {
    var buffer = Buffer()   // reference type inside struct
}

var p1 = Packet()
var p2 = p1               // struct is copied, but buffer is shared!
p2.buffer.data.append(0xFF)
// p1.buffer.data is also [0xFF] — surprise!

// Fix: use Copy-on-Write (see 3.21) or make Buffer a struct too

Rule of thumb: if all stored properties are value types (or COW types like Array/String), copying the struct gives genuinely independent data. One class property breaks that guarantee.
