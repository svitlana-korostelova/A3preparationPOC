3.17. Detect memory issues

Tool Overview

1. Xcode Memory Graph Debugger

The fastest way to catch retain cycles. While the app is running in the debugger:

  1. Click the Memory Graph button in the debug bar (icon: three connected nodes).
  2. Xcode pauses execution and renders the object graph.
  3. Purple arrows mark retain cycles (objects that reference each other in a cycle, preventing dealloc).
  4. Click any object to see its backtrace (requires Malloc Stack Logging enabled in Scheme → Diagnostics).

Enable Malloc Stack Logging beforehand: Scheme → Run → Diagnostics → Malloc Stack → "Live Allocations Only". Without it, you see the cycle but not where the objects were created.

2. Instruments — Leaks

Runs a live leak detector that scans the heap periodically for objects with no path from GC roots (unreachable objects that are still allocated).

  1. Product → Profile → choose Leaks template.
  2. Exercise the app — navigate screens, trigger the suspected flow.
  3. Red bars in the Leaks track indicate leaked objects at that moment.
  4. Select a leak → Cycles & Roots view shows the retain cycle graph.
  5. Switch to Call Tree view with "Invert Call Tree" to find the allocation site.

3. Instruments — Allocations

Tracks every heap allocation and deallocation over time.

  • "Mark Generation": snapshot allocations at a point in time. Navigate away and back; new generation shows what wasn't released. Repeated generations that grow = leak.
  • Heap Snapshot: compare before/after a flow to see net allocations.
  • Statistics view: sort by "Persistent" (currently live) to find dominant object types.

4. Address Sanitizer (ASan)

A compiler instrumentation tool that catches memory safety violations at runtime. Enabled per-scheme, not per-run; it adds ~2x runtime overhead.

Enable: Scheme → Run → Diagnostics → Address Sanitizer ✓

  • Use-after-free: accessing deallocated memory
  • Heap buffer overflow: writing past an allocated region
  • Stack buffer overflow: writing past a stack array
  • Use of uninitialized memory (with -fsanitize=memory)

ASan cannot detect retain cycles — use the Memory Graph for those.

5. MallocStackLogging

Records the call stack at every allocation. Combined with the Memory Graph Debugger, it shows where leaked objects were created, not just that they exist.

// Enable via environment variable (Scheme → Run → Arguments → Environment)
// MallocStackLogging = 1        (record all allocs)
// MallocStackLogging = lite     (record only allocation events, less overhead)

// Or in Xcode Scheme → Diagnostics → Malloc Stack → Live Allocations Only

On the command line, malloc_history <pid> <address> prints the allocation backtrace for a specific address.

6. Xcode Runtime Warnings

These appear as purple runtime issues in the debug navigator without any extra configuration:

  • "Publishing changes from background threads" — mutating @Published / @State off main thread in SwiftUI
  • "UI API called from background thread" — UIKit access off main
  • Main actor violations — in Swift Concurrency strict mode

These warnings don't catch memory leaks but catch the kind of concurrency bugs that often cause use-after-free crashes.

Common Code Patterns That Leak

// 1. Missing [weak self] in closure that captures self strongly
class ViewModel {
    var onUpdate: (() -> Void)?

    func setup() {
        onUpdate = {            // ← captures self strongly
            self.reload()       // ← cycle: ViewModel → closure → ViewModel
        }
    }
    func reload() {}
}

// Fix:
func setup() {
    onUpdate = { [weak self] in
        self?.reload()
    }
}

// 2. NotificationCenter observer not removed
class BadVC: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        NotificationCenter.default.addObserver(
            self, selector: #selector(handle), name: .someNote, object: nil
        )
        // ↑ old API keeps a strong reference — VC never deallocates
        // Fix: call removeObserver in deinit, OR use block-based API with [weak self]
    }
}

// 3. Timer not invalidated → Timer holds strong ref to target
class BadVC: UIViewController {
    var timer: Timer?

    override func viewDidLoad() {
        timer = Timer.scheduledTimer(
            target: self,             // ← Timer retains self strongly
            selector: #selector(tick),
            userInfo: nil, repeats: true
        )
    }
    deinit {
        timer?.invalidate()  // ← must call; invalidate() releases target reference
    }
}

Delegate as Strong Reference

// Common pattern that leaks:
class NetworkClient {
    var delegate: NetworkDelegate?  // should be `weak`
}

// ViewController creates NetworkClient and sets itself as delegate:
// ViewController → (strong) NetworkClient → (strong) ViewController
// Fix: make delegate weak
class NetworkClient {
    weak var delegate: NetworkDelegate?
}

Quick Checklist Before Shipping

  • Run Memory Graph after major navigation flows — no purple arrows
  • Run Instruments Leaks after exercising all screens
  • Check Allocations for unbounded growth across back-forward navigation
  • Review all closures stored as properties: do they capture self strongly?
  • Review all delegates: are they weak?
  • Confirm every Timer / CADisplayLink has a matching invalidate()
  • Confirm NotificationCenter old-style observers are removed in deinit
