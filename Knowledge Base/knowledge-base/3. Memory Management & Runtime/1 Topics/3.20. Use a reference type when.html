3.20. Use a reference type when…

Reference types — class, actor — store a single object on the heap and share it via pointers. Here are the concrete signals that a reference type is the right choice.

1. Shared mutable state across multiple owners

When multiple parts of the app need to read and write the same data, a class lets them all hold a reference to one object. A struct would give each caller an independent copy, defeating the purpose.

class ImageCache {
    private var storage: [URL: UIImage] = [:]

    func store(_ image: UIImage, for url: URL) { storage[url] = image }
    func image(for url: URL) -> UIImage?  { storage[url] }
}

// One shared instance — every view controller sees the same cache
let cache = ImageCache()
let vc1 = FeedViewController(cache: cache)
let vc2 = DetailViewController(cache: cache)

2. Lifecycle management — deinit

Classes have a deinit that fires exactly once when the last strong reference drops. Use this to close file handles, cancel subscriptions, invalidate timers, or release C resources.

class DatabaseConnection {
    private let handle: OpaquePointer

    init(path: String) {
        handle = openDatabase(path)
    }

    deinit {
        closeDatabase(handle)   // guaranteed cleanup
    }
}

Structs have no deinit. If you need deterministic teardown tied to object lifetime, you need a class.

3. Identity matters

Sometimes two objects with identical data are different things — a user's two devices, two network sessions opened at different times. Classes let you use === to check pointer identity.

class NetworkSession {
    let id = UUID()
}

let s1 = NetworkSession()
let s2 = NetworkSession()
s1 === s1   // true  — same object
s1 === s2   // false — different sessions, even if id happened to match

4. Inheritance hierarchy required

Only classes support single-class inheritance. If you need to specialise behaviour across a type hierarchy — UIViewController subclasses, NSOperation subclasses, plugin/strategy hierarchies with shared base state — you need a class.

class BaseCoordinator {
    var childCoordinators: [BaseCoordinator] = []
    func start() { /* override */ }
}

class AuthCoordinator: BaseCoordinator {
    override func start() { showLoginScreen() }
}

class AppCoordinator: BaseCoordinator {
    override func start() { showMainTab() }
}

5. Interfacing with Obj-C / UIKit

UIKit and AppKit are built on Obj-C, which has no value-type semantics. UIView, UIViewController, CALayer, URLSessionTask — all are classes. Subclassing them requires a class.

class ProfileViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        setupUI()
    }
}

6. Holding external resources

A type that wraps a file descriptor, socket, hardware connection, or C library handle must be a class. Resources can't be copied — you want exactly one owner managing the resource lifetime.

class FileHandle {
    private let fd: Int32

    init(path: String) { fd = open(path, O_RDONLY) }
    deinit             { close(fd) }

    func read(count: Int) -> Data { /* ... */ }
}
// Copying a file handle struct would mean two owners calling close(fd)

7. Delegate / observer pattern

Delegates and notification observers must be stable objects — callbacks come in at unknown future times and must reach the same instance that registered. Passing a struct by value here breaks the contract.

protocol DataSourceDelegate: AnyObject {
    func didUpdate(items: [Item])
}

class FeedViewController: UIViewController, DataSourceDelegate {
    func didUpdate(items: [Item]) { reload(items) }
}

let ds = DataSource()
ds.delegate = feedVC   // weak reference to the class instance

8. Large data not worth copying

Swift's standard collections use Copy-on-Write, so passing an Array is usually cheap. But a truly large object graph — a parsed AST, a document model, a compiled shader — may be better as a class to ensure it is never accidentally copied in full.

SwiftUI note: ObservableObject requires a class

@StateObject and @ObservedObject hold a reference type that conforms to ObservableObject. SwiftUI manages its lifetime and observes objectWillChange to trigger redraws. The class's identity is what SwiftUI tracks across re-renders.

final class UserSession: ObservableObject {
    @Published var isLoggedIn = false
    @Published var userName: String = ""
}

struct RootView: View {
    @StateObject private var session = UserSession()
    var body: some View {
        session.isLoggedIn ? AnyView(MainTab()) : AnyView(LoginView())
    }
}
