3.9. Heap

What the heap is

The heap is a large region of virtual memory shared by all threads in a process. Unlike the stack, it has no fixed layout — allocations can be any size, in any order, with any lifetime. The system allocator (libmalloc on Apple platforms) manages free blocks and recycles memory when it is released.

Allocation lifecycle

  1. Request: malloc(size) (called internally by Swift runtime on class init)
  2. Search: allocator finds a free block ≥ size in its free list or allocates a new page
  3. Bookkeeping: header metadata written; block marked in-use
  4. Return: aligned pointer handed to the caller
  5. Deallocation: ARC's swift_release decrements the retain count; at zero, deinit runs, then free(ptr)

Step 2–3 require either a lock or a lock-free CAS loop, making heap allocation orders of magnitude slower than a stack SP decrement.

ARC object header layout

Every Swift class instance on the heap begins with a fixed header (on 64-bit platforms):

OffsetFieldSizePurpose
0isa8 bytesPointer to the class metadata (type information, vtable)
8RefCounts8 bytesPacked strong count + weak count flags + side-table bit

Total minimum overhead: 16 bytes per object, before any stored properties.

class Node {
    var value: Int          // 8 bytes stored property
    var next: Node?         // 8 bytes (optional pointer)
    init(_ v: Int) { value = v }
}
// Heap layout of Node: [isa 8B][refcounts 8B][value 8B][next 8B] = 32 bytes minimum

Thread safety of heap allocation

Apple's libmalloc uses magazine allocators — per-CPU or per-thread caches of fixed-size blocks — to reduce lock contention. For small allocations (common case), a thread can often grab a block from its own magazine without any lock. Larger allocations still require global locking.

However, thread-safety of allocation doesn't mean thread-safety of the object. Multiple threads reading and writing the same heap object's properties still requires synchronization (actor, DispatchQueue, os_lock, etc.).

ARC atomic operations

The retain count field uses atomic increment/decrement (lock xadd on x86, stlxr/`ldadd` on ARM). This guarantees correctness across threads but adds CPU barrier overhead on every copy of a reference.

class Session { var id: String = "" }

func work() {
    let s = Session()       // malloc + refCount = 1
    let copy = s             // atomic retain → refCount = 2
    // copy goes out of scope → atomic release → refCount = 1
    // s goes out of scope   → atomic release → refCount = 0 → deinit → free()
    _ = copy
}

Memory fragmentation

Over time, allocating and freeing objects of varying sizes leaves gaps in the heap. These gaps are too small for new allocations but too large to ignore — this is fragmentation. On iOS, the OS can compact physical pages (via the virtual memory system) but cannot move Swift objects in place. Fragmentation manifests as increased dirty memory in Instruments and higher memory pressure.

Mitigation: use value types for short-lived data, pool expensive objects, and avoid creating many tiny heap allocations in tight loops.
