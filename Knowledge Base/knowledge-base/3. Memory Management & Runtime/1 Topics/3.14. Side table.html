3.14. Side table

The Problem: One Header, Too Many Counters

Every Swift heap object starts with a HeapObject header — just 16 bytes on a 64-bit system: 8 bytes for the metadata pointer (isa) and 8 bytes for a packed reference counts field. That 8-byte field must simultaneously track:

  • Strong reference count
  • Unowned reference count
  • Weak reference count
  • Whether the object is being deallocated (a "deiniting" flag)
  • Whether a side table exists

Packing all of this into 64 bits is tight. The solution is a two-tier system: the common case (strong refs only, no overflow) stays in the header; the rare case (weak refs or counter overflow) spills to a side table.

Normal Object Layout (No Side Table)

// HeapObject in memory (simplified)
// Offset 0: metadata pointer (8 bytes)   ← type info, vtable
// Offset 8: ref counts    (8 bytes)
//   bits 63:   hasSideTable flag = 0
//   bits 62-32: strong ref count (inline, non-atomic fast path)
//   bits 31-0:  unowned ref count (inline)

As long as hasSideTable == 0, ARC operations work entirely within the header with no indirection — this is the common, fast path.

When a Side Table Is Created

The runtime allocates a side table (HeapObjectSideTableEntry) in two situations:

  1. A weak reference is taken to the object — weak refs are tracked exclusively in the side table.
  2. The inline strong/unowned count overflows its bit field (rare in practice).

At that moment the runtime:

  1. Allocates a HeapObjectSideTableEntry on the heap.
  2. Moves the current ref counts into it.
  3. Writes the side table's address into the object's ref-count field.
  4. Sets hasSideTable = 1 in the header to signal the change.

Side Table Layout

// HeapObjectSideTableEntry (pseudocode)
struct HeapObjectSideTableEntry {
    var object: UnsafeMutableRawPointer  // back-pointer to the heap object
    var strongCount:  UInt32
    var unownedCount: UInt32
    var weakCount:    UInt32            // +1 for the object itself while alive
}

The side table's weak count starts at 1 — the object itself holds a "stake" in its own side table. When the object deallocates, it decrements this count. Only when all weak references are also released does the side table itself get freed.

Weak Reference Lifecycle Through the Side Table

class Owner {}
class Observer {
    weak var owner: Owner?  // stored as: pointer → side table entry
}

func example() {
    var o: Owner? = Owner()
    let obs = Observer()
    obs.owner = o  // ← side table created; weakCount = 2 (object + this weak ref)

    o = nil  // strong count → 0 → object deallocated
             // side table: weakCount decremented to 1 (only obs.owner holds it)
             // side table survives; object pointer in it set to nil

    print(obs.owner)  // → nil (loads via side table, sees object is gone)
    // obs deallocs → weak ref released → weakCount → 0 → side table freed
}

How Weak Load Works

Loading a weak var is not a simple pointer dereference. The runtime calls swift_weakLoadStrong:

  1. Load the pointer stored in the weak variable — it points to the side table entry (not directly to the object).
  2. Check if the side table's object pointer is non-nil and the strong count > 0.
  3. If alive: atomically increment strong count (to prevent deallocation mid-load), return pointer to object.
  4. If dead: return nil.

This is why weak loads in Swift are thread-safe by design — the atomic bump in step 3 prevents a race where the object dies between the check and the use.

Why Not Zero Out Weak Refs Eagerly?

An alternative design would walk all weak references on dealloc and zero them. The side table avoids this: you only need to update one location (the object pointer in the side table), and all weak references automatically see nil on next load — no scan, no pointer chasing. This is O(1) on dealloc regardless of how many weak references exist.

Interview Takeaway

The side table is a lazy optimization: most objects never need one (no weak references), so they pay no overhead. The moment a weak reference is taken, the runtime transparently promotes the object to use the side table — callers see no change. The key invariant is that a side table can outlive the object it describes, which is exactly what allows weak references to safely return nil after dealloc without any eager zeroing pass.
