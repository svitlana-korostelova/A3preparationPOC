3.6. Unowned references

Definition

An unowned reference holds a reference to an object without increasing its retain count, just like weak. The key difference: unowned is non-optional and assumes the referenced object will always be alive when you access it. If the assumption is violated — the object was deallocated but you still access the reference — the program traps with a fatal error.

When to use unowned

Use unowned when the lifetime of the referencing object is strictly contained within the lifetime of the referenced object. The referenced object must be created first and destroyed last.

Classic example: Customer and CreditCard

class Customer {
    let name: String
    var card: CreditCard?        // Customer optionally owns a card
    init(_ n: String) { name = n }
    deinit { print("\(name) gone") }
}

class CreditCard {
    let number: Int
    unowned let owner: Customer  // card CANNOT exist without a customer
    init(_ n: Int, owner: Customer) {
        number = n
        self.owner = owner
    }
    deinit { print("card \(number) gone") }
}

var alice: Customer? = Customer("Alice")
alice!.card = CreditCard(1234, owner: alice!)

alice = nil
// prints "card 1234 gone" then "Alice gone" — no leak
// CreditCard is released (Customer releases it), then Customer releases itself

Closure capture with unowned

class ViewController: UIViewController {
    var onTap: (() -> Void)?

    func viewDidLoad() {
        super.viewDidLoad()
        onTap = { [unowned self] in
            // Safe only if the closure cannot outlive self.
            // If the button is released when VC is gone, this will crash.
            self.dismiss(animated: true)
        }
    }
}

Prefer [weak self] when in doubt. Use [unowned self] only when you are certain the closure's lifetime is contained within self's lifetime.

unowned(safe) vs unowned(unsafe)

VariantOn dealloc accessUse case
unowned / unowned(safe)Fatal error (trap) — detectableDefault; gives a crash with a clear message
unowned(unsafe)Undefined behaviour — dangling pointer, possible silent corruptionPerformance-critical interop with C; no ARC checks at all

Never use unowned(unsafe) unless you are absolutely certain of the lifetime and need to eliminate the ARC overhead of even the safety trap check.
