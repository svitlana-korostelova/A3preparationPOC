3.4. Object lifetime

Lifetime rule

A heap-allocated object is alive as long as its strong reference count is greater than zero. The moment it drops to zero, the runtime calls deinit synchronously on the calling thread, then frees the memory.

Phases

PhaseWhat happens
Allocationmalloc on the heap; ARC header initialised with strong count = 1
UseStrong count fluctuates as references are assigned and released
Deallocation triggerStrong count drops to 0
deinitCalled exactly once, synchronously, on the thread that released the last reference
Memory freedAfter deinit returns; weak refs are zeroed; the heap block is returned

deinit use cases

class FileHandle {
    private let fd: Int32

    init(path: String) {
        fd = open(path, O_RDONLY)
    }

    deinit {
        close(fd)               // release the file descriptor
        print("FileHandle closed")
    }
}

class ViewController: UIViewController {
    deinit {
        NotificationCenter.default.removeObserver(self)  // remove observers
        timer?.invalidate()                                // cancel timers
    }
}

Swift guarantees about deinit

  • Called exactly once — never skipped, never called twice.
  • Called on the thread that decrements the count to zero — could be any thread. If you update UI in deinit, dispatch to the main thread.
  • Cannot be called manually — deinit is not a regular method.
  • Subclass deinit runs before superclass deinit automatically.

Closures extending lifetime

A closure that captures self strongly holds a strong reference. This can unexpectedly extend an object's lifetime beyond what you intend:

class Fetcher {
    func load() {
        URLSession.shared.dataTask(with: url) { [weak self] data, _, _ in
            // Without [weak self], the network task holds Fetcher alive
            // until the response arrives — even if the view is gone.
            self?.process(data)
        }.resume()
    }
}

withExtendedLifetime

Occasionally you need to guarantee an object stays alive through a block of code — for example when interoperating with C APIs that take an unretained pointer:

func callCAPI(with obj: MyClass) {
    withExtendedLifetime(obj) {
        // ARC may not insert a retain here otherwise
        cFunctionTakingRawPointer(Unmanaged.passUnretained(obj).toOpaque())
    }
    // obj guaranteed alive through the closure above
}

withExtendedLifetime inserts a use of the object that prevents the compiler from releasing it early — a hint to both ARC and the optimiser.

Weak references and deallocation

When an object is deallocated, the runtime automatically sets all weak references to it to nil before the memory is freed. This is why weak var must always be Optional — it may become nil at any point.
