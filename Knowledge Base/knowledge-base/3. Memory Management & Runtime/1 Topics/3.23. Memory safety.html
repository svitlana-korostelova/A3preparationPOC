3.23. Memory safety

Swift's four core memory-safety guarantees

1. No uninitialized memory

Every variable must be initialized before it is read. The compiler enforces this statically. There is no equivalent of C's uninitialised stack variable that silently reads garbage.

var count: Int
print(count)   // ❌ compiler error: variable 'count' used before being initialized

var count: Int = 0
print(count)   // ✅ always 0

2. No dangling pointers

ARC ensures an object is kept alive as long as there is a strong reference to it. You cannot hold a raw pointer to memory that has been freed — there is no free() for Swift objects. Unsafe pointer APIs exist, but you must manage their lifetime explicitly (see below).

3. No buffer overflows (in safe code)

Array and collection accesses are bounds-checked at runtime. An out-of-bounds index triggers a runtime trap rather than silently reading adjacent memory.

let arr = [1, 2, 3]
let x = arr[5]   // runtime trap: index 5 is out of bounds for array of size 3

In optimised builds the compiler may elide redundant bounds checks when it can prove safety statically, but the guarantee holds for all bounds it cannot prove.

4. Exclusive access law

Swift enforces that a variable cannot be read and written — or written twice — at the same time. This rule is checked at compile time where possible, and at runtime otherwise. It prevents a class of bugs common in C where a pointer alias lets two paths touch the same memory simultaneously.

Exclusive access in detail

inout parameters

When you pass a variable as inout, Swift takes an exclusive write-access lock for the duration of the call. No other access to that variable is allowed while the function runs.

func increment(_ n: inout Int) { n += 1 }

var score = 0
increment(&score)   // exclusive write access during the call

// ❌ conflict: passing the same variable twice
func swap(_ a: inout Int, _ b: inout Int) { let tmp = a; a = b; b = tmp }
swap(&score, &score)   // compile error: inout arguments alias each other

mutating methods and captured variables

Calling a mutating method on a struct takes a write access for the entire duration of the call. Reading the struct inside the method is safe, but passing it elsewhere as inout simultaneously is not.

struct Counter {
    var value = 0
    mutating func reset() { value = 0 }
}

var c = Counter()
c.reset()   // exclusive write access; safe

Runtime access conflict example

The compiler cannot always detect conflicts statically. For captured variables in closures, access tracking happens at runtime.

var total = 0
func modify(_ body: (inout Int) -> Void) { body(&total) }

// ❌ runtime exclusivity violation — total is simultaneously read and passed inout
modify { total += $0 }   // closure reads `total` while `total` is inout

Unsafe pointer APIs — opting out of safety

Swift provides unsafe pointer types for C interoperability and performance-critical code. Using them opts out of memory safety guarantees. You become responsible for lifetime, alignment, and bounds.

TypeSemantics
UnsafePointer<T>Read-only typed pointer; no bounds checking
UnsafeMutablePointer<T>Read/write typed pointer; no bounds checking
UnsafeRawPointerRead-only untyped pointer (raw bytes)
UnsafeMutableRawPointerRead/write untyped pointer (raw bytes)
UnsafeBufferPointer<T>Typed pointer + count (still no bounds trap)
// Calling a C function that fills a buffer
var buffer = [UInt8](repeating: 0, count: 256)
buffer.withUnsafeMutableBytes { ptr in
    fillBuffer(ptr.baseAddress!, Int32(ptr.count))
    // Inside this scope ptr is valid. After the closure, it must not be used.
}

// Dangerous: storing a pointer beyond its safe lifetime
var dangling: UnsafePointer<Int>?
var x = 42
withUnsafePointer(to: &x) { dangling = $0 }
// ❌ dangling now points to freed stack memory

withUnsafeMutablePointer and withUnsafeBytes

withUnsafeMutablePointer(to:_:) and Array.withUnsafeBytes(_:) are the safe entry points for unsafe access: they provide a pointer valid only for the lifetime of the closure, preventing you from storing it beyond its valid scope (at least, they make it obvious you shouldn't).

Undefined behaviour in unsafe code

When you cross into the unsafe zone and violate the rules, you get undefined behaviour — the same class of bugs as in C. The Swift compiler can assume safe code is well-behaved and may reorder, elide, or miscompile unsafe violations in optimised builds.

Common sources of UB with unsafe Swift:

  • Dereferencing a pointer after the pointee's lifetime ends.
  • Writing through a UnsafePointer (read-only type) via a cast.
  • Accessing a buffer past its bounds through an UnsafeBufferPointer.
  • Violating strict aliasing by reinterpreting memory as the wrong type without using UnsafeRawPointer properly.

Best practices for unsafe code

  • Isolate it. Wrap unsafe code in a clearly-named function or extension. The surface area of unsafe code should be minimal.
  • Document the invariants. Comment exactly what you are assuming about lifetimes, alignment, and bounds. Future readers (and the compiler) cannot check these for you.
  • Use the withUnsafe* family over storing raw pointers — the closure-based API makes the valid lifetime explicit.
  • Prefer UnsafeBufferPointer over a bare pointer + length pair; it at least keeps them together.
  • Test with Address Sanitizer (ASan) — Xcode's ASan detects use-after-free, buffer overflows, and other memory errors in unsafe code at runtime.
