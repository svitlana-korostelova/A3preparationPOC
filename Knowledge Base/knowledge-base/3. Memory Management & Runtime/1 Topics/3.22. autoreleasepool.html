3.22. autoreleasepool

What autorelease is

In the Objective-C runtime, an object can be sent autorelease instead of release. Rather than decrementing the reference count immediately, autorelease registers the object in the current autorelease pool. When the pool drains, every registered object is sent release — their reference count decrements and, if it reaches zero, they are deallocated.

This mechanism exists because many Obj-C factory methods need to return an object the caller can use but nobody currently owns. Instead of leaking it, the method autoreleases it and lets the pool's drain clean it up.

The main run loop and automatic drain

On the main thread the run loop wraps each event iteration in an autorelease pool. The cycle is:

  1. Pool is pushed (created) at the start of the iteration.
  2. Event is processed — UIKit, timers, notifications fire.
  3. Pool is popped (drained) at the end of the iteration.

For typical UI code this means autoreleased objects live for at most one run-loop turn — about one frame (≈ 16 ms). Under normal conditions you don't think about it.

When you need an explicit autoreleasepool

1. Background threads

Threads you create with Thread, DispatchQueue.global(), or OperationQueue have no automatic autorelease pool. Autoreleased objects from Obj-C APIs accumulate without limit. When the thread ends or the pool is never drained, they leak.

DispatchQueue.global().async {
    autoreleasepool {                     // explicit pool on background thread
        let data = NSData(contentsOfFile: path)   // autoreleased NSData
        process(data)
    }                                     // data released here, not at thread end
}

2. Tight loops creating many temporaries

If each loop iteration calls Obj-C APIs that return autoreleased objects, those objects accumulate in the pool until the run loop drains at the end of the current event. With thousands of iterations this causes a memory spike. Wrapping each iteration in autoreleasepool drains after each step.

// Without autoreleasepool — memory grows across all iterations
for url in imageURLs {
    let image = UIImage(contentsOfFile: url.path)
    saveThumbnail(image)
    // image is autoreleased but won't be freed until run-loop drains
}

// With autoreleasepool — each UIImage freed after the iteration
for url in imageURLs {
    autoreleasepool {
        let image = UIImage(contentsOfFile: url.path)
        saveThumbnail(image)
    }   // pool drains → image freed immediately
}

The memory profile difference can be dramatic: without the pool, peak memory is proportional to the array size; with it, peak is proportional to one iteration.

3. Unit tests and command-line tools

XCTest test targets and command-line Swift programs may not have a run loop at all, or may have one that never drains. Wrap autorelease-heavy work in an explicit pool.

func testImageProcessing() {
    autoreleasepool {
        let result = processLargeBatch()
        XCTAssertEqual(result.count, 1000)
    }
}

Swift-native APIs and autorelease

Pure Swift types do not use autorelease — ARC deallocates them immediately when the reference count hits zero. The autoreleasepool block is only relevant when calling Obj-C APIs bridged into Swift: Foundation types (NSData, NSString, NSArray), UIKit, Core Graphics, Core Data, etc.

If your loop only creates Swift structs and Swift classes, adding autoreleasepool around it is a no-op. Only add it when you are certain Obj-C methods are involved.

Cost of autoreleasepool

Pushing and popping a pool is very cheap — it is a stack operation on the thread's pool stack. The overhead is negligible compared to the allocation cost of the objects inside it. Do not avoid autoreleasepool on performance grounds.

Swift concurrency: implicit pool per Task

Each Swift Task body gets an implicit autorelease pool for the synchronous portion of its execution. This means you rarely need an explicit pool inside async functions — but you may still need one around loops that call Obj-C synchronous APIs intensively within an async context.

func processBatch() async {
    for item in heavyBatch {
        autoreleasepool {               // belt-and-suspenders in a hot async loop
            renderObjCThumbnail(item)
        }
    }
}
