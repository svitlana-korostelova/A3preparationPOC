3.11. ARC in detail

What ARC is

Automatic Reference Counting is a compile-time transformation. The Swift compiler analyzes your code and inserts swift_retain and swift_release calls at the appropriate points. There is no garbage collector running at runtime, and no stop-the-world pauses. The only runtime cost is the atomic increment/decrement when a reference is copied or drops out of scope.

Compiler-inserted calls

// Your Swift source:
func process() {
    let obj = MyClass()
    use(obj)
}

// What the compiler effectively generates (pseudo-code):
func process() {
    let obj = swift_allocObject(MyClass.self)  // malloc + refCount=1
    swift_retain(obj)                            // passing to `use` may need retain
    use(obj)
    swift_release(obj)                           // parameter ref done
    swift_release(obj)                           // local `obj` done → count=0 → deinit
}

The compiler optimises redundant pairs away — it won't emit a retain+release if the lifetime is trivially bounded in the same basic block.

Object header and reference count encoding

On 64-bit Apple platforms, every heap object begins with two words:

WordFieldDetails
0 (8 bytes)isaPointer to class metadata. On ARM64 the top bits encode type flags (is-pure-ObjC, has-custom-deinit, etc.) — "isa tagging".
1 (8 bytes)RefCountsBit-packed: strong count (30 bits), unowned count (7 bits), flags (immortal, deiniting, side-table present, etc.).

Side table

When the inline refcount bits overflow (strong count > 2^30) or a weak reference is taken, ARC allocates a separate side table for that object. The RefCounts word is replaced with a pointer to the side table. The side table holds:

  • Full strong count (64-bit)
  • Weak count (64-bit)
  • Unowned count
  • The original object pointer

This is rare in practice but explains why weak references have a small extra cost over unowned.

Retain/release atomicity

Both swift_retain and swift_release use atomic fetch-add/fetch-sub. On ARM64 this is a ldadd instruction (LSE) or an stlxr/ldxr loop on older CPUs. This is thread-safe but adds a memory barrier, which prevents CPU reordering and causes cache coherency traffic on multi-core.

On the fast path (refcount in the inline bits and not overflowing), retain/release are a few nanoseconds each. That's why avoiding unnecessary class copies in tight loops matters.

Compiler optimisations

OptimisationEffect
ARC coalescingMultiple retain/release pairs within one function collapsed into fewer operations

Devirtualizationfinal class or non-overridden method → static dispatch → inlineable retain elision

Unowned retain/check

unowned references use swift_retainUnowned — which checks that the unowned count hasn't been decremented to zero (i.e., the object still exists) without actually retaining. If the object is dead, it traps immediately. This is faster than weak (no side table write) but unsafe after deallocation.

class Owner {
    lazy var child: Child = Child(owner: self)
}
class Child {
    unowned let owner: Owner   // no retain; traps if Owner is dead
    init(owner: Owner) { self.owner = owner }
}

Deinit chain

When swift_release drops the strong count to zero:

  1. The object's deinit runs (your Swift-defined cleanup)
  2. Superclass deinit runs (if any), walking up the class hierarchy
  3. At the root (NSObject), dealloc is called
  4. free(ptr) returns the memory to the heap

Stored strong references inside the object are released during deinit, potentially triggering cascading deallocs.

class Animal {
    deinit { print("Animal deinit") }
}
class Dog: Animal {
    deinit { print("Dog deinit") }  // runs first
    // then Animal deinit runs automatically
}

var d: Dog? = Dog()
d = nil
// prints: "Dog deinit", then "Animal deinit"
