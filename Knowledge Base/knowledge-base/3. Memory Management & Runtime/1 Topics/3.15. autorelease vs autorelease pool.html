3.15. autorelease vs autorelease pool

Historical Context (MRC Era)

Before ARC, Objective-C programmers managed retain/release manually. autorelease was a way to say "release this object, but not yet — defer until the pool drains." This let a method return an object it no longer owns without an immediate crash: the caller got a valid pointer for long enough to retain it if desired.

// Old MRC Obj-C pattern (not ARC)
- (NSString *)greet {
    NSString *s = [[[NSString alloc] initWithFormat:@"Hello"] autorelease];
    return s;  // safe: will be released when pool drains, not now
}

autorelease vs autorelease pool — Definitions

ConceptWhat it is
autorelease (the message)Registers an object with the current autorelease pool. The pool will send it release when the pool is drained.
Autorelease poolA stack-based collection that holds autoreleased objects. Draining the pool sends release to every object it holds, then destroys the pool.
@autoreleasepool { }Modern syntax. Creates a pool on entry, drains it on exit (even on throw).

Modern Swift / ARC — When Does It Matter?

Under ARC, the compiler inserts retain/release automatically. For pure Swift objects ARC uses direct release — no autorelease pool needed. However, you still interact with the pool when calling Obj-C APIs that return autoreleased objects (most of Foundation/UIKit), because those APIs were written against the Obj-C convention.

The main thread is covered automatically: UIKit and AppKit wrap each run-loop iteration in an @autoreleasepool, so objects autoreleased during normal UI events are cleaned up between frames.

When You Must Use @autoreleasepool

1. Tight loops creating many Obj-C temporaries

// Bad — all UIImages accumulate until run loop ends (huge peak RSS)
for path in imagePaths {
    let img = UIImage(contentsOfFile: path)
    process(img)
}

// Good — pool drains every iteration; memory stays flat
for path in imagePaths {
    autoreleasepool {
        let img = UIImage(contentsOfFile: path)
        process(img)
    }
}

2. Background threads

Threads you create (GCD, Thread, OperationQueue) have no implicit pool. If Obj-C APIs are called on them, autoreleased objects accumulate indefinitely. The runtime will log a warning and will eventually create a pool, but relying on that is fragile.

DispatchQueue.global().async {
    autoreleasepool {
        // Any Obj-C APIs (NSData, NSString, Foundation) called here
        // are safely drained when the block returns
        let data = NSData(contentsOfFile: heavyFile)
        parseData(data)
    }
}

3. Unit tests and command-line tools

Test runners and non-AppKit/UIKit executables (Swift scripts, CLIs) have no run-loop pool. Wrap main or test bodies in @autoreleasepool if they use Foundation.

Always use @autoreleasepool { } in new code. NSAutoreleasePool is unavailable in Swift.

ARC Return Value Optimization

The Swift/Obj-C compiler can elide the autorelease entirely when the caller and callee are compiled together (same module, LTO, or direct call). This is the autoreleasepool elision / retain-release elimination optimization. The object is returned directly with a strong reference, bypassing the pool. You cannot rely on an object being autoreleased — it may or may not be, depending on optimization level and call context.

Thread Safety

Each thread has its own stack of autorelease pools. Pools are per-thread — you cannot drain another thread's pool. Objects can only be released on the thread that autoreleased them (because that thread owns the pool). This is one reason passing autoreleased objects between threads is unsafe without an explicit retain.
