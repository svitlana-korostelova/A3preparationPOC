3.18. When to use struct vs class?

The Core Distinction

Structs are value types: each copy is independent. Mutation of one copy does not affect another. No ARC, no heap allocation for the struct itself, no reference counting overhead.

Classes are reference types: all variables pointing to the same object share the same instance. Mutation is visible everywhere that holds a reference. ARC tracks the lifetime via retain/release.

Decision Table

CriterionStructClass
Copying semanticsEach copy is independent — idealShared reference — all aliases see mutations
Shared mutable state needed?No — copies divergeYes — one object, many observers
Inheritance required?No (protocols only)Yes — class hierarchy
Obj-C interop needed?Bridged but limitedFull bridging with @objc / NSObject
Lifecycle control needed?No deinitYes — deinit for cleanup (file handles, etc.)

Use a Struct When…

// ✅ Data models — independent copies make sense
struct User {
    var id: UUID
    var name: String
    var age: Int
}

// ✅ Geometry / math — value semantics, hot path
struct Point { var x, y: Double }
struct Rect  { var origin: Point; var size: Size }

// ✅ API response models (Codable)
struct ArticleResponse: Codable {
    var id: Int
    var title: String
    var body: String
}

// ✅ SwiftUI views — always structs
struct ProfileView: View {
    let user: User
    var body: some View { Text(user.name) }
}

// ✅ Configuration / options
struct RequestConfig {
    var timeout: TimeInterval = 30
    var retryCount: Int = 3
    var headers: [String: String] = [:]
}

Use a Class When…

// ✅ Shared identity — all holders must see the same mutations
class UserSession {
    var token: String?
    var userId: UUID?
    // Multiple modules hold the same session — changes must be visible everywhere
}

// ✅ Lifecycle management — needs deinit for cleanup
class DatabaseConnection {
    private let handle: OpaquePointer
    init(path: String) { handle = openDB(path) }
    deinit { closeDB(handle) }  // ← only classes have deinit
}

// ✅ UIKit — ViewControllers must be classes
class ProfileViewController: UIViewController {
    override func viewDidLoad() { super.viewDidLoad() }
}

// ✅ Inheritance needed
class BaseRouter {
    func navigate(to route: Route) {}
}
class AuthRouter: BaseRouter {
    override func navigate(to route: Route) {
        // guard auth, then super.navigate
    }
}

// ✅ Observable objects in UIKit / Combine
final class CartViewModel: ObservableObject {
    @Published var items: [CartItem] = []
    // Multiple views / controllers observe this single instance
}

SwiftUI: Almost Always Struct

SwiftUI views are structs by design. The framework diffs view hierarchies and rebuilds cheaply — value semantics make this safe and fast. The exceptions that are classes: ObservableObject view models, UIViewRepresentable coordinators, and @NSApplicationDelegateAdaptor / @UIApplicationDelegateAdaptor.

Common Mistakes

Mistake 1: Making everything a class "to be safe"

// ❌ Unnecessary class — no shared state, no inheritance, no deinit
class Color {
    var r, g, b: Double
}
// Every copy is a reference; unexpected aliasing bugs possible

// ✅ Correct
struct Color {
    var r, g, b: Double
}

Mistake 2: Using struct for shared mutable state

// ❌ Counter struct — each copy diverges, updates don't propagate
struct BadCounter {
    var count = 0
}
var a = BadCounter()
var b = a            // copy
a.count += 1
print(b.count)       // 0 — b is unaffected!

// ✅ If shared mutation is the intent, use a class
final class Counter {
    var count = 0
}
let c = Counter()
let d = c           // same reference
c.count += 1
print(d.count)      // 1 ✓

Mistake 3: Ignoring the overhead of large structs

Value types are copied on assignment. A struct with many large fields (e.g., a 10MB image buffer stored inline) copies that entire payload on every assignment. Use a class (or COW — see topic 3.21) when the data is large and copying is expensive.

The Rule of Thumb

Start with struct. Switch to class only when you need: shared mutable identity, inheritance, deinit, or Obj-C subclassing.

Apple's own Swift standard library follows this: Array, String, Dictionary, Set, URL, Date, IndexPath — all structs with copy-on-write semantics for large storage.
