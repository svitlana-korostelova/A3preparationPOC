3.6. Swift runtime and side table

Short answer

The Swift runtime (libswiftCore) does work at run time that the compiler cannot do ahead of time. The side table is an extra heap record for an object's reference counts, created mostly when a weak reference is taken.

What the runtime does

  • Allocates objects (swift_allocObject).
  • Runs ARC (swift_retain, swift_release).
  • Casts types (as?, is).
  • Dispatches protocol calls (witness tables).
  • Provides reflection (Mirror).

Since Swift 5 the runtime ships inside the OS, so apps link to it and do not bundle it.

Object layout

  • Every class object starts with a 16-byte header: type metadata pointer and ref counts.
  • Your stored properties follow the header.

Method dispatch

  • Class methods: vtable call. Use final to make it a direct call.
  • Protocol methods (any P): witness table call, plus unpacking the existential. Generic code with a concrete type is faster.
  • @objc methods: objc_msgSend. Slowest, so use only when needed.

Swift vs Objective-C runtime

  • Swift uses static dispatch (vtables, witness tables). Obj-C uses message sending.
  • Pure Swift classes are not registered with Obj-C.
  • Subclassing NSObject or using @objc is needed for KVO, #selector and target-action.

The side table

  • The header has little space for counts. Most objects keep counts inline.
  • When an object needs more, the runtime moves its counts to a side table and stores a pointer to it in the header.
  • It is created mainly when a weak reference is taken.

How a weak reference works

  • A weak variable points to the side table, not the object.
  • On read, the runtime returns the object if it is alive, or nil if it is dead.
var owner: Owner? = Owner()
let obs = Observer()
obs.owner = owner   // side table created
owner = nil          // object dies; side table stays alive
print(obs.owner)    // nil

Why it matters

  • Objects without weak references never get a side table.
  • When the object dies, the runtime updates the side table, not every weak variable.

Weak vs unowned

  • weak: needs a side table, returns nil after the object dies.
  • unowned: no side table, traps if the object is already dead.
