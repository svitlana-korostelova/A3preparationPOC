3.6. Swift runtime and side table

Short answer

The Swift runtime (libswiftCore.dylib) is the library inside every Swift process that does the work the compiler cannot do ahead of time: allocate objects, run ARC, cast types, look up protocol conformances and provide reflection. The side table is a small extra heap record the runtime adds to an object when it needs more counter space, mainly when someone takes a weak reference to it.

Since Swift 5 the runtime ships inside the OS (ABI stable), so apps link to it instead of bundling it.

Object layout and allocation

MyClass() becomes a call to swift_allocObject. It allocates memory, writes a 16-byte HeapObject header and then your init runs.

0 (8 bytes)Metadata pointer (isa)Points to the class's type metadata (vtable, field info)

Your stored properties follow the header.

An existential container (any Protocol) is 5 words: 3 for an inline value (bigger values go to a heap box), 1 for type metadata, and 1 per protocol for its witness table. This is why any P costs more than a generic some P.

The side table

The problem

The 8-byte ref-count field has to hold the strong count, unowned count, weak information and flags. Space is tight, so the runtime uses two tiers:

  • Fast path (most objects): counts are stored inline in the header.
  • Slow path: the header holds a pointer to a side table object that holds the full counts.

When it is created

  1. Someone takes a weak reference to the object (the usual reason).
  2. An inline count overflows (rare).

The runtime allocates the side table, moves the counts into it and puts a pointer (plus a "has side table" flag) in the header. Callers see no difference.

// HeapObjectSideTableEntry (simplified)
struct SideTable {
    var object: UnsafeRawPointer?   // back pointer; cleared when the object dies
    var strongCount: UInt32
    var unownedCount: UInt32
    var weakCount: UInt32        // starts at 1: the object itself counts as one
}

How a weak reference works

A weak variable stores a pointer to the side table, not to the object. Loading it calls swift_weakLoadStrong:

  1. Follow the pointer to the side table.
  2. If the object is still alive, atomically increment the strong count (so it cannot die mid-use) and return it.
  3. If it is dead, return nil.
var owner: Owner? = Owner()
let obs = Observer()
obs.owner = owner   // side table created, weakCount = 2
owner = nil          // object dies; side table stays because obs still points to it
print(obs.owner)    // nil: read through the side table
// when obs goes away, weakCount reaches 0 and the side table is freed

Why this design

  • O(1) death: the runtime updates one place (the side table), not every weak variable. No scan.
  • Pay only when used: objects with no weak references never get a side table.
  • Thread-safe loads thanks to the atomic increment in step 2.
  • Side tables can outlive the object. That is exactly what lets a weak variable safely read nil later.
