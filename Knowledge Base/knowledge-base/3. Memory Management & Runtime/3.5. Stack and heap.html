3.5. Stack and heap

Short answer

The stack is fast, private to one thread, and freed automatically when a function returns. The heap is shared, flexible, slower, and its lifetime is managed by ARC. Local value types (struct, enum, tuples, Int) usually live on the stack. Class instances always live on the heap.

Stack details

A function call moves the stack pointer down by the size of its frame (return address, saved registers, arguments, locals). Returning moves it back up. There is no free(), no ARC and no lock.

Stack overflow happens when frames exceed the stack size, almost always from unbounded recursion. The crash is EXC_BAD_ACCESS on the guard page. On a 512 KB thread you get roughly 1,000–2,500 recursive calls with typical frames. For deep recursion, use an explicit stack in an Array, which lives on the heap:

func dfs(root: TreeNode?) {
    var stack: [TreeNode] = root.map { [$0] } ?? []
    while let node = stack.popLast() {
        // process node
        if let r = node.right { stack.append(r) }
        if let l = node.left  { stack.append(l) }
    }
}

Heap details

  1. A class init calls swift_allocObject, which calls malloc.
  2. The allocator finds a free block and the runtime writes the 16-byte header (metadata pointer + ref counts).
  3. ARC retains and releases as references are copied.
  4. At count 0: deinit, then free().
class Node {
    var value: Int     // 8 bytes
    var next: Node?   // 8 bytes
}
// Heap size: header 16 + 8 + 8 = 32 bytes minimum

Apple's allocator (libmalloc) uses per-thread caches for small blocks, so contention is low. It cannot move live Swift objects, so many tiny, short-lived allocations can fragment memory.

Why it matters for speed

A heap allocation costs the allocation itself, ARC traffic and cache misses. In a hot path (60 fps rendering, large parsing), replacing small classes with structs can remove thousands of allocations per frame.

class FrameClass { var x, y, w, h: Double = 0 }   // heap + ARC per instance
struct FrameStruct { var x, y, w, h: Double }     // inline, no ARC

Measure with Instruments → Allocations before you optimize.

When a value type ends up on the heap

"Struct = stack" is a default, not a rule. A value is placed on the heap when it must outlive the current stack frame, or when its size is not known or too big.

SituationWhere the value goes
Local variable, not capturedStack
Captured and modified by an @escaping closureHeap box shared with the closure
Stored property of a classInside the class's heap block
Protocol existential (any P) bigger than 3 words (24 bytes)Heap buffer, pointer kept in the existential container
indirect enum caseHeap box for the payload
Local used after an awaitTask's heap-allocated async frame
Array, String, Dictionary contentsHeap buffer (the struct itself is only a pointer + metadata)
func makeCounter() -> () -> Int {
    var count = 0          // Int, but boxed on the heap
    return { count += 1; return count }   // the closure outlives this frame
}

indirect enum Tree {
    case leaf(Int)
    case node(Tree, Tree)   // recursive, so each payload is boxed
}

The reverse also happens: when escape analysis proves a class instance never leaves its function, the optimizer may allocate it on the stack. Do not rely on it.

Quick rule

  • Plain data, hot paths, independent copies → struct.
  • Shared identity or controlled lifetime → class, and accept the heap cost.
  • Profile first. Do not guess.
