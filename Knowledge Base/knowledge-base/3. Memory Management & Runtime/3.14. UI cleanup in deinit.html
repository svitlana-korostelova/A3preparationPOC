3.14. UI cleanup in deinit

Short answer

deinit runs on the thread that released the last strong reference. That is not always the main thread. If deinit touches UI, switch to the main thread first with DispatchQueue.main.async. Do not capture self in that closure. Copy the values you need first. See 3.2.

Why it can go wrong

A background closure can hold the last reference to a screen. This happens when the user closes the screen while a download is still running.

  1. The user closes the screen. The navigation stack drops its reference on the main thread.
  2. The download is still running. Its closure holds a strong reference to the controller.
  3. The download finishes on a background queue. The closure is released and the last reference is gone.
  4. deinit runs on the background thread. A UI call there gives a purple runtime warning, a glitch, or a crash.

Bad example

class VideoPlayerViewController: UIViewController {
    let spinner = UIActivityIndicatorView()
    let loader = VideoLoader()

    func start() {
        loader.download { [self] data in   // strong capture, runs on a background queue
            self.play(data)
        }
    }

    deinit {
        spinner.stopAnimating()            // ❌ UI call, may run on a background thread
    }
}

Fix

deinit {
    let spinner = self.spinner            // copy what you need
    DispatchQueue.main.async {
        spinner.stopAnimating()           // ✅ runs on main
    }
}

Notes

  • Most classes never hit this, because their last release happens on the main thread. It only shows up when a background closure or task can hold the last reference.
  • Better still: use [weak self] in the closure (see 3.3). Then the background work does not keep the screen alive.
  • Do not use self inside the async block. The object is already being destroyed.
