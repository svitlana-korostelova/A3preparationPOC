3.4. Retain cycles and leaks

Short answer

A retain cycle (strong reference cycle) is when two or more objects hold strong references to each other in a loop. None of their counts can reach 0, so ARC never frees them. The memory stays until the app is killed. Break the loop by making one link weak or unowned (see 3.3).

Three common cycles

1. Two objects pointing at each other

class Person {
    var apartment: Apartment?     // strong
    deinit { print("Person gone") }
}
class Apartment {
    var tenant: Person?         // strong → cycle. Fix: weak var tenant
    deinit { print("Apartment gone") }
}

var john: Person? = Person()
var flat: Apartment? = Apartment()
john?.apartment = flat
flat?.tenant = john
john = nil; flat = nil   // no deinit prints: both leak

2. Strong delegate

class NetworkClient {
    var delegate: NetworkDelegate?        // ❌ should be weak
}
// ViewController → client (strong), client → ViewController (strong) = cycle

3. Closure stored on self

class ViewModel {
    var onUpdate: (() -> Void)?

    func setup() {
        onUpdate = { self.reload() }                 // ❌ self → closure → self
        onUpdate = { [weak self] in self?.reload() }  // ✅
    }
    func reload() {}
}

A closure only creates a cycle if self also holds the closure. A one-shot closure that is not stored (e.g. DispatchQueue.main.async) only extends the lifetime until it runs.

Leaks that are not cycles

The object is kept alive by something outside your code.

  • Timer with target: self — the run loop holds the timer and the timer holds self. Call invalidate() (not in deinit, because deinit never runs; use viewWillDisappear or the block API with [weak self]).
  • Old NotificationCenter API — since iOS 9 selector-based observers are not retained, but block-based observers (addObserver(forName:...)) must be removed, and the block needs [weak self].
  • Combine sink / assign(to:on:) — assign(to:on: self) retains self. Store the AnyCancellable and use [weak self] in sink.
  • Long Swift Task — a task that captures self keeps it alive until it ends. Cancel it or use [weak self].
  • Singletons and caches — anything they reference lives for the whole app.
// Timer holds its target strongly until invalidated
timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
    self?.tick()
}
// still call timer?.invalidate() when the screen goes away

How to prevent them

ToolUse when
weak varDelegates, parent links, or any link where the other side may be nil
unownedThe other object always outlives this one
[weak self] in closuresThe closure is stored, or runs later than the screen's lifetime
structNo identity needed. Value types cannot form cycles
Invalidate / cancelTimers, CADisplayLink, Combine subscriptions, Tasks

How to find them

  • Print in deinit and navigate back from the screen. No print means a leak.
  • Memory Graph Debugger and Instruments — see 3.11.
  • Unit test: keep a weak reference and assert it is nil after the strong one goes away.
func testNoLeak() {
    weak var weakVM: ViewModel?
    autoreleasepool {
        let vm = ViewModel()
        vm.setup()
        weakVM = vm
    }
    XCTAssertNil(weakVM, "ViewModel should be deallocated")
}

Review checklist

  • Every delegate property is weak.
  • Every closure stored in a property uses [weak self] (or [unowned self] with a proven lifetime).
  • Every Timer, CADisplayLink, observer and subscription has a matching stop or cancel.
