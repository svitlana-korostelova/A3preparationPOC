3.11. Detecting memory issues

Short answer

Start with deinit prints and the Memory Graph Debugger for retain cycles. Use Instruments (Leaks, Allocations) for growth over time. Use Address Sanitizer for crashes from freed or corrupted memory. Each tool answers a different question.

1. Memory Graph Debugger

  1. Run the app, use the suspect flow, then leave the screen.
  2. Click Debug Memory Graph (three connected nodes) in the debug bar.
  3. Look for instances of your screen or view model that should be gone. A leaked object shows a purple "!". Select it to see the chain of strong references.
  4. Turn on Scheme → Run → Diagnostics → Malloc Stack Logging (Live Allocations Only) first to see the creation backtrace.

2. Instruments — Leaks

  1. Product → Profile → Leaks.
  2. Use the app. Red marks show leaked objects.
  3. Open Cycles & Roots to see the cycle, and the call tree (inverted) to find where it was allocated.

Leaks only finds memory with no references left (usually cycles). It misses "abandoned" memory that is still referenced, like a growing cache. Use Allocations for that.

3. Instruments — Allocations

  • Mark Generation: take a snapshot, do an action, take another. Memory that remains in the new generation was not freed.
  • Statistics: sort by Persistent to see which types stay alive and how many.
// Back-and-forth test for a leaking screen:
// open A → mark generation 1
// push B, go back → mark generation 2
// repeat several times. If generation 2+ keeps growing with B's objects, B leaks.

4. Address Sanitizer

Compiler instrumentation, enabled per scheme: Run → Diagnostics → Address Sanitizer. It slows the app about 2×. It detects use-after-free, heap and stack buffer overflows. It does not find retain cycles. For Swift this is mostly relevant with Unsafe*Pointer, Unmanaged and C interop (see 3.12).

5. Malloc Stack Logging

Records the call stack of each allocation. Turn it on in Scheme diagnostics, or with the environment variable MallocStackLogging=1. From the command line, malloc_history <pid> <address> shows how an address was allocated.

6. Runtime issues

Purple warnings in the Issue navigator, with no setup: "Publishing changes from background threads", "UI API called from a background thread", and main-actor violations. They are not leaks, but races like these often lead to freed-object crashes.

Typical causes to check first

Details and fixes are in 3.4.

  • Stored closure capturing self without [weak self].
  • Strong delegate property.
  • Timer with target: self that is never invalidated.
  • Combine subscriptions, Tasks or block observers that capture self.
  • Singletons and caches that hold large objects forever.
  • Obj-C temporaries in a long loop (see 3.9).

Before shipping

  • Navigate through all main flows, then check the Memory Graph for leftover screens.
  • Run Leaks, and run Allocations on back-and-forth navigation.
  • Check memory on the oldest supported device. It has the lowest jetsam limit.
